# 輸入對照檢查：brief 系列 → PRD

## 範圍與方法

- **對照的輸入**：`briefs/brief-research-radar-2026-11-06/brief.md`（下稱 brief）、同資料夾 `addendum.md`（下稱 brief addendum）、`docs/input/brief-input.md`（下稱構想文件）。
- **被檢查的文件**：`prd.md`、`addendum.md`（下稱 PRD addendum）。
- **判斷標準**：`.memlog.md` 記錄過的後期決定一律視為刻意變更，不算缺口。只列出「PRD 沒寫、也沒有決定紀錄」或「PRD 和輸入矛盾、卻沒說明原因」的項目。
- **已核對、屬於刻意變更而跳過的**：BYOK 移除（#12）、訪客改靜態快照、即時問答延到 Should（K1）、中大 OpenURL 不做、PDF 取消 lab 選項、「候選題目」改「證據簡報」、每日抓取改每週、開發期改 12/25 起、付費全文 v1 只存不擷取、GROBID 延到 Should（K5 縮小版）、Zotero 推送 Could、不寄信給圖書館。

## 發現（依重要程度排序）

### G1. 「筆記」與「個人文獻庫」在 PRD 裡沒有對應功能（缺口，高）

- **輸入出處**：構想文件第 29、39、55 行（成員可用「個人文獻庫、上傳 PDF、筆記、問答、查看共用文獻庫」；F6「個人文獻庫、實驗室共用文獻庫」）；brief「使用者」表、解決方式第 6 點；brief addendum F5、F6。
- **PRD 現況**：
  - FR-35 規定「筆記預設 private，可以分享給全實驗室」，但沒有任何 FR 讓使用者建立或編輯筆記。§2.1 成員能做的事也沒有「筆記」。
  - FR-28 的問答範圍包含「個人文獻庫」，§3 名詞表卻沒有定義它，也沒有 FR 說明論文怎麼進入個人文獻庫。只有 UJ-1 的「加入待讀清單」、§10 的「待讀清單／加入合集」，而合集（S17）是 Should。
- **為什麼是問題**：memlog 沒有刪除這兩項的紀錄。現在 FR-35 的可見範圍規則和 FR-28 的範圍篩選，都指向不存在的東西。到了 UX 和拆 Story 階段，會不知道要不要做、該做成什麼樣子。
- **建議放置**：
  - §3 名詞表加「個人文獻庫」（例如：自己上傳的論文＋加入待讀清單的論文）和「筆記」的定義。
  - §4.11 新增一條 FR（或併入 FR-35），寫清楚 v1 的個人文獻庫怎麼形成、筆記是自由文字還是只有結構化欄位。如果 v1 決定不做個人筆記，就從 FR-35 拿掉「筆記」，並在 §7 或 §8.3 寫明延後。
  - §2.1 成員欄同步更新。

### G2. 使用者修正「筆記」（結構化摘要、研究模型）在 v1 沒有路徑（缺口／內部不一致，中高）

- **輸入出處**：構想文件 F3「使用者可以修正分類與筆記」（第 50 行）；brief 解決方式第 3 點同句。
- **PRD 現況**：v1 只有 FR-16 修正分類。研究模型的手動填寫是 Should，中文結構化摘要沒有修正機制。memlog #5 只決定了「分類」修正，K2 只說「完整介面併入 admin UI（Should）」，兩者都沒有提到結構化摘要和研究模型的修正。
- **內部不一致**：FR-4 的驗收條件要求「重跑萃取後人工值不變，並記錄新模型與人工值的同意率」，等於假設 v1 已經有人工修正萃取欄位的資料。但 v1 唯一的萃取人工輸入只有構念合併的 CLI 匯入（FR-18）。
- **建議放置**：FR-16 擴充範圍，或在 §4.6 Should 清單裡明寫「結構化摘要／研究模型修正延到 Should，v1 只能改分類」。同時在 FR-4 註明 v1 的人工值來源（分類下拉選單、合併 CLI、金標準標註）。

### G3. 構想文件說結構化筆記「可以直接用在文獻回顧」，PRD 改成「不可直接放入論文」，但沒交代轉向（未說明的矛盾，中）

- **輸入出處**：構想文件第 27 行（「貼合資管行為研究的閱讀方式，可以直接用在文獻回顧」）；brief「要解決的問題」第 2 點（「只能一篇一篇手動抄進筆記」）。
- **PRD 現況**：FR-14 寫「供篩選閱讀，不可直接放入論文」，FR-38 只能複製引用。這個方向和 M09 誠信呈現一致，本身合理。但 memlog 只記錄了「研究問題不由 AI 生成」，沒有記錄「結構化筆記從文獻回顧素材降級成篩選工具」這件事。原本痛點「手動抄筆記」在 v1 也沒有說明由什麼取代：文獻整理表 S02 是 Should。
- **為什麼是問題**：這是產品意圖的轉變。PRD 讀者（尤其同學和面試官）會問「那整理文獻回顧的痛點誰解決？」
- **建議放置**：§4.4 開頭補一句：結構化摘要的定位從「文獻回顧素材」改成「篩選閱讀」，理由是誠信規範（M09），文獻回顧整理的路徑是 S02 文獻整理表（Should）＋ Zotero。必要時在 memlog 補一筆。

### G4. 「系統保留改用個人 key 的路」被 BYOK 的移除一起吃掉了（缺口，中）

- **輸入出處**：構想文件「設計原則」LLM 費用一條（第 84 行：「額度綁在 Max 訂閱上，系統要保留改用個人 key 的路」）；brief「限制與原則」LLM 費用一條（「系統保留改用個人 key 的路」）。
- **辨析**：這裡的「個人 key」指的是**系統本身**的 API 金鑰來源：Max 訂閱停掉或額度用完時，可以改用 Kevin（或日後接手者）自己付費的 key。這和 memlog #12 移除的「成員各自填 key（BYOK）」不是同一件事。
- **PRD 現況**：§6 只寫「Max 附贈額度」，NFR-9 把模型 ID 與價格表放進設定檔，FR-46 處理帳號擁有者，但沒有一條需求保證「換金鑰來源／帳單來源不用改程式」。學弟妹接手時不會有 Kevin 的 Max 訂閱，這點和支柱四「可接手」直接相關。
- **建議放置**：NFR-9 或 NFR-15 加一句「LLM 金鑰與帳單來源只靠環境變數切換，不綁 Max 訂閱」，或放進 FR-46 的驗收條件。§7「不提供個人 API key（BYOK）」旁邊註明「指成員個人 key，系統金鑰可替換」，避免誤讀。

### G5. 「邊做邊學、每天留時間弄懂為什麼」這個意圖只剩 FR-8 一句（質性缺口，中）

- **輸入出處**：構想文件「時程」第 154 行、brief addendum「第一版時程細節」（「AI 寫程式很快，時間主要花在審查、測試和理解設計；每天要留時間弄懂『為什麼這樣做』」）。memlog 的 #1、#3 也都用「邊做邊學」當理由。
- **PRD 現況**：§1 有「講得出每個決策的理由」，§4.2 有「Kevin 想藉此學會…」，但兩件事都沒寫：
  - 學習本身就是專案目標之一，這也解釋了為什麼某些 Must（完整 pipeline）沒有被砍。
  - 時程是否預留每天的理解時間。§8.4 可用 180–225 h、功能預算 120–150 h，差額是不是理解與審查時間，沒有說明。
- **建議放置**：§1 第三段補一句「學習與理解是目標之一」；§8.4 或 PRD addendum 的工時表註明「可用時數與功能預算的差額，保留給審查、測試與理解設計」。

### G6. 分類清單（OQ-07）原本要和同學討論後定版，PRD 直接凍結初版（未說明的矛盾，中）

- **輸入出處**：brief 解決方式第 3 點（「這份清單會在訪談同學後定版（OQ-07）」）、brief 風險表 OQ-07；構想文件 OQ-07（「參考 Notion 論文筆記的欄位，再和同學討論」）。
- **PRD 現況**：FR-15「沿用 brief 初版」。memlog 只寫「推定，使用者未反對；OQ-07 不變」，語意不清：是「仍待確認」還是「維持初版」？§11 待確認事項和 §12 假設索引都沒有列 OQ-07。
- **為什麼重要**：FR-3／FR-41 要求 schema 與金標準在第一次十年匯入前定版。分類清單如果之後才和同學討論而改動，50 篇標註要重做。
- **建議放置**：二擇一：(a) §12 加假設「分類清單維持 brief 初版，未和同學討論」；(b) §11 加待確認事項「金標準標註前，和同學確認分類清單」。

### G7. 給同學試用的測試環境（家裡 PC＋Cloudflare Tunnel）在 PRD 消失（缺口，中低）

- **輸入出處**：brief「限制與原則」環境一條（「Mac 只用來開發。測試環境用家裡的 PC＋Cloudflare Tunnel，給同學試用」）；brief addendum「主機」一條。
- **PRD 現況**：§8.4 時程從開發直接跳到 2027-01 部署 Azure，沒有「同學先在測試環境試用」的階段。§10 的第一次可用性測試用的是設計稿。NFR-17 的「Kevin 的電腦」也沒說是 Mac 還是家裡的 PC。
- **為什麼重要**：SM-1 要求 2/14 前 4 位同學都在正式環境用過。沒有測試環境，同學最早到 1 月才摸得到真系統，回饋來不及改。
- **建議放置**：§8.4 時程加一列「測試環境（家裡 PC＋Tunnel）給同學試用」的時間點；PRD addendum ARCH 表加一項「測試環境與正式環境的關係、重運算放哪台電腦」。

## 次要項目（低）

- **作品集要補的三塊能力**（構想文件第 19 行、brief 摘要第 3 段：部署上雲的後端、資料 pipeline、RAG，以及目標職缺）：PRD §1 只說「作品集主力專案」。這三塊是混合架構（不全部用 Cloudflare，保留 Python＋PostgreSQL）的理由，建議在 §1 補半句，或在 PRD addendum 的 ADR 清單指向 brief addendum 的「混合架構」段落。
- **Crossref**：構想文件 F1、brief 解決方式第 1 點把它列為抓取來源。PRD FR-8／FR-11 只剩 OpenAlex／S2／上傳 PDF，FR-12「有 DOI 自動補齊書目」也沒寫用哪個來源。建議在 ARCH-9 或 FR-12 註明補書目的來源。
- **Semantic Scholar 標示要求**：brief addendum F1 寫「公開顯示要標示並連回 Semantic Scholar」。PRD 的 Could 只寫「先確認授權、示範站不得使用」，建議補上「實驗室內顯示時要標示來源並連回」。
- **「比較這幾篇的研究方法」**：構想文件 F5、brief addendum F5 的範例問題需要「指定幾篇」當範圍。FR-28 的範圍只有個人／實驗室／全部三種。如果 v1 不支援，在 FR-28 或多輪追問（Should）旁註明即可。
- **願景段落**：brief「願景」寫的擴充主題（AI／LLM、半導體製造）、串起全文／引用／每週推播，PRD 沒有對應的長期願景段落，只有 FR-36 的「設定即資料」。可在 §1 末尾或 §8.3 補一句。
- **「真實回饋」怎麼收**：SM-1 要求「蒐集到回饋」，但沒寫怎麼收。§10 上線兩週後的第二次可用性測試可以當作收集方式，建議在 SM-1 寫明。
