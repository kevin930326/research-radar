# ADR-0015：AI 產出怎麼存、怎麼換版，以及哪一種論文做哪些處理

- 狀態：提議（等 Kevin 在 PR 確認）
- 日期：2026-11-12
- 對應：PRD FR-1、FR-3、FR-4、FR-11、FR-14、FR-15、FR-17、FR-18、FR-37、FR-49；UX 文件「AI 產出還沒好」的各種狀態；架構文件 AD-7、AD-10、AD-30

## 背景

系統有四種由模型產生、要存下來的東西：中文重點、分類（主題與方法）、研究模型（構面與假設）、合併建議的判斷。PRD FR-1 要求每一筆都查得到來歷（哪個模型、哪版 prompt、看的是標題還是摘要），而且「同一篇、同一種工作、同一種語言只有一筆有效」，舊的標成已取代、不刪除。

第一版的架構只寫了「每張 AI 表都要有來歷欄位和狀態」。審查時發現這樣寫，各 Story 會做出不相容的東西：

1. **一次產出很多列的資料沒有說怎麼辦。** 一篇論文一次擷取出 5 條假設；重跑後變成 4 條。如果每條假設各有自己的「有效／已取代」，沒有人知道舊的第 5 條該不該留著。
2. **換模型的結果一寫進去就生效**，但 FR-4 規定「同意率低於門檻不得切換有效版本」，中間缺一個「先放著、還不算數」的狀態。
3. **一篇論文可能有兩個來源的摘要**（OpenAlex、之後的 Semantic Scholar）。給模型看的、算向量的、畫面顯示的、算「有摘要」的，如果各挑各的，同一篇論文在不同地方會不一致。
4. **「還沒有 AI 產出」有很多種原因**（排隊中、預算用完延後、沒有摘要所以不做、被驗證拒收），UX 文件每一種都有不同的畫面文字，但 API 要回什麼形狀沒有定。
5. **哪些論文要跑哪些 AI 工作沒有一個地方說了算。** 被排除的非研究文章、成員私下匯入的追蹤範圍外論文、手填的書目，匯入、上傳、合併建議、檢索各自判斷的話一定會不一樣。

## 考慮過的選項

**多列的產出怎麼存**

- **A. 每一列各帶自己的來歷與狀態。**（第一版的寫法）
- **B. 一次產出一列「表頭」，來歷與狀態只在表頭；細項掛在表頭底下。**
- **C. 一次產出存成一整包 JSON。** 最簡單，但關係的篇數要用 SQL 從假設和構面算（ADR-0012），假設也要用外來鍵指到構面，一整包 JSON 做不到。

**換模型的結果**

- **甲. 寫進去就取代舊的。**
- **乙. 先存成「候選」，評估過了才由一個指令切換。**

**哪些論文做哪些處理**

- **一. 各流程自己判斷。**
- **二. 一個函式回答，其他地方只能問它。**

## 決定

**B＋乙＋二。**

### 一次產出一列表頭

1. 表頭表有四張，一張對應一種工作：

   | 表頭表 | 底下掛的細項 | 對象 |
   |---|---|---|
   | `zh_summary`（中文重點） | 沒有，內容就在表頭 | 論文 |
   | `classification`（分類） | `classification_label`：一列一個標籤，記是主題還是方法，以及設定檔裡的代號 | 論文 |
   | `research_model`（研究模型） | `construct_mention`（提到的構面）、`hypothesis`（假設） | 論文 |
   | `merge_judgment`（合併建議的 LLM 判斷） | 沒有 | 一筆合併建議 |

2. 表頭的欄位，四張表都一樣：

   | 欄位 | 內容 |
   |---|---|
   | `run_id` | 指向那一次模型呼叫的來歷紀錄（模型、prompt 版本、設定檔版本、程式版本；ADR-0009） |
   | `input_kind` | 模型看的是什麼：`title`、`abstract`、`fulltext` |
   | `input_sha256` | 輸入的指紋：送給模型的內容，加上會影響結果的設定檔版本（分類表、情境值清單） |
   | `abstract_id` | 用的是哪一筆摘要（只看標題時是空的） |
   | `lang` | 產出的語言：`zh-Hant`（繁體中文）、`en`；沒有語言可言的（例如分類的代號）用 `zxx` |
   | `status` | `candidate`、`active`、`superseded`、`rejected` |

3. **細項不帶自己的狀態。** 重跑是新增一列表頭和它的全部細項，再把舊表頭標成 `superseded`；舊的細項跟著舊表頭一起變成歷史。內容欄位寫入後不修改。
4. 資料庫保證（部分唯一索引）：同一個對象、同一種語言，最多只有一筆 `active`。
5. 論文層級的擷取結果（研究情境、研究限制、是不是文獻回顧或後設分析）放在 `research_model` 表頭上。
6. 模型沒提到的欄位存空值；「摘要未提及」這類字是畫面文字，不存進資料。
7. 構面的繁中標籤（FR-3）跟著每一筆 `construct_mention` 存。一個構面在畫面上顯示哪一個標籤，由 `repo/constructs.py` 的一個函式決定；挑選規則留給做研究模型的那個 Story，定了寫回這份 ADR。
8. **不算表頭表的**：向量只記是哪一次算的與輸入指紋，同一篇同一個模型直接覆寫（ADR-0005）；合併建議的前兩層（名稱相同、相似度）不是模型的產出，沒有來歷欄位（ADR-0012）。

### 四個狀態與「候選」

| 狀態 | 意思 | 畫面與統計 |
|---|---|---|
| `candidate` | 跑出來了，還不算數 | 不顯示、不進統計 |
| `active` | 現在有效的那一筆 | 用它 |
| `superseded` | 被新的取代了 | 不用，留著查 |
| `rejected` | 沒通過輸出驗證（例如假設原句不在摘要裡） | 不用；同樣的輸入不會自動重跑，要用 `radar runs retry` |

- 平常的流程（新論文、摘要變了、prompt 升版）寫進去就是 `active`，舊的變 `superseded`。
- **換模型**與**量「同一篇跑兩次一不一致」**的結果一律是 `candidate`。跑兩次會被「同一份輸入不重跑」擋住，所以評估走專用的路（`radar eval`，ADR-0009 第 4 點），那是唯一不受這條規則限制的呼叫。評估留下的候選不算「已經有結果」，不會擋住平常的流程。
- **晚到的結果不啟用**：結果要寫成 `active` 之前，先鎖住這篇論文，在同一個短交易裡核對它用的輸入（實際送給模型的內容加設定檔版本）、prompt 版本、模型是不是這篇論文現在該用的，再切換；不是的話只存成 `superseded`（ADR-0009）。
- `candidate` 變成 `active` 只有一條路：`radar runs promote`。要指定是哪一次評估（`eval_run`）；它先查那一次的一致率與同意率，不低於門檻才切換（FR-4），沒過就拒絕執行。同一篇在那一次有多筆候選時用最早執行的那一筆，其餘標成 `superseded`；啟用時上鎖、核對輸入與 prompt 版本的做法和上一點相同；不同的是模型核對這次要切過去的那一個，而且那筆候選的來歷紀錄必須是做完了的（ADR-0009「啟用有兩個入口」）。來歷紀錄被判定失敗的結果，不管走哪一條路都不能啟用。這個指令只有管理者能用。
- 人工修正不受換版影響：有效值由 view 決定，有人工值就用人工值（架構文件 AD-10）。

### 中文重點被回報有誤之後

成員可以回報中文重點的某一欄可能有誤（FR-14 附則）。回報是一筆人工判斷事件，不改內容；被回報的欄位旁邊顯示「有成員回報此欄可能有誤」。

- 管理者看過後有兩種處理，都用 CLI：重新產生，或標記「已確認無誤」。
- 處理結果是**另一筆**人工判斷事件（`summary_report_resolution`），指向原本那筆回報，記結果（`confirmed_ok` 或 `regenerated`）與是哪位管理者。事件只能新增，所以不是去改原本的回報。
- 「有成員回報」的標示＝這一欄有回報、而且還沒有處理結果。由讀取中文重點的那個 view 算，所有畫面共用。
- 第一版只有回報、沒有處理結果這種事件，標成「已確認無誤」後標示沒辦法消失（Codex 審查指出）。

### 一篇論文只有一筆「目前的摘要」

1. 摘要存在 `paper_abstract`，一篇論文可以有多筆（不同來源）。
2. 其中最多一筆標成 `is_current`（資料庫保證）。由寫入摘要的那個模組依設定檔裡的來源優先順序決定，其他地方不能改。
3. **所有用到摘要的地方都只用這一筆**：給模型的輸入、向量的輸入、全文檢索、問答的內容、畫面顯示、「有摘要」的計數與篩選、示範站匯出。
4. 換了一筆就等於摘要變了：輸入指紋不同，相關的 AI 工作會重跑。
5. 表頭上的 `abstract_id` 讓「依摘要來源找出並移除衍生產出」（FR-11）變成一個查詢。
6. 從成員上傳的 PDF 讀出的摘要（FR-13，Should）只有上傳者看得到（ADR-0002），所以不會被標成全站的「目前的摘要」；v1 不做這一項，做的時候要替這個例外補規則。

### API 與示範站怎麼表示一個 AI 區塊

每個 AI 區塊在 API 回應與示範站檔案裡是同一個外層：`state`、`value`、`provenance`。

| `state` | 什麼時候 | 帶內容嗎 | 帶來歷嗎 |
|---|---|---|---|
| `ready` | 有有效的產出 | 是 | 是 |
| `empty` | 跑過了，但沒有可擷取的內容（例如摘要裡沒有假設） | 否 | 是 |
| `pending_interactive` | 使用者觸發的工作正在跑（通常幾秒到幾分鐘） | 否 | 否 |
| `pending_batch` | 排在批次裡（最長 24 小時） | 否 | 否 |
| `deferred_budget` | 這個月的預算用完，延到下個月 | 否 | 否 |
| `no_input` | 這項工作需要摘要，而這篇沒有 | 否 | 否 |
| `failed` | 產出被驗證拒收 | 否 | 否 |
| `not_applicable` | 這種論文不做這項工作（下一節的表） | 否 | 否 |

- 判定只寫在一個函式（`repo/ai_blocks.py`），所有端點與示範站匯出共用。
- 前端的 AI 標章只在有來歷時出現；沒有來歷就不顯示內容（ADR-0010）。
- 判定的順序固定（前面的條件成立就不往下看）：
  1. 這種論文不做這項工作 → `not_applicable`
  2. 這項工作需要摘要而這篇沒有 → `no_input`
  3. 有有效的產出（人工值或 `active`）→ `ready` 或 `empty`
  4. 目前這份輸入的最新結果是 `rejected`，或它所在的批次卡在 `needs_attention`（要管理者確認才會動，ADR-0004）→ `failed`
  5. 這個月的預算用完 → `deferred_budget`
  6. 其餘（排隊中、執行中、暫時性失敗等下一次排程）→ 使用者觸發的是 `pending_interactive`，其他是 `pending_batch`
- UX 文件已經有「還在產生」「這個月的 AI 額度用完了」「沒有摘要」的畫面文字；`failed` 與 `not_applicable` **還沒有對應的文字，由 UX 文件定**。`failed` 不得顯示成「還在產生」（下一節）。

### 被拒收之後會不會重跑

結論：**被拒收的不會自動重跑，停在 `rejected`（畫面上的 `failed`），這是終點狀態。** 只有暫時性的失敗會自動再試，它們從頭到尾都算「還在產生」。原則是：**`pending_*` 只用在不需要人介入、一定會再跑的情況**；要等管理者處理才會動的，一律是 `failed`。

| 情況 | 例子 | 會自動重試嗎 | 最後停在哪裡 |
|---|---|---|---|
| 暫時性失敗 | 連線逾時、被限流、對方服務出錯、批次裡的項目過期或被取消 | 會。連線層先重試，再來是工作層；都不行就留給下一次每週更新補跑 | 不寫結果。畫面一直是 `pending_*`，直到跑成功 |
| 模型拒答 | 模型表示不回答這個請求 | 不會 | `rejected` → 畫面 `failed` |
| 輸出被長度上限截斷 | 產出寫到一半就到上限 | 不會（同樣的輸入與上限，再跑還是會截斷） | `rejected` → 畫面 `failed` |
| 驗證沒過 | 格式不對；假設原句不在摘要裡 | 不會 | `rejected` → 畫面 `failed` |
| 批次卡在等管理者確認 | 送出批次時程式中斷，不確定對方收到了沒（`needs_attention`） | 不會，怕重複送出重複花錢 | 畫面 `failed`，直到管理者用 `radar batches resolve` 處理；處理後回到 `pending_batch` |
| 請求本身不合法 | 批次回報這一筆的請求格式錯誤（是程式的錯） | 不會 | `rejected` → 畫面 `failed`，另寫錯誤日誌 |

- **不算拒收的**：模型選了清單以外的分類標籤或研究情境值時，只丟掉那一個並記數，其餘照常寫入（PRD FR-15）；標籤全部被丟掉的論文是「未分類」，不是 `failed`。
- **為什麼不自動重試**：這幾種多半再跑也是同樣的結果，而每跑一次都要花錢；每週自動重送會變成固定的浪費（ADR-0009）。
- **`rejected` 的列記什麼**：和其他表頭一樣的來歷欄位，加上失敗原因的代碼（全站同一份錯誤代碼清單）；沒有內容。
- **什麼時候會離開 `failed`**，只有三種：
  1. 管理者用 `radar runs retry` 要求重跑（CLI 可以列出全部被拒收的項目與原因）。
  2. 輸入變了：這篇論文目前的摘要換了或更新了，或分類表、情境值清單改版（設定檔版本算在輸入指紋裡）。
  3. 做法變了：prompt 升版或換模型。
  - 後兩種是因為「要不要跑」是照（對象、工作、prompt 版本、模型、輸入指紋）判斷的，其中一項不同就是一件新的工作，會照平常的流程自動跑。
- **原本就有有效產出的論文不會變成 `failed`**：新的一次被拒收時，舊的有效產出照樣有效、照樣顯示（判定順序第 3 步在第 4 步前面）。所以 `failed` 只會出現在「從來沒有成功過」的區塊。
- **每週更新補跑的範圍**：每週更新對所有該做這項工作的論文問一次「要不要跑」，不只問這一週新收的。暫時性失敗沒有留下結果，所以下一週會被排進去；被拒收的有 `rejected` 那一列擋著，不會。
- `failed` 的區塊目前不帶原因給前端。UX 如果要依原因顯示不同的文字，再加一個原因代碼的欄位。
- 示範站匯出時還在等的區塊照樣輸出它的 `state`，不假裝成沒有內容。

### 哪一種論文做哪些處理

只由 `domain/processing.py` 的 `plan_for(論文)` 回答，匯入、上傳、每週更新、合併建議都問它，不自己判斷。

由上往下看，先符合的那一列算：

| 論文的種類 | 中文重點 | 分類 | 研究模型 | 向量 |
|---|---|---|---|---|
| 被排除的非研究文章 | 不做 | 不做 | 不做 | 不做 |
| 手填書目 | 不做 | 不做 | 不做 | 只有標題 |
| 其餘的論文，有目前的摘要 | 做 | 做 | 做 | 標題＋摘要 |
| 其餘的論文，沒有摘要 | 不做 | 做（只根據標題） | 不做 | 只有標題 |

- **表只看三件事**：是不是被排除的非研究文章、是不是手填的、有沒有摘要。**不看**是不是在追蹤範圍內，也不看有沒有進已發佈的快照。第一版的表用「算數的論文」「追蹤範圍外有摘要」分列，漏了兩種實際會出現的論文（Codex 審查指出）：追蹤範圍外而沒有摘要的；追蹤範圍內、成員先上傳、還沒被每週更新收進快照的。現在它們都落在後兩列。
- **做不做處理，和算不算進統計是兩件事。** 追蹤範圍外的論文也擷取研究模型，是照 UX 文件（論文頁對這種論文也顯示研究模型區塊）。但全實驗室共用的數字只算「算數的論文」（`counted_paper`）：構面出現次數、合併建議、關係的篇數都是（ADR-0012）。
- 被排除的非研究文章不進任何檢索；其餘論文能被哪個範圍搜到，照可見範圍與檢索範圍的規則（ADR-0002、ADR-0005）。
- 使用者觸發的（上傳、推薦清單）走互動呼叫，其餘走批次（ADR-0004）。

## 理由

1. **狀態放在表頭，重跑才有明確的意思**：「這一次擷取取代上一次擷取」，不用逐條比對哪條假設還在。
2. **細項仍然是一列一列的資料表**，所以關係的篇數、分類的計數可以直接用 SQL 算，假設可以用外來鍵指到構面。
3. **候選狀態讓「先量、再換」有地方放。** 沒有它，換模型的評估要嘛另開一套表，要嘛直接蓋掉正在用的資料。
4. **只有一筆目前的摘要，一篇論文在所有地方才會一致**；不然可能出現「搜尋搜得到的內容，論文頁上看不到」。
5. **八種狀態寫死成一份清單，前端才能替每一種寫對應的畫面**，而不是從「內容是空的」去猜原因。
6. **`plan_for` 是預算的第一道門。** 非研究文章與手填書目根本不會被送去花錢。

## 取捨

- **比「每列各帶狀態」多一層表**，查詢要多接一次。有效值都透過 view 讀，接的動作只寫一次。
- **重跑會把細項整批重寫**，即使只有一條假設不同。舊的留著查，佔一點空間；量很小（一篇幾列）。
- **`candidate` 會累積**（每次評估一批）。保留多久沒有定；目前不刪，之後空間有壓力再定規則。
- **分類表或研究情境清單改版，會讓相關的 AI 工作在下一次每週更新整批重跑。** 設定檔版本算在輸入指紋裡（為了讓晚到的舊結果不會用舊的分類表蓋掉新的），所以改版等於每一篇的輸入都變了：改分類表會重跑全部論文的分類，改研究情境清單會重跑全部有摘要的論文的擷取。人工修正不受影響（有人工值就用人工值）。
  - **走不走 Batch**：走。重跑是由每週更新排進去的，每週更新的 AI 工作一律走 Batch（ADR-0004 第 8 項）。改版當下不會立刻重跑。
  - **單次每週更新的重跑有沒有上限：現在沒有專門的上限，待決。** 現有的保護只有每月預算：預算用完時，重跑的工作延到下個月（ADR-0009）。畫面照上面的判定順序：已經有有效產出（人工值或 `active`）的區塊照常顯示原本的內容（`ready` 或 `empty`，第 3 步在預算那一步前面）；沒有有效產出的才繼續往下看第 4、5 步，不屬於第 4 步（被拒收或批次卡住）的就是 `deferred_budget`（畫面上的「額度用完」）。要不要另外設「一次最多重跑幾篇，超過就分幾週跑完，或停下來等管理者確認」還沒定。
  - **改版前能不能先知道會重跑幾篇：現在沒有，待決。** 做得到（對每一篇問一次「要不要跑」但不真的排進去，只回報篇數與估計費用），但要不要做成一個指令還沒定。
  - 後兩點要在第一次匯入後、用實測的呼叫量與費用來定，而且要在第一次改分類表之前定好（架構文件 Deferred）。在那之前，改分類表或情境清單前先問 Kevin。
- **追蹤範圍外的論文也跑完整的 AI 處理，要花預算。** 成員一次匯入 100 篇追蹤範圍外的論文，就是 100 篇的摘要、分類、擷取費用（照 PRD §6 的單價估，一篇不到 0.01 美元）；仍然受每月預算上限保護。
- **PRD FR-49 寫推薦清單匯入的論文「摘要與分類用系統既有的資料」**，沒有提研究模型；這裡照 UX 文件多做了擷取。**請 Kevin 確認**；如果不要，在 `plan_for` 加一列「追蹤範圍外：不做研究模型」即可。

## 名詞

- **表頭表**：一次產出只記一列的那張表，記「這一次是誰、用什麼、看了什麼產生的」；細項另外掛在底下。像一張訂單（表頭）和它的品項（細項）。
- **候選（candidate）**：已經跑出來、但還沒被採用的 AI 產出；評估過關後才會變成有效的。
- **有效（active）**：同一篇論文、同一種工作目前被採用的那一筆 AI 產出。
- **部分唯一索引**：只對符合某個條件的列檢查「不能重複」的索引；這裡用來保證「標成有效的最多一筆」。
- **BCP 47**：語言代號的國際寫法，例如 `zh-Hant` 是繁體中文、`en` 是英文、`zxx` 是「沒有語言內容」。
- **信封**：包在資料外面的固定外層；這裡指每個 AI 區塊都有的 `state`、`value`、`provenance` 三個欄位。
