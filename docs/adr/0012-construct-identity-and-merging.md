# ADR-0012：構念的身分、合併與關係的識別方式

- 狀態：提議（等 Kevin 在 PR 確認）
- 日期：2026-11-12
- 對應：PRD FR-4、FR-17、FR-18、FR-19、FR-20、FR-21、§8.5 的 K8；addendum ARCH-3、ARCH-4、ARCH-8、R4；UX 文件「關係已經被合併掉」狀態；架構文件 AD-10、AD-16、AD-27、AD-30

## 背景

研究模型擷取會從每篇論文抓出構念與假設。同一個概念在不同論文裡寫法不同（"perceived usefulness"、"Perceived Usefulness (PU)"、"usefulness perception"），不合併的話，一條其實很多人研究過的關係會被拆成好幾條，每條都顯示「本資料庫中少見」。

要決定的事：

1. 構念用什麼識別；合併之後、合併被推翻之後，資料怎麼變。
2. 「關係」是什麼；它的網址在合併之後怎麼辦（UX 文件要求舊網址顯示「這條關係已經併入…」）。
3. 合併建議怎麼產生（ARCH-8：除了名稱也比對定義），而且 LLM 那一段要能拿掉（K8 預期會觸發）。
4. 研究篇數、支持篇數的規則很細（FR-19、FR-20），要寫在哪裡。

## 考慮過的選項

**合併怎麼記**

- **A. 直接改資料：把被合併構念底下的資料改掛到另一個構念。** 最簡單，但推翻時不知道原本誰是誰。
- **B. 構念本身不動，只記「合併決定」的事件；目前誰併入誰，由事件算出來。**

**關係的識別**

- **甲. 關係有自己的 ID。** 合併兩個構念時，兩條關係要併成一條，ID 要選一個、另一個作廢。
- **乙. 關係沒有自己的 ID，就是「構念 A → 構念 B」這一對。**

## 決定

**B＋乙。**

### 構念

1. 擷取時，每個構念名稱先經過 `domain/constructs.py` 的 `normalize_name`：統一大小寫、去掉標點與連字號、去掉括號裡的縮寫、把多個空白合成一個。**不做字根還原**（例如把 "trusting" 變成 "trust"），因為會把不同的概念誤併，而且拆不回來。
2. `construct` 表以正規化後的名稱為唯一鍵。正規化後相同的，從一開始就是同一個構念，不需要人審。
3. 每個構念有一個 `canonical_id`，指向它目前所屬的那一組的代表。這個欄位**不可為空**：新構念建立時就指向自己（由 `repo/constructs.py` 寫入）。如果允許是空的，新擷取出來、還沒遇過任何合併的構念就不會出現在排行表上。
4. **代表固定是那一組裡 ID 最小的構念。** ID 用 `uuidv7()` 產生，開頭是時間，所以 ID 最小就是最早建立的；用 ID 比不用建立時間比，是因為同一批寫入的構念建立時間可能相同。代表不會因為合併的先後順序而變。
5. 論文裡提到構念的紀錄（`construct_mention`）與假設（`hypothesis`）永遠指向**原本的**構念，不因合併而改。它們掛在那一次擷取的表頭（`research_model`，ADR-0015）底下；論文層級的擷取結果（研究情境、研究限制、是不是文獻回顧或後設分析）放在表頭上。
6. 研究情境的國家、產業、研究設計、分析單位只能是設定檔清單裡的代號，模型寫了清單以外的值就存成空的。不這樣做的話，「未出現的情境」沒有辦法算（"US"、"USA"、"United States" 會被當成三個情境）。
7. 構念的定義是選填的，只能取自摘要的原句，和假設原句一樣要通過「逐字出現在輸入裡」的驗證。**PRD 的 FR-3（擷取格式）沒有列這個欄位**，它是為了 ARCH-8「也比對定義」加的；請 Kevin 在 PRD 下次修訂時補上。

### 合併

1. 合併的決定是人工判斷事件（FR-4）：哪兩個構念、接受或拒絕、證據層級（名稱／定義／題項）、誰決定的、身分是成員還是管理者。事件只能新增。一對構念固定把 ID 小的放前面，「A 和 B」與「B 和 A」才會是同一對。
2. **目前的合併結果由事件重算**（`repo.constructs.rebuild_canonical()`）：每一對構念取最新的決定（管理者的決定蓋過成員的）；所有「接受」的配對連起來成為一組一組；每組的代表是 ID 最小的那個；然後一次更新全部構念的 `canonical_id`。
3. **連起來之後和某個「拒絕」衝突時，這一組不合併。** 例：A＝B 接受、B＝C 接受，但 A＝C 的最新決定是拒絕。照「接受的連起來」A、B、C 會變成一組，等於推翻了那個拒絕。規則：一組裡只要有任何一對的最新決定是拒絕，這一組的構念全部維持各自獨立，並列進 CLI 的待處理清單，由 Kevin 決定推翻哪一筆。寧可少併，不默默併錯。
4. 每次有新的合併事件，就整個重算一次。構念只有幾千個，重算是毫秒的事；整個重算代表「推翻」不需要另外寫邏輯。
5. **重算只有一個呼叫處**：`services/merges.py` 在寫入合併事件的同一個交易裡呼叫，而且開頭先拿一把資料庫的鎖（advisory lock）。兩個人同時按確認時，後面那個等前面那個做完再算，不會各算各的、互相蓋掉。
6. 成員在證據簡報確認的合併立即生效，標示「成員確認、待管理者複核」；Kevin 用 CLI 推翻時，就是再新增一筆事件。**已經有決定的配對，只有管理者能再做決定**（成員不能把另一位成員的確認改回去；架構文件 AD-27）。
7. 證據層級由系統依當時畫面顯示的內容自動記（UX 文件的決定）：畫面只並排了名稱就是「名稱」，有並排定義就是「定義」。

### 關係

1. 關係＝（代表構念 A, 代表構念 B）這一對，有方向。沒有自己的 ID。
2. 網址用兩個構念的 ID：`/relations/{構念 A 的 ID}/{構念 B 的 ID}`。
3. 用舊的 ID 打開時，後端發現它不是代表，回應裡帶 `merged_into`（現在的那一對）；前端顯示「這條關係已經併入〔另一條關係〕」與連結。不自動跳轉，因為使用者需要知道發生了合併。
4. **關係排行表的資料與畫法分開（ARCH-3）**：API 回傳的是關係的清單（兩端的構念、各種計數與標記）。之後做 2D 鄰居圖、3D 全景圖（Should／Could）時讀同一個 API，不另外做一套資料。

### 數字的規則只寫在一個 view

view `relation_stats` 是下面這些規則唯一的實作處；排行表、混合支持篩選、證據簡報、示範站匯出都讀它。它的資料只來自算數的論文（`counted_paper`）與目前有效的研究模型（`effective_research_model`）：成員私下匯入的追蹤範圍外論文雖然也擷取研究模型（ADR-0015），但不進這個 view，否則一個人匯入的論文會改變全實驗室看到的篇數。

- **研究篇數**：只計追蹤範圍內（`counted_paper`，ADR-0011）、證據類型是實證檢定／分析推導／模擬／質性、而且論文本身不是文獻回顧或後設分析的論文。以論文為單位，同一篇提到同一條關係多次只算一篇。
- **支持篇數**：只從證據類型是實證檢定、而且有報告結果的假設計算。
- **混合支持**：實證檢定的論文裡，同時有「支持」與「不支持」。總篇數少於 3 標「資料不足」。
- **本資料庫中少見**：研究篇數 ≤2（門檻在設定檔）。
- **合併未完成**：關係的任一端還有沒審的合併建議，或落在「有衝突所以整組沒合併」的那一組裡（合併的第 3 項）。
- **覆蓋率警告**：來源論文所屬（期刊, 年份）的摘要覆蓋率，取最小值，低於門檻就警告。覆蓋率在這裡用 SQL 又算了一次，是比例公式唯一的第二份實作（ADR-0011）。
- **證據簡報另外需要的欄位**：最新年份、關係的主題（來源論文的有效主題裡最多的那幾個）、未出現的情境（設定檔清單裡有、來源論文裡沒有的值）、情境未知的篇數。
- 研究篇數是 0 的關係（只有概念主張或文獻回顧提到）照樣在 view 裡，帶「不計入研究篇數」的標記；排行表預設不列（UX 文件的決定）。

不屬於單一關係的數字「已審合併的構念占比」是 `repo/relations.py` 的一個函式，排行表頁首與證據簡報都用它。

證據簡報全部由程式從這些資料算出，不呼叫 LLM、伺服器不存檔；回應裡帶產生時間。需要留存時用「匯出」產生固定的檔案，內容與可見範圍的規則在 ADR-0011「可重現靠匯出檔」。

### 合併建議怎麼產生

分三層，前兩層不用 LLM，可以獨立運作：

| 層 | 做法 | 用 LLM 嗎 | 優先 |
|---|---|---|---|
| 1 名稱相同 | 正規化後相同就是同一個構念 | 否 | Must |
| 2 相似度 | 把「名稱＋定義」（有定義才加）轉成向量，找出相近的配對；名稱另外用字元相似度（`pg_trgm`）補抓拼法接近的。超過門檻的列為建議。向量查詢用 `repo/retrieval.py` 裡專門給構念用的那個函式（ADR-0005），不另寫一套 | 否（用既有的 embedding） | Must |
| 3 LLM 判斷 | 對第 2 層的候選，請 LLM 判斷是不是同一個概念並寫一句理由，用來排序與輔助人審 | 是 | K8 觸發時拿掉 |

- 範圍照 FR-18：出現 2 次以上的構念之間互相比；只出現 1 次的，只和出現次數前 200 名的比。**出現次數只算 `counted_paper` 的論文**，候選也只從這些論文的構念裡挑；私人論文裡才有的構念不產生建議。
- 被拒絕過的配對不再建議：產生建議時先排除已經有決定事件的配對。
- 建議存在 `merge_suggestion` 表，記錄是哪一層產生的、相似度多少。前兩層不是模型的產出，所以這張表沒有模型來歷的欄位。
- 第 3 層 LLM 的判斷與理由存在另一張表 `merge_judgment`，掛在建議底下，和其他 AI 產出同一套欄位與狀態（ADR-0015）；K8 觸發時這張表就是空的，前兩層不受影響。
- CLI 把建議匯出成試算表給 Kevin 批次審，再把決定匯回成事件（K2）。
- 「參考 Larsen & Bong（2016）」的部分：他們的做法核心是比對量表題目的文字。v1 只有摘要，拿不到題目，所以先做到名稱與定義這兩層，並把每個決定的證據層級記下來；之後有全文、拿得到題目時，可以加第三種證據，不用改資料表。

## 理由

1. **合併是判斷，不是事實**，判斷會被推翻。把判斷記成事件、結果用算的，推翻就只是多一筆事件。
2. **原始資料不動。** 哪篇論文用了哪個寫法永遠查得到；合併規則改了可以整個重算。
3. **關係不給 ID，就沒有「合併後哪個 ID 留下來」的問題。** 網址由構念 ID 組成，構念 ID 永遠不會消失。
4. **篇數規則很細，只寫一次。** FR-19 與 FR-20 的每一條「計入／不計入」如果分散在排行表、簡報、示範站各自的查詢裡，一定會有一處不一樣。
5. **LLM 層做成最後一層、只加分不必要**，K8 觸發時整層拿掉，前兩層照樣產生建議。

## 取捨

- **每次合併都整個重算**，構念數量到幾萬個時會變慢。目前估計是幾千個；到時改成只重算受影響的那幾組。
- **有衝突的那一組整組不合併**，在 Kevin 處理之前，那幾個構念的關係會暫時拆開顯示、篇數偏低。接受：這種情況應該很少。這幾條關係會帶「合併未完成」的標記：第一版只看有沒有沒審的建議，三對都審過卻互相衝突時不會有標記，篇數偏低又沒有警告（Codex 審查指出），所以標記的條件加了「落在有衝突的那一組」。
- **正規化後相同就自動視為同一個**，沒有人審。同名但意思不同的構念（例如不同理論裡的 "trust"）會被併在一起。接受：這種情況靠名稱本來就分不開；之後要拆，是另一種事件（拆分），列在架構文件的 Deferred。
- **`relation_stats` 是一個複雜的 view**，資料多了會慢。和 ADR-0011 一樣，慢了就改成實體化 view。
- **構念數量到數千個時圖怎麼畫得動（ARCH-4）**不在這裡決定；圖是 Should，排行表是分頁的表格，不受影響。

## 名詞

- **構念的代表（canonical）**：幾個被認定是同一個概念的構念裡，被選出來代表整組的那一個；顯示與計數都用它。
- **正規化**：把寫法不同但其實一樣的東西變成同一種寫法，例如統一大小寫、去掉標點。
- **字根還原**：把單字的變化形還原成原形（trusting → trust）；這裡刻意不做。
- **字元相似度（pg_trgm）**：PostgreSQL 的功能，把字串拆成三個字元一組來比對，抓得到拼法接近的字。
- **事件**：只新增、不修改的一筆紀錄，內容是「某人在某時做了某個決定」。目前的狀態由全部事件算出來。
- **advisory lock**：PostgreSQL 提供的一種「自己約定用途」的鎖；這裡約定「正在重算合併結果的人拿著它」，其他人要算就先排隊。
