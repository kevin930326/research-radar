# ADR-0008：登入用 Google 帳號＋允許名單，登入狀態存在資料庫

- 狀態：提議（等 Kevin 在 PR 確認）
- 日期：2026-11-12
- 對應：PRD FR-34、FR-36、NFR-15、NFR-16；addendum ARCH-7；架構文件 AD-23

## 背景

FR-34：成員用自己既有的帳號登入；管理者只維護允許名單；系統盡量不保存密碼。實驗室成員都有 Google 帳號（學校信箱也是 Google）。使用者只有 4 人加管理者。

## 考慮過的選項

**用什麼登入**

- **A. Google 登入（OIDC）＋自己的允許名單。**
- **B. 寄登入連結到信箱（magic link）。** 不用密碼，但要接一個寄信服務，信還可能進垃圾信匣。
- **C. 自己做帳號密碼。** 要保存密碼、做重設流程，FR-34 明確不想要。
- **D. Cloudflare Access。** 在 Cloudflare 那一層擋，程式幾乎不用寫。但允許名單會放在 Cloudflare 的後台，不符合 FR-36「用 CLI／設定檔維護」，名單變更也進不了本系統的稽核紀錄（NFR-16）；本機開發與自動化測試也要另外想辦法。

**登入狀態放哪裡**

- **甲. 伺服器端 session：** 瀏覽器只拿到一個隨機編號，資料在資料庫。
- **乙. JWT：** 把登入資料簽名後整包放在瀏覽器。不用查資料庫，但發出去就收不回來，要撤銷得另外做黑名單。

**用哪個函式庫**

- **1. Authlib 的 Starlette 整合。** 最常見，整個流程（轉址、換 token、驗 token）都由它做。
- **2. 自己寫授權碼流程，ID token 用 `joserfc` 驗簽。** 只對 Google 一家，流程固定，約一百行。

2026-11-12 查到的事實（兩個函式庫是同一位維護者）：

| | Authlib | joserfc |
|---|---|---|
| 目前版本 | 1.9.5 | 1.8.0 |
| 相依套件 | `cryptography`、`joserfc`（Authlib 自己就依賴 joserfc）；HTTP 的部分從 1.8.0 起改用 `httpx2` | `cryptography` |
| 今年的安全公告 | 公告頁第一頁 10 則（2026-10-14 六則、2026-11-01～11-05 四則）。多數是「當授權伺服器」才用得到的功能；和「當登入的用戶端」有關的有兩則：ID token 的 `nonce` 檢查可以被弄失效、簽章驗證繞過（Critical） | 至少 10 則。包括：把 RSA 公鑰當成 HMAC 密鑰可以偽造 HS256 的 token（2026-11-03，1.7.7 修正）、JSON 格式的簽章驗證繞過（2026-09，1.7.4 修正；這裡用的精簡格式不受影響）、陣列型別的 `iss`／`sub` 可以繞過檢查（2026-08） |

這份 ADR 的前一版寫「Authlib 會拉進已經停止更新的 `httpx`」，查證後不成立（1.8.0 起已改用 `httpx2`），已經改掉。

## 決定

**A＋甲＋2。**

1. **流程**（授權碼流程＋PKCE，全部在後端處理，瀏覽器的 JavaScript 碰不到任何 token）：
   1. `GET /api/v1/auth/login`：產生 `state`、`nonce`、PKCE 的驗證碼，存進 `login_attempt` 表（10 分鐘過期）；瀏覽器只拿到這筆紀錄的隨機編號（cookie），然後被轉到 Google。
   2. Google 轉回 `/api/v1/auth/callback`：核對 `state`；用授權碼向 Google 換 ID token。
   3. 驗 ID token：簽章（Google 公開的金鑰）、簽發者、對象（本系統的 client ID）、有效期限、`nonce`、`email_verified` 必須為真。**驗簽時允許的演算法只有 `RS256`，金鑰只以 RSA 金鑰的型別從 Google 的金鑰清單（JWKS）載入**；`iss`、`aud`、`sub` 必須是字串，不接受陣列。這一條直接擋掉上表 joserfc 那幾類問題，不管函式庫有沒有修。
   4. 用小寫的 email 查允許名單。不在名單：不建立任何東西，顯示 UX 文件「10. 登入」的說明頁。
   5. 在名單：成員資料在加入允許名單時就已經建立（見第 4 項）；第一次登入時補上 Google 的使用者識別碼（`sub`）與第一次登入的時間，之後以 `sub` 認人。同一個 email 換了一個 `sub`，拒絕登入並寫稽核事件；畫面顯示一般的「登入失敗」，不另外說明原因。
   6. 建立 session，轉回原本要開的頁面（只接受站內路徑）。
2. **session**
   - cookie 名稱 `__Host-radar_session`，屬性 `HttpOnly`、`Secure`、`SameSite=Lax`、`Path=/`。
   - cookie 的值是 256 位元的隨機數；資料庫只存它的 SHA-256 雜湊，資料庫外洩也無法拿來登入。
   - 14 天沒使用就過期，最長 30 天（放設定檔）。
   - 從允許名單移除某人時，同一個交易裡刪掉他所有的 session。
3. **防跨站請求（CSRF）**：會改資料的請求一律不是 GET；中介層檢查 `Origin` 標頭必須是本站，否則拒絕。唯一的例外是登入的起點 `GET /api/v1/auth/login`：它會寫一筆 `login_attempt`，但除此之外不改任何資料。
4. **允許名單與管理者**：`radar members allow <email> --name <名稱>`（名稱必填）、`radar members revoke <email>`、`radar members set-admin <email>`。每次變更寫稽核事件。`allow` 當下就建立成員資料（還沒有 `sub`），這樣還沒登入過的人也有一筆資料可以被引用（例如 Kevin 用 CLI 以管理者身分匯回合併決定）。管理者在網站上看到的和一般成員一樣（ADR-0002）。
5. **不存的東西**：密碼、Google 的 access token 與 refresh token（換到 ID token、驗完就丟）。日誌不記 email，只記成員 ID。
6. **向 Google 要的權限只有 `openid email`**，不拿姓名與大頭貼。成員在畫面上的顯示名稱，由管理者加入允許名單時用 CLI 填，所以是必填。
7. **成員的第一次登入時間記在伺服器**，系統首頁「第二次以後登入」的版面與問答「第一次進來」的說明都讀它；記在瀏覽器的話換裝置就不一致。
8. **沒登入的請求回 401**；登入了但沒有權限，回 404（ADR-0002）。
9. **測試**：`IdentityProvider` 是一個 port，測試用假的實作發 ID token（用測試自己產生的金鑰簽）。負面樣本：`state` 不符、`nonce` 不符、過期、對象不對、`email_verified` 為假、不在名單、`sub` 變了、用 `HS256` 簽的 token、`iss` 是陣列。

## 理由

1. **不保存密碼**，也就沒有密碼外洩、重設密碼這些事。
2. **允許名單在自己的資料庫**，才能用 CLI 維護、寫稽核、在測試裡切換身分（FR-7 的換人測試）。
3. **4 個人的規模，查一次資料庫的成本可以忽略**；換來的是移除名單後立刻失效。
4. **選 2 的理由是相依的東西比較少，不是 Authlib 不好。** Authlib 自己就依賴 joserfc，所以選 Authlib 等於兩個函式庫的問題都要跟；只用 joserfc 是它的子集。這裡只需要「驗一個 Google 簽的 token」這一小塊，用不到 Authlib 其餘的 OAuth 功能（今年的公告多數出在那些功能）。自己寫的部分只有「轉址、換 token、驗 token」三步，驗簽交給 `joserfc`，沒有自己實作任何密碼學。

## 取捨

- **「不要自己寫登入」是常見的建議，這裡刻意沒照做。** 風險在於漏掉某一項檢查。補救：第 1 項的每一個檢查都有對應的負面測試；上線前的資安檢查（`docs/skills-plan.md` 的 `insecure-defaults`、`differential-review`）特別看這一段。如果審查認為風險太高，退路是改用 Authlib（鎖在 1.9.5 以上），資料表與 cookie 的設計不用改。**這一題兩邊都說得通，Kevin 想改用 Authlib 的話在 PR 說一聲即可。**
- **joserfc 今年的公告不少。** 版本鎖在 1.8.0，不得低於 1.7.7；CI 加相依套件的弱點掃描（pip-audit），有新公告時會擋下合併。
- **綁定 Google。** 沒有 Google 帳號的人進不來。實驗室成員都有，接受。之後要加第二家（例如學校的單一登入），`IdentityProvider` 再多一個實作。
- **Google 的服務中斷時沒辦法登入**；已經登入的人不受影響。
- **K9 觸發時**（Kevin 單人上線、先不做登入）的做法不在這份 ADR 裡，列在架構文件的 Deferred。

## 名詞

- **OIDC（OpenID Connect）**：「用 Google 登入」背後的標準；網站把使用者帶去 Google，Google 確認身分後告訴網站「這個人是誰」。
- **允許名單**：可以登入的 email 清單；不在上面的人就算有 Google 帳號也進不來。
- **session**：登入狀態。伺服器記著「這個編號是誰」，瀏覽器每次帶著編號來。
- **cookie**：網站存在瀏覽器裡的一小段資料，之後每次連線都會自動帶上。
- **ID token**：Google 簽過名的一小段資料，內容是「這個人的身分」；網站驗證簽名後才相信。
- **PKCE**：授權碼流程的加強保護；就算有人攔到授權碼，沒有一開始產生的那組驗證碼也換不到 token。
- **CSRF（跨站請求偽造）**：別的網站偷偷用你已登入的身分對本站送出請求；檢查請求來源可以擋掉。
- **JWT**：一種簽過名的資料格式，可以把登入資料整包放在瀏覽器；這裡只在驗證 Google 的 ID token 時用到。
