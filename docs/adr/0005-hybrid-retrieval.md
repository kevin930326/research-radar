# ADR-0005：搜尋、找相似論文、問答共用一套檢索：向量＋關鍵字，在一條 SQL 裡融合

- 狀態：提議（等 Kevin 在 PR 確認）
- 日期：2026-11-12
- 更新：2026-11-28（Story 4.1 實作時補的決定：全文檢索資料怎麼存、查詢向量的結果怎麼記、背景向量化停在 80%；見「2026-11 實作更新」一節）
- 對應：PRD FR-5、FR-26、FR-27、FR-28、FR-43、NFR-19；addendum ARCH-6、R5；`hybrid-search-implementation` 與 `supabase-postgres-best-practices` 兩個 skill；架構文件 AD-11、AD-12

## 背景

三個功能都要「從論文裡找出最相關的幾篇」：一句話搜尋（FR-26）、找相似論文（FR-27）、問答（FR-28）。PRD 明寫問答的檢索和搜尋共用同一套（ARCH-6）。示範站的展示問答（FR-43）也要用，而且範圍只限示範站可用論文。

要顧到的事：

- 中文查詢要找得到英文論文（FR-26 的驗收）。
- 查專有名詞（例如 "UTAUT"、作者姓氏）時，要找得到字面上有這個詞的論文。
- 每一條檢索路徑都要套用可見範圍（ADR-0002）。
- 正式主機只有 1 GB，不能跑模型。

## 考慮過的選項

**A. 只用向量搜尋。** 中文找英文沒問題，但專有名詞與縮寫容易漏。

**B. 向量＋關鍵字，用 RRF 融合，全部在 PostgreSQL。** 兩種方法各找一批，再依名次合併。

**C. B 再加重排模型（reranker）。** 品質最好，但要多跑一個模型：1 GB 主機跑不動，用雲端的又多一個供應商與一筆費用。

**D. 另外架搜尋引擎（Elasticsearch、Meilisearch 等）。** addendum 已排除獨立的搜尋／向量資料庫。

## 決定

選 **B**。

1. **只有一個入口**：`services/retrieval.py` 的 `retrieve(viewer, query 或 paper_id, scope, filters, k, offset)`。搜尋、找相似論文、問答、展示問答都呼叫它；其他地方不得自己寫向量或全文檢索的 SQL。唯一的例外是合併建議要用的「構面相似度」（ADR-0012）：它比的是構面不是論文，簽名對不上，所以是同一個 repo 模組裡的另一個函式，同樣強制帶 `model_id`，只給合併建議用。
2. **`scope` 是固定的四種**：

   | scope | 範圍 |
   |---|---|
   | `personal` | 這位成員的個人文獻庫 |
   | `lab` | 這位成員看得到的全部論文（追蹤範圍內＋引用擴展＋成員分享的追蹤範圍外論文＋他自己私人的） |
   | `tracked` | 計入統計的論文，等於 view `counted_paper`（追蹤範圍內、不含被排除的非研究文章、快照已發佈）。這樣從篇數連結進到找論文再搜尋，母體和數字是同一批 |
   | `demo` | 示範站有完整內容的論文，等於 view `demo_full_paper`；只有 `PublicViewer` 能用 |

   不管哪一種，都先套用 viewer 的可見範圍條件，再套 scope。
3. **向量腿**
   - 每篇論文一個向量，內容是「標題＋目前用的那一筆摘要」；沒有摘要的只用標題。哪些論文要建向量由一張固定的表決定（架構文件 AD-30），例如被排除的非研究文章不建。
   - **有相似度下限**（設定值，用 FR-26 的評估題組調）。向量搜尋永遠找得到「最近的」幾篇，不管多不相關；沒有下限的話，「找不到相關的論文」「沒有夠相似的論文」這兩個畫面永遠不會出現。
   - 模型：Cloudflare Workers AI 的 Qwen3-Embedding-0.6B，1,024 維。
   - 存成 pgvector 的 `halfvec`（每個數字用一半的空間，準確度幾乎不變）。
   - 每個模型一個 HNSW 部分索引（只索引那個模型的向量）。**查詢一定要帶 `model_id`**，否則用不到索引，也可能把兩個模型的向量混在一起比。
   - `EmbeddingProvider` 有兩個方法：`embed_documents` 與 `embed_query`。這個模型對「查詢」要加一段指示文字，對「文件」不加；分成兩個方法，就不會有人用錯。
4. **關鍵字腿**
   - PostgreSQL 內建的全文檢索，英文設定，內容是標題＋目前用的那一筆摘要，一篇論文一列 `tsvector`，建 GIN 索引。（一篇論文可能有兩個來源的摘要；全系統只用標成「目前」的那一筆，見 ADR-0015。）
   - 查詢用 `websearch_to_tsquery`（看得懂引號與減號，使用者亂打也不會出錯）。
   - 中文查詢在這條腿找不到東西，這是預期的；這時結果全部來自向量腿。
5. **融合**：兩條腿各取前 100 名，用 RRF（k＝60）算分，在同一條 SQL 裡完成。兩個數字是設定值。
6. **過濾放在哪裡**
   - `personal` 範圍通常只有幾十到幾百篇：先過濾、再精確比對距離，不用 HNSW 索引。
   - 其他範圍：用 HNSW，並打開 pgvector 的 iterative scan（過濾後數量不夠時，自動往下多找）。
7. **找相似論文**：只用向量腿，拿這篇論文自己的向量去找，結果排除自己。
8. **回傳的是排好序的論文 ID、名次與 `total`**（算得上結果的篇數，最多到上限），不含內容。呼叫的人再用 viewer 去拿它被允許看的內容。問答取前 12 篇、搜尋每次 20 篇，數字放設定檔。分頁是在融合後的名次裡用位移（從第幾名開始），不用清單常用的 cursor：依相關程度排的結果本來就是「前 k 名」。
9. **中文結構化摘要 v1 不進檢索。** FR-28 允許它用來幫忙排序，但目前兩條腿都只用原文。之後要加（例如 S04 的中文查詢管線），是加第三條腿，不改既有兩條。

## 理由

1. **RRF 不用調參數。** 向量的相似度和全文檢索的分數單位不同，不能直接相加；RRF 只看名次。
2. **全部在一個資料庫。** 少一個服務；可見範圍的條件和檢索寫在同一條 SQL，不會有「搜尋引擎裡的權限和資料庫不同步」。
3. **多語言模型解決中文找英文。** Qwen3-Embedding 支援中英文，中文問句和英文摘要會落在相近的位置，不必先翻譯。
4. **規模小。** 一萬到兩萬個向量，檢索本身在幾十毫秒內；NFR-19 的 2 秒主要花在把查詢送去 Workers AI 轉成向量。

## 取捨

- **沒有重排模型**，前幾名的順序不如有重排的系統。先量：FR-26（中文查詢前 10 名命中 ≥70%）與 FR-27 的評估數字出來後，不夠再考慮。
- **中文查詢少了關鍵字腿**，查中文專有名詞（例如「科技接受模型」）只能靠向量。FR-26 未達標時，PRD 已經定了對策：把 S04（用 LLM 把查詢改寫成英文）提前。
- **每次搜尋都要呼叫 Workers AI 一次。** Workers AI 連不上時，搜尋直接回錯誤（固定的錯誤代碼），畫面用既有的錯誤訊息條。不退回「只用關鍵字腿」：中文查詢在關鍵字腿找不到東西，降級後會變成看起來正常的零結果，比明講壞了更誤導；UX 文件也沒有這個降級狀態。
- **每篇只有一個向量**，長摘要後半段的內容比重較低。全文切塊是全文管線（Should）的事，資料表已經留了位置（`item_type` 欄位）。

## 2026-11 實作更新

Story 4.1 實作時補上的決定。上面的九點不變。

### 1. 全文檢索的資料存在哪裡、怎麼跟著變

**選項**
- **a. 產生欄位（generated column）放在 `paper` 上。** 最省事，但產生欄位只能用同一列的欄位；摘要在另一張表 `paper_abstract`（一篇可能有兩個來源，用 `is_current` 標目前的那一筆，ADR-0015），算不出來。
- **b. 另一張表，由寫入路徑維護。** 每個改標題、寫摘要、換目前摘要的地方都要記得重算。寫這兩個欄位的地方很多（匯入、每週更新、補摘要、`radar reparse`、上傳），漏一個就默默不一致，而且沒有測試抓得到「以後新增的寫入路徑忘了重算」。
- **c. 另一張表，由資料庫的觸發器維護。** 不管從哪裡寫，資料庫都會重算。

**決定：c。** 遷移 0023 建 `paper_search_document`（一篇一列：`paper_id`、`tsvector`、`updated_at`；GIN 索引）。內容是英文設定的「標題（權重 A）＋目前那一筆摘要（權重 B）」，沒有目前的摘要只用標題。
- `paper` 新增或改標題、`paper_abstract` 新增／改內容／改 `is_current`／刪除時，觸發器重算那一篇（換了 `paper_id` 時新舊兩篇都算）。改標題以外的欄位不重算。
- 重算的函式與兩個觸發器函式都是 `SECURITY DEFINER`、固定 `search_path`，三個都收回 PUBLIC 的 EXECUTE（審查後補）；應用程式角色對這張表只能讀，寫只能經觸發器（觸發器觸發時不檢查 EXECUTE）。
- **同一篇同時改標題與摘要**（審查後補）：重算先鎖論文那一列（`FOR NO KEY UPDATE`），鎖到之後才另起一句讀標題與摘要。改標題（`UPDATE paper` 本身就鎖這一列）和改摘要因此排隊，鎖的順序固定是「論文 → 全文檢索資料」，後到的那個交易看得到先到的已經 commit 的改動。只用一句 `INSERT … SELECT` 時，後到的會用等鎖之前讀到的舊標題（或舊摘要）蓋掉先到的結果，而且之後不會自己修好。用 `FOR NO KEY UPDATE` 而不是 `FOR UPDATE`：一樣和改標題互斥，但不擋其他表新增列時外鍵檢查的 KEY SHARE。
- **被排除的論文**：資料照留，查詢時用可見條件與 `excluded_reason IS NULL` 篩掉。這樣取消排除時不用補算，也只有一個地方決定「誰算得上結果」。
- **既有的一萬多篇**：在遷移 0023 裡用一句 `INSERT … SELECT` 回填（和觸發器用同一段算法）。真實資料庫由 Kevin 跑 `radar migrate` 時一起做完；降版會把表、觸發器、函式一起刪掉。

**理由**：一致性交給資料庫，不靠每個寫入的人記得。**取捨**：寫入時多一點成本（一篇重算一次，量很小）；改摘要的交易多拿一把論文的鎖，同一篇的改標題、改摘要會排隊（不同篇不受影響）；邏輯在 SQL 裡，Python 端看不到，所以遷移測試逐一驗了每種觸發情況、兩條連線的並行與權限（`tests/integration/test_migration_0023.py`）。

### 2. 查詢向量的結果怎麼記：`api_call.outcome`

原本 `api_call` 只有狀態碼與估計 token，「額度用完沒有送出」和「送了但連不上」分不出來（兩個都沒有狀態碼）。

**選項**
- **a. 不加欄位，用「狀態碼是空的、估計 token 是 0」代表額度用完。** 不用遷移，但連不上的那一筆也可能剛好是 0 token，靠巧合區分；之後查帳的人要知道這個約定。
- **b. 額度用完不記 `api_call`，只寫日誌。** 帳上看不到「今天有幾次搜尋被額度擋下」。
- **c. 加一個可空的文字欄 `outcome`，用 CHECK 限定可以用的值。**

**決定：c。** 遷移 0023 加 `api_call.outcome`：`succeeded`、`unreachable`（沒有回應、408、429、5xx）、`rejected`（其他 4xx 等，多半是設定錯）、`quota_exhausted`（今天的額度放不下，沒有送出；狀態碼一定是空的、估計 token 一定是 0）、`not_sent`（其他沒有送出的失敗：等額度鎖逾時，或 adapter 第一次送出前就停下；狀態碼空、估計 token 0；審查後補）。只有查詢向量（`embed_query`）記，背景向量化照舊是 NULL。每次嘗試一筆（adapter 重試幾次就幾筆），和背景向量化同一本帳；沒送出的失敗也記一筆，所以每次搜尋至少有一筆。額度用完另外寫一筆警告日誌（不含查詢內容）。

**占用記下操作種類**（審查後補）：`embedding_quota_hold` 加 `operation`（既有的列補 `embed_documents`）。搜尋的行程送出後被砍、沒回來結清時，占用過期後照 `embed_query` 轉成用量（`outcome` 是 NULL，代表「不知道結果」），不會被記成背景向量化。「`before` 成功、已送出、還沒進 `after` 就中斷」這條路徑核對過不存在：adapter 的送出包在 `try/finally`，`finally` 一定呼叫 `after(sent=True)`（行程被中斷的 `BaseException` 也一樣）；結清的交易本身失敗時占用留在資料庫、照上面過期轉成用量。integration 測試用真的 adapter 接模擬傳輸，在送出後丟中斷驗過只記一筆。

**理由**：查帳一句 SQL 就分得出兩種失敗，也對得上 API 回的兩個錯誤代碼（`search_quota_exhausted`、`search_embedding_unavailable`）。**取捨**：多一次遷移與兩個欄位。**降版會永久丟掉 `outcome` 的紀錄**（降版刪欄，重新升版回來是 NULL）：和其他加欄位的遷移一樣（例如 0015），降版只在開發時用，正式不降版。

### 3. 背景向量化停在 80%，搜尋可以用到 100%

`config/embeddings.yaml` 的 `stop_at_ratio` 從 0.9 改成 0.8（Kevin 的決定）：背景向量化用到每日免費額度的 80% 就停，剩下的 20% 留給搜尋。背景的 80% 把搜尋用掉的也算進去（同一本帳、同一句加總）。搜尋判斷額度時用 100%，同樣經額度鎖與占用（ADR-0040 第 11 點）排隊，兩個請求同時搶最後的額度時只會送出放得下的那一個（第二個請求在第一個還沒寫好占用時就來，也會等額度鎖）。

**取捨**：
- 背景補向量每天少做一點（約 10%）；換到的是白天搜尋不會因為背景工作用光額度而壞掉。
- **搜尋的 100% 是估計值的 100%**（Kevin 要知道的限制）：Workers AI 的回應沒有用量，`api_call` 記的是自己估的 token（ADR-0040 第 4 點，除數是經驗值、不保證偏高）。實際用量比估計多時，搜尋放行到估計的 100% 可能已經超過真的免費額度。和背景向量化是同一套做法；20 篇試跑校正除數之後才比較準。
- **UTC 跨日時上一天還沒結清的占用算進新的一天**：已記的用量照 UTC 日期篩，占用中的卻不分日期加總。午夜前送出、午夜後還在等回應的那幾次，會暫時把新一天的可用額度壓低一點，直到結清或過期。方向是保守的（多算、提早停），背景本來就這樣，不改。

### 4. 檢索範圍的型別與找論文清單的範圍並存

`domain/retrieval.RetrievalScope` 有四種，清單的 `PaperListScope` 維持三種（清單 API 不收 `demo`）。前三種同名同義，篩選條件共用 `repo/paper_filters.py`（從 `paper_list.py` 搬過來的那一段，行為不變）。`demo` 只給 `PublicViewer`：`retrieve` 的型別簽名擋（成員的 viewer 傳 `demo` 型別檢查不過）；執行時 `retrieve` 一進來、送查詢向量或讀起點之前就擋（審查後改：原本到組 SQL 時才擋，非 `PublicViewer` 的搜尋已經送出查詢、占了額度），`visibility.visible_demo_papers` 組條件時再擋一次。

**`lab` 的定義照 ADR-0050，和上面第 2 點的表格不同**（Kevin 2026-11-28 決定以 ADR-0050 為準；第 2 點表格的原文保留不改，以這一段為準）：第 2 點的表格把「自己的私人論文」算進 `lab`；後來的 ADR-0050 定 `lab` 就是全實驗室看得到的論文（`lab_visible`），找論文清單照它做，Story 4.1 又要求檢索和清單同一套篩選。所以實作的 `lab` 不含自己的私人論文（要找自己的私人論文用 `personal`），測試也這樣寫。要改成第 2 點的定義，清單與檢索要一起改。

**放棄**：把 `demo` 加進 `PaperListScope`。那樣清單 API 要在每個地方多擋一種值，擋漏了就是權限問題。

### 5. 找相似論文拿起點的向量：新的 `find_visible_paper_embedding`

起點要「viewer 看得到、沒有被排除」，再拿它這個模型的向量。既有讀向量的函式不套 viewer 的可見條件（給背景向量化用），所以新增一個帶 viewer 的讀法，一句 SQL 同時判斷可見與拿向量。看不到、不存在、被排除三種都回同一個錯誤（不透露論文存在）；看得到但還沒有向量就回空的結果，不呼叫 Workers AI。

### 6. `total` 與分頁在 Python 算

一句 SQL 取回融合後的全部名次（最多 2 × 每條腿名額，預設 200 篇），`total` 與這一頁都從同一份結果切。這樣 `total` 和翻得到的篇數一定一致，也不用再下一句 `count`。**取捨**：
- 每翻一頁都重跑一次檢索（含查詢向量）；結果最多 200 篇，量過反應時間不受影響（見下）。
- 同一頁之內一定不重複不漏；**兩頁之間資料變了**（新論文、改摘要、被排除、向量補上）時，名次可能移動：原本第 20 名移到第 21 名就會在第二頁再出現一次，反過來就漏掉一篇。這是第 8 點「用位移、不用 cursor」本來就接受的結果：依相關程度排的結果是「現在的前 k 名」，不是固定的名單；要固定就得把整份名單存起來，這次不做。
- **同距離的論文怎麼排**（審查後補）：`personal`（精確比對）在取前 N 名之前就用（距離, 論文 id）排，第 N 名附近同距離時入榜的一定是 id 小的。其他範圍走 HNSW 索引，`ORDER BY` 多加 id 就用不到索引，所以只照距離排；索引本來就是近似搜尋（再加上 `relaxed_order`），第 N 名附近誰入榜不保證，入榜之後才用 id 決定同距離的順序。

### 7. 量過的反應時間

10,000 篇假論文、1,024 維假向量（真的模型的 HNSW 索引），本機 Docker PostgreSQL 18.7／pgvector 0.8.7，每種情況量 200 次：搜尋的 p95 是 14–22 毫秒、找相似論文 7–8 毫秒（不含 Workers AI 往返）。做法與數字在 `spikes/epic-4a-retrieval-p95/`。正式主機要另外量。

## 名詞

- **混合檢索**：同時用「意思相近」（向量）和「字面相符」（關鍵字）兩種方法找，再把結果合起來。
- **向量（embedding）**：把一段文字轉成一串數字，意思相近的文字數字也相近，所以可以用「距離」找相似內容。
- **RRF（Reciprocal Rank Fusion，倒數排名融合）**：合併兩份排名的方法：每篇在各份名單裡的名次取倒數後相加，兩邊都排前面的分數最高。
- **HNSW**：一種向量索引，像替向量先畫好一張「鄰居地圖」，查詢時沿著地圖走，不用每一筆都比。
- **halfvec**：pgvector 的省空間向量型別，每個數字用 2 個位元組（一般是 4 個）。
- **全文檢索／tsvector**：PostgreSQL 內建的關鍵字搜尋；`tsvector` 是把文章拆成單字、去掉字尾變化後存起來的格式。
- **GIN 索引**：適合「一筆資料裡有很多個詞」的索引，全文檢索用它。
- **重排模型（reranker）**：先粗略找出一批候選，再用另一個比較準但比較慢的模型重新排序。
- **iterative scan**：pgvector 0.8 的功能；索引找到的結果被過濾條件篩掉太多時，自動繼續往下找，直到數量夠。
