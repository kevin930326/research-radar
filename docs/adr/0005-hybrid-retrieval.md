# ADR-0005：搜尋、找相似論文、問答共用一套檢索：向量＋關鍵字，在一條 SQL 裡融合

- 狀態：提議（等 Kevin 在 PR 確認）
- 日期：2026-11-12
- 對應：PRD FR-5、FR-26、FR-27、FR-28、FR-43、NFR-19；addendum ARCH-6、R5；`hybrid-search-implementation` 與 `supabase-postgres-best-practices` 兩個 skill；架構文件 AD-11、AD-12

## 背景

三個功能都要「從論文裡找出最相關的幾篇」：一句話搜尋（FR-26）、找相似論文（FR-27）、問答（FR-28）。PRD 明寫問答的檢索和搜尋共用同一套（ARCH-6）。示範站的展示問答（FR-43）也要用，而且範圍只限示範站可用論文。

要顧到的事：

- 中文查詢要找得到英文論文（FR-26 的驗收）。
- 查專有名詞（例如 "UTAUT"、作者姓氏）時，要找得到字面上有這個詞的論文。
- 每一條檢索路徑都要套用可見範圍（ADR-0002）。
- 正式主機只有 1 GB，不能跑模型。

## 考慮過的選項

**A. 只用向量搜尋。** 中文找英文沒問題，但專有名詞與縮寫容易漏。

**B. 向量＋關鍵字，用 RRF 融合，全部在 PostgreSQL。** 兩種方法各找一批，再依名次合併。

**C. B 再加重排模型（reranker）。** 品質最好，但要多跑一個模型：1 GB 主機跑不動，用雲端的又多一個供應商與一筆費用。

**D. 另外架搜尋引擎（Elasticsearch、Meilisearch 等）。** addendum 已排除獨立的搜尋／向量資料庫。

## 決定

選 **B**。

1. **只有一個入口**：`services/retrieval.py` 的 `retrieve(viewer, query 或 paper_id, scope, filters, k, offset)`。搜尋、找相似論文、問答、展示問答都呼叫它；其他地方不得自己寫向量或全文檢索的 SQL。唯一的例外是合併建議要用的「構念相似度」（ADR-0012）：它比的是構念不是論文，簽名對不上，所以是同一個 repo 模組裡的另一個函式，同樣強制帶 `model_id`，只給合併建議用。
2. **`scope` 是固定的四種**：

   | scope | 範圍 |
   |---|---|
   | `personal` | 這位成員的個人文獻庫 |
   | `lab` | 這位成員看得到的全部論文（追蹤範圍內＋引用擴展＋成員分享的追蹤範圍外論文＋他自己私人的） |
   | `tracked` | 計入統計的論文，等於 view `counted_paper`（追蹤範圍內、不含被排除的非研究文章、快照已發佈）。這樣從篇數連結進到找論文再搜尋，母體和數字是同一批 |
   | `demo` | 示範站有完整內容的論文，等於 view `demo_full_paper`；只有 `PublicViewer` 能用 |

   不管哪一種，都先套用 viewer 的可見範圍條件，再套 scope。
3. **向量腿**
   - 每篇論文一個向量，內容是「標題＋目前用的那一筆摘要」；沒有摘要的只用標題。哪些論文要建向量由一張固定的表決定（架構文件 AD-30），例如被排除的非研究文章不建。
   - **有相似度下限**（設定值，用 FR-26 的評估題組調）。向量搜尋永遠找得到「最近的」幾篇，不管多不相關；沒有下限的話，「找不到相關的論文」「沒有夠相似的論文」這兩個畫面永遠不會出現。
   - 模型：Cloudflare Workers AI 的 Qwen3-Embedding-0.6B，1,024 維。
   - 存成 pgvector 的 `halfvec`（每個數字用一半的空間，準確度幾乎不變）。
   - 每個模型一個 HNSW 部分索引（只索引那個模型的向量）。**查詢一定要帶 `model_id`**，否則用不到索引，也可能把兩個模型的向量混在一起比。
   - `EmbeddingProvider` 有兩個方法：`embed_documents` 與 `embed_query`。這個模型對「查詢」要加一段指示文字，對「文件」不加；分成兩個方法，就不會有人用錯。
4. **關鍵字腿**
   - PostgreSQL 內建的全文檢索，英文設定，內容是標題＋目前用的那一筆摘要，一篇論文一列 `tsvector`，建 GIN 索引。（一篇論文可能有兩個來源的摘要；全系統只用標成「目前」的那一筆，見 ADR-0015。）
   - 查詢用 `websearch_to_tsquery`（看得懂引號與減號，使用者亂打也不會出錯）。
   - 中文查詢在這條腿找不到東西，這是預期的；這時結果全部來自向量腿。
5. **融合**：兩條腿各取前 100 名，用 RRF（k＝60）算分，在同一條 SQL 裡完成。兩個數字是設定值。
6. **過濾放在哪裡**
   - `personal` 範圍通常只有幾十到幾百篇：先過濾、再精確比對距離，不用 HNSW 索引。
   - 其他範圍：用 HNSW，並打開 pgvector 的 iterative scan（過濾後數量不夠時，自動往下多找）。
7. **找相似論文**：只用向量腿，拿這篇論文自己的向量去找，結果排除自己。
8. **回傳的是排好序的論文 ID、名次與 `total`**（算得上結果的篇數，最多到上限），不含內容。呼叫的人再用 viewer 去拿它被允許看的內容。問答取前 12 篇、搜尋每次 20 篇，數字放設定檔。分頁是在融合後的名次裡用位移（從第幾名開始），不用清單常用的 cursor：依相關程度排的結果本來就是「前 k 名」。
9. **中文結構化摘要 v1 不進檢索。** FR-28 允許它用來幫忙排序，但目前兩條腿都只用原文。之後要加（例如 S04 的中文查詢管線），是加第三條腿，不改既有兩條。

## 理由

1. **RRF 不用調參數。** 向量的相似度和全文檢索的分數單位不同，不能直接相加；RRF 只看名次。
2. **全部在一個資料庫。** 少一個服務；可見範圍的條件和檢索寫在同一條 SQL，不會有「搜尋引擎裡的權限和資料庫不同步」。
3. **多語言模型解決中文找英文。** Qwen3-Embedding 支援中英文，中文問句和英文摘要會落在相近的位置，不必先翻譯。
4. **規模小。** 一萬到兩萬個向量，檢索本身在幾十毫秒內；NFR-19 的 2 秒主要花在把查詢送去 Workers AI 轉成向量。

## 取捨

- **沒有重排模型**，前幾名的順序不如有重排的系統。先量：FR-26（中文查詢前 10 名命中 ≥70%）與 FR-27 的評估數字出來後，不夠再考慮。
- **中文查詢少了關鍵字腿**，查中文專有名詞（例如「科技接受模型」）只能靠向量。FR-26 未達標時，PRD 已經定了對策：把 S04（用 LLM 把查詢改寫成英文）提前。
- **每次搜尋都要呼叫 Workers AI 一次。** Workers AI 連不上時，搜尋直接回錯誤（固定的錯誤代碼），畫面用既有的錯誤訊息條。不退回「只用關鍵字腿」：中文查詢在關鍵字腿找不到東西，降級後會變成看起來正常的零結果，比明講壞了更誤導；UX 文件也沒有這個降級狀態。
- **每篇只有一個向量**，長摘要後半段的內容比重較低。全文切塊是全文管線（Should）的事，資料表已經留了位置（`item_type` 欄位）。

## 名詞

- **混合檢索**：同時用「意思相近」（向量）和「字面相符」（關鍵字）兩種方法找，再把結果合起來。
- **向量（embedding）**：把一段文字轉成一串數字，意思相近的文字數字也相近，所以可以用「距離」找相似內容。
- **RRF（Reciprocal Rank Fusion，倒數排名融合）**：合併兩份排名的方法：每篇在各份名單裡的名次取倒數後相加，兩邊都排前面的分數最高。
- **HNSW**：一種向量索引，像替向量先畫好一張「鄰居地圖」，查詢時沿著地圖走，不用每一筆都比。
- **halfvec**：pgvector 的省空間向量型別，每個數字用 2 個位元組（一般是 4 個）。
- **全文檢索／tsvector**：PostgreSQL 內建的關鍵字搜尋；`tsvector` 是把文章拆成單字、去掉字尾變化後存起來的格式。
- **GIN 索引**：適合「一筆資料裡有很多個詞」的索引，全文檢索用它。
- **重排模型（reranker）**：先粗略找出一批候選，再用另一個比較準但比較慢的模型重新排序。
- **iterative scan**：pgvector 0.8 的功能；索引找到的結果被過濾條件篩掉太多時，自動繼續往下找，直到數量夠。
