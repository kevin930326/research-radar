# ADR-0013：PDF 經由 API 上傳；辨認只讀前幾頁；沒有下載聲明的檔案讀完就刪

- 狀態：提議（等 Kevin 在 PR 確認）
- 日期：2026-11-12
- 更新：2026-11-13（設計階段的決定寫回：傳到一半的檔案放哪裡、取消上傳怎麼清、「不加入」這個狀態與復原、「開啟 PDF」的路徑；同一天依審查補上：保存的 PDF 誰佔著與怎麼放掉、配額算什麼、沒完成的分段上傳怎麼清；Kevin 同一天決定：同一篇只留一份 PDF，新的要使用者確認才取代舊的；等確認取代的那一份不算配額；處理失敗與沒人確認的 PDF 保留 7 天，處理失敗的可以自己刪；配額改成收檔時粗檢查、認出論文之後才算準，多一種狀態 `over_quota`；勾了聲明的批次不能分享書目；項目多記「上一個狀態」讓畫面分得出「沒有換」與「沒有加入」；設計補上的畫面文字寫回；論文頁按「換一個 PDF」之後原本那一份算不加入；沒勾聲明的失敗列一樣顯示「刪除」；保存的位置改成一筆紀錄一個檔，「保存的 PDF」整節與搬的順序重寫，這部分沒有經過之前的審查）
- 對應：PRD FR-7、FR-12、FR-13、FR-49、NFR-1、NFR-19；addendum ARCH-9、ARCH-10；UX 文件「8. 論文頁」「14. 上傳與匯入」與「給架構階段的事項」；架構文件 AD-14、AD-24

## 背景

成員上傳 PDF 有兩種情況，畫面上用一個勾選框分開：

- **勾了下載聲明**（「這是我自己用學校權限下載的」）：檔案要保存，只有上傳者看得到。
- **沒勾**（別人分享的資料夾，當推薦清單）：只用來辨認是哪一篇論文，讀出需要的資料後檔案必須消失；處理到一半當掉，檔案也要在一小時左右被清掉（實際上限見「三道防線」）。這種批次另外有一個選項：「把追蹤範圍外的論文也加入實驗室文獻庫」。

其他限制：單檔 50 MB、一次 100 份、每人 1.5 GB；worker 只有 400 MB 記憶體，一份壞掉或超大的 PDF 不能把它拖垮；v1 不用 GROBID；付費論文的內容不能送到任何雲端 AI 服務。

## 考慮過的選項

**檔案怎麼到儲存空間**

- **A. 經過 API。** 瀏覽器傳給 API，API 一邊收一邊轉存到物件儲存。
- **B. 預先簽名的網址（presigned URL）。** API 發一個限時的上傳網址，瀏覽器直接傳到 R2，不經過 API。省主機流量，但檔案大小、檔頭檢查要等傳完才能做；瀏覽器要連到另一個網域（CSP 要放寬）；「沒勾聲明的只能放暫存區」要靠網址的設計保證。

**怎麼從 PDF 認出是哪一篇**

- **甲. 讀前幾頁的文字，用規則找 DOI；找不到再用標題比對。**
- **乙. GROBID。** 最準，但要另外跑一個吃記憶體的服務；PRD 已經把它延到 Should。
- **丙. 把第一頁丟給 LLM 判斷。** 付費論文的內容不能送雲端，直接排除。

## 決定

**A＋甲。**

### 上傳

1. 流程：
   1. `POST /api/v1/uploads`：建立一批上傳（`upload_batch`）。先檢查份數與配額。
   2. 每個檔案一個 `PUT`，API 邊收邊做三件事：算 SHA-256、檢查開頭是不是 `%PDF-`、累計大小（超過 50 MB 立刻中斷）。通過的同時串流寫到物件儲存的暫存區（見下面「傳到一半的檔案」）。不接受的檔案不建立紀錄，直接回固定的錯誤代碼。
   3. 整份收完、檢查都通過之後，才寫一筆 `upload_item`；勾了聲明的先搬到保存的位置，再排一個背景工作去辨認（順序見下面「傳到一半的檔案」第 4 點）。
   - **`upload_batch` 記什麼**：擁有者、`declared`（有沒有勾下載聲明，整批一個值）、`share_out_of_scope`（把追蹤範圍外的論文也加入實驗室文獻庫）、使用者看過結果的時間（背景完成的提示用）。
   - **兩個旗標的關係**：`share_out_of_scope` 只有在 `declared` 是假的時候可以是真（資料庫的檢查條件）。也就是說，勾了下載聲明的批次，對到的追蹤範圍外論文只會進上傳者自己的文獻庫。**這是 Kevin 2026-11-13 決定的，不是畫面漏畫**：勾了下載聲明的批次不能分享追蹤範圍外論文的書目，分享選項只出現在沒勾聲明的那一種。要分享得另外用推薦清單（不勾聲明）傳一次。PRD FR-49 還沒寫這個條件，見「和 PRD 不一致的地方」。
   - `share_out_of_scope` 只決定論文的書目大家看不看得到（`lab_visible`）。**PDF 檔案本身沒有任何可見範圍的參數**，一律只有上傳者看得到。
2. **存放位置由聲明決定，程式裡只有一個函式決定路徑**（`domain/storage_keys.py`）：
   - 勾了：`pdf/<上傳者 ID>/<upload_item ID>.pdf`（Kevin 2026-11-13 決定：一筆紀錄一個檔。原本是用內容的 SHA-256 當檔名）
   - 沒勾：`tmp/<upload_item ID>.pdf`
3. 開啟自己的 PDF 時，API 檢查擁有者後串流回去，不發公開網址（FR-12）。路徑與開新分頁的做法見下面「開啟 PDF」。

### 傳到一半的檔案、取消上傳（2026-11-13 補）

第一版沒有寫兩件事：使用者按「取消」之後已經傳上來的部分怎麼辦；勾了聲明的 PDF 還沒收完、還沒有紀錄的時候放哪裡。

1. **還在傳的內容一律先寫到 `tmp/<upload_item ID>.pdf`**，不管有沒有勾聲明。ID 由 API 在開始收的時候產生（這時還沒有 `upload_item` 那一列；其他表的 ID 是資料庫給的，這裡是明列的例外，格式一樣）。
2. **整份收完、檢查通過，才寫 `upload_item`**（狀態 `received`）。所以「不接受」與「已取消」的檔案在資料庫裡沒有紀錄；UX 文件決定這兩種離開再回來不用列（決定清單第 36 項），剛好不需要紀錄。
3. **取消、斷線、檢查沒過**：API 立刻中止寫入，把已經寫進去的部分刪掉，不建列。
4. **勾了聲明的 PDF，順序固定**：寫 `upload_item`（`received`）並完成交易 → 搬到 `pdf/<上傳者 ID>/<upload_item ID>.pdf` → 在 `upload_item` 記下搬好的時間（`stored_at`）→ 刪掉暫存的那一份 → 才排入辨認工作。
   - **紀錄一定先寫完，才開始搬。** 所以 `pdf/` 底下的每個物件，從出現的那一刻起就有一筆紀錄對著它（補刪靠這一點，見下一節）。
   - 先搬好才排入，是因為只傳一份時辨認工作幾毫秒後就開始；兩邊同時搬，會有一邊找不到來源而回報錯誤。
   - **「搬好了沒」只看 `stored_at`**，不看物件在不在。辨認工作的第一步：勾了聲明而 `stored_at` 是空的就補搬。已經搬好的項目不會因為暫存檔被清掉而變成 `expired`（保留期到了是另一回事，見下面「保留 7 天」）。
   - **搬這一步可以重做，不用上鎖**：來源與目的地都由項目的 ID 決定，重做一次只是把同樣的內容再蓋上去。做法分三步，不在開著的交易裡呼叫物件儲存：(1) 複製；(2) 開一個短交易鎖住這一列並重讀，項目還沒放掉才記 `stored_at`；(3) 記好了就刪暫存的那一份。第 (2) 步發現項目已經放掉（例如同時被清暫存檔的工作標成 `expired`）時不記 `stored_at`，改成把剛複製進去的那個物件放掉。
   - 複製時來源已經不在：重讀這一列，`stored_at` 有值就當作搬好了（另一邊先搬完了）；沒有值才標成 `expired`。
   - 搬是物件儲存自己複製，用一個請求做完的那一種（`copy_object`），不用會自動分段的複製：分段複製中斷時會在 `pdf/` 留下看不到的分段。
   - API 在寫好紀錄之後、排入之前當掉：這一項停在 `received`，`sweep` 會補排（ADR-0004），辨認工作再補搬。
5. **萬一沒清到**（API 行程在收檔時整個被結束）：留下的東西只會在 `tmp/` 底下。已經寫完的檔案由下面「三道防線」清。**沒完成的分段上傳**不算一個檔案，`purge-tmp` 列物件時看不到，所以 `purge-tmp` 多做一步：列出 `tmp/` 底下還沒完成的分段上傳，開始超過 60 分鐘的一律中止。bucket 另設一條規則當最後一道：1 天後自動中止（R2 預設是 7 天，Cloudflare 文件 2026-11-13 查；這種規則的單位是天，1 天是最短）。
6. 這樣設計的重點：**一個檔案在還沒有紀錄之前，只可能待在 `tmp/`**；`pdf/` 底下的每個 PDF 從檔名就看得出是哪一個上傳項目的（下一節）。

代價：勾了聲明的 PDF 要多一次複製（在物件儲存裡面做，不經過主機）。

### 保存的 PDF：誰佔著、怎麼放掉、配額算什麼（2026-11-13 補；同一天改成一筆紀錄一個檔後整節重寫）

> **這一節是重寫的，沒有經過之前那三輪審查。** Kevin 2026-11-13 決定把存放位置從「內容的 SHA-256」改成「上傳項目的 ID」。原本同一個人把同一份 PDF 傳兩次，兩筆紀錄共用一個物件，刪除前要查還有誰在用、要上鎖；現在一個物件只屬於一個上傳項目，這些都不需要了。之前定的規則沒有變：新的處理成功並確認之前舊的不動、取消時新的立刻放掉、等確認取代不算配額、失敗保留 7 天、寬限是每人總共 50 MB。

1. **一個物件只對一個上傳項目。** 位置是 `pdf/<上傳者 ID>/<upload_item ID>.pdf`。項目對到論文時，建立的 `pdf_file` 記下這個項目的 ID 當「物件編號」（唯一），之後由 `pdf_file` 接手同一個物件，不搬、不複製。SHA-256 照樣算、照樣存在 `upload_item` 與 `pdf_file`，只用來比「內容是不是一樣」，不決定存放位置。
2. **「這個物件還有沒有人要」只有一個定義**（一個查詢，用物件編號查）。下面任何一個成立就是還有人要：
   - 那個 `upload_item` 存在，而且還沒放掉（`released_at` 是空的）。**不看 `stored_at`**：紀錄先寫、才開始搬，搬到一半的也算有人要。
   - 有還沒刪的 `pdf_file`，物件編號是它。
3. **只會從「有人要」變成「沒人要」，不會變回來。** `released_at` 填了不能清空；`pdf_file` 標成已刪除不能還原；項目的 ID 不重用。狀態函式擋住前兩項，各有測試。因為不會變回來，刪除之前查一次就夠，不用上鎖。
4. **項目什麼時候放掉**（填 `released_at`）：
   - 對到論文、建立 `pdf_file` 的那個交易：交給 `pdf_file`，物件留著。
   - 變成 `duplicate`：這位上傳者已經有同一篇、內容相同的 PDF。**新傳的這一份刪掉**，原本那一份（它自己的物件）不動。
   - 變成 `declined`（下面「不加入」、取代時按了「不換」、處理失敗時按了「刪除」、論文頁按了「換一個 PDF」）。
   - 變成 `expired`（保留期到了）或 `over_quota`。
5. **刪物件只經一個函式**：`services/uploads.py` 的 `release_stored_pdf(物件編號)`。「不加入」、刪除自己的 PDF、取代、刪除處理失敗的 PDF、保留期到了、`duplicate`、`over_quota` 都只呼叫它，不自己刪。
   - 先在自己的交易裡把紀錄改好（填 `released_at`，或把 `pdf_file` 標成已刪除），**交易完成後**才呼叫。
   - 它先查第 2 點，還有人要就什麼都不做；沒人要才刪物件。刪一個已經不在的物件不算錯，所以可以重送。
   - 它不上鎖，也不在開著的交易裡呼叫物件儲存。原本「持有鎖的時候呼叫物件儲存」的兩處例外因此拿掉。
6. **補刪：紀錄改好了、物件還沒刪就當掉**。`purge-tmp` 每次也列出 `pdf/` 底下的物件，把沒人要的清掉。**只清「沒有任何紀錄還要它」的物件**（項目已經放掉、`pdf_file` 已經刪除，或根本找不到紀錄），而且要通過下面每一道保護：
   - **紀錄還沒放掉的不清**（第 2 點）。剛收進來、正在搬、`stored_at` 還沒記的物件因此不會被當成沒人要：它的紀錄在開始搬之前就寫完了。
   - **物件在儲存空間放滿 60 分鐘才清**（設定值；用物件儲存回報的最後修改時間算）。這是第二道：就算哪裡的順序寫錯了、紀錄比物件晚出現，剛進來的物件也不會被清。複製一份 PDF 只要幾秒，60 分鐘遠大於它。
   - **檔名不是 `pdf/<上傳者 ID>/<upload_item ID>.pdf` 這個樣子的不清**，只記一筆警告。不認得的東西不刪。
   - **查資料庫失敗時，這一輪什麼都不清。**
   - **一輪要清的超過上限（設定值，預設 20 個）時，一個都不清**，寫錯誤日誌，這一輪不送 `purge-tmp` 的心跳，Kevin 因此收到通知。正常情況下要補刪的只有當掉留下的一兩個；一次出現很多，比較可能是資料庫被還原到舊的時間點或接錯了資料庫，這時所有 PDF 看起來都沒人要，照刪會刪光成員的 PDF。
   - 通過的才交給第 5 點的函式（它會再查一次）。
   - 多久補上：放了超過 60 分鐘的物件，最慢 15 分鐘後；剛進來的，最慢 75 分鐘後。這段時間那個物件沒有人開得到（紀錄已經放掉），也不算配額（配額看紀錄）。
7. **配額分兩次檢查：收檔時粗檢查，認出論文之後才算準**（Kevin 2026-11-13 決定）。只有勾了聲明的 PDF 算配額；沒勾的不保存，不檢查。大小看紀錄，分成兩群；一個物件只會被算一次（項目還沒放掉時算在項目，交給 `pdf_file` 之後算在 `pdf_file`）：
   - **已經算進配額的**：還沒刪的 `pdf_file`，加上停在 `needs_manual`、`mismatch_confirm`、`failed` 的項目。畫面上「已用的儲存空間」就是這個數字，它不會超過配額。
   - **收進來了、還沒算的**：停在 `received`、`identifying`、`needs_confirm`、`lookup_deferred`、`replace_confirm` 的項目。前四種是還不知道它是新的一篇還是要取代舊的；最後一種是知道了，在等使用者確認取代。
8. **收檔時的檢查**：已經算進配額的 ＋ 收進來還沒算的 ＋ 這一份，不可以超過「配額 ＋ 寬限」。寬限是設定值，預設 50 MB（等於單檔上限）。
   - **寬限是這位成員總共的額度，不是每個檔案各算一次。** 前面收進來、還沒算的都加在裡面，所以一次傳很多份不會全部放行。
   - 寫 `upload_item` 的交易先鎖住這位上傳者再算，同時傳好幾份也不會各自都過。超過就不建列、刪掉暫存的那一份、回配額的錯誤代碼。
   - 為什麼要有寬限：收檔時還沒讀檔，不知道這一份是不是要取代舊的。沒有寬限的話，配額快滿的人傳新版本在這一步就被擋，永遠換不了。
   - **和改之前唯一看得到的差別**：重複傳一份已經有的 PDF，在判定成 `duplicate` 之前也算在「收進來還沒算的」裡（它現在真的另外佔一份空間，判定後就刪掉）。原本它和舊的共用一個物件，不另外算。
9. **認出論文之後的檢查**（準確的那一次）：項目要從「還沒算的」變成「算進配額的」時（對到新的一篇而建立 `pdf_file`、改成 `needs_manual`、`mismatch_confirm`、`failed`），狀態函式鎖住這位上傳者，檢查「已經算進配額的 ＋ 這一份」有沒有超過配額。
   - 沒超過：照常。
   - 超過：項目改成 `over_quota`（終點狀態）、填 `released_at`，交易完成後放掉這一份。畫面的文字設計已經補上（2026-11-13）；總結多一項「N 個空間不夠」。
   - 變成 `replace_confirm` 不檢查（它不算配額）；按確認時才用「已用 − 舊的 ＋ 新的」檢查（下面「同一篇的第二份 PDF」）。變成 `duplicate` 也不檢查（那一份馬上刪掉）。
10. 「刪不刪物件」看第 2 點，「算不算配額」看第 7 點的分法；兩個都只各有一個查詢，不各寫一份。

**一次傳多份的測試情境**（拆 Story 時帶進驗收條件；和改存放方式之前是同一組，數字沒有變）。配額 1,500 MB、寬限 50 MB；這位成員已經算進配額的是 1,480 MB；同一批傳三份、各 30 MB、都勾了聲明：

| 步驟 | 算式 | 預期結果 |
|---|---|---|
| 收第 1 份 | 1,480 ＋ 0 ＋ 30 ＝ 1,510，不超過 1,550 | 收下；物件在 `pdf/<上傳者>/<第 1 份的項目 ID>.pdf` |
| 收第 2 份 | 1,480 ＋ 30 ＋ 30 ＝ 1,540，不超過 1,550 | 收下；它有自己的物件 |
| 收第 3 份 | 1,480 ＋ 60 ＋ 30 ＝ 1,570，超過 1,550 | 不接受，回配額的錯誤代碼，不建列、暫存的那一份刪掉；`pdf/` 底下沒有它的物件 |
| 三份同時送出 | 同上，只是順序不一定 | 一樣只收下兩份，不會三份都過 |
| 第 1 份認出是同一篇的新版本（舊的 25 MB） | 不檢查 | 變成 `replace_confirm`；已用的儲存空間還是 1,480 MB；舊的與新的兩個物件都在 |
| 第 2 份認出是新的一篇 | 1,480 ＋ 30 ＝ 1,510，超過 1,500 | 變成 `over_quota`，第 2 份的物件從儲存空間刪掉；已用的還是 1,480 MB |
| 第 1 份按確認取代 | 1,480 − 25 ＋ 30 ＝ 1,485，不超過 1,500 | 取代成功，舊的那個物件刪掉、新的那個物件還在（沒有搬）；已用的變成 1,485 MB |
| 之後再傳第 3 份 | 收檔：1,485 ＋ 0 ＋ 30 ＝ 1,515，不超過 1,550 | 收下；認出是新的一篇時 1,515 超過 1,500，變成 `over_quota`，它的物件刪掉 |

**一筆紀錄一個檔多出來的測試情境**（一樣帶進驗收條件）：

| 情境 | 預期結果 |
|---|---|

**勾了聲明的 PDF 在每個狀態下在哪裡、使用者怎麼讓它消失**

| 狀態 | PDF 在哪裡 | 怎麼消失 |
|---|---|---|
| `received`、`identifying` | 先在 `tmp/`，搬好後在 `pdf/`，是這個項目的 | 等處理完 |
| `matched` | `pdf/`，交給 `pdf_file` 了（同一個物件） | 論文頁「刪除 PDF」 |
| `duplicate` | 這一份已經刪掉；原本那一份照舊在 `pdf/`，是原本那筆 `pdf_file` 的 | 原本那一份：論文頁「刪除 PDF」 |
| `needs_confirm` | `pdf/`，是這個項目的；還沒算配額 | 按「是這一篇」之後同 `matched`；按「不是」之後同 `needs_manual` |
| `needs_manual` | `pdf/`，是這個項目的；算在配額裡 | 「存檔」之後同 `matched`；「不加入」之後放掉 |
| `lookup_deferred` | 同上；還沒算配額 | 稍後自動再查，之後落到上面其中一種 |
| `mismatch_confirm` | 同上；算在配額裡 | 「放在這一篇」之後同 `matched`；「換一個 PDF」之後放掉 |
| `replace_confirm` | 新的那一份在 `pdf/`，是這個項目的，**不算配額**；舊的那一份是另一個物件，照舊是 `pdf_file` 的 | 按確認：新的同 `matched`，舊的放掉。按「不換」：新的放掉，舊的不動。都沒做，7 天後自動放掉新的，舊的不動 |
| `failed` | `pdf/`，是這個項目的；算在配額裡 | 「重試」成功後照新的狀態走；按「刪除」立刻放掉；都沒做，7 天後自動放掉 |
| `declined`、`expired`、`over_quota` | 已經放掉 | — |

### 辨認

1. 背景工作開一個**子行程**來讀 PDF，並設兩道限制：記憶體上限（200 MB）與時間上限（30 秒）。超過任何一個，子行程被結束，這個檔案標成 `failed`，worker 本身不受影響。`pdf` 這條佇列的工作共用一把鎖，同時只跑一個（ADR-0004 第 6 項）。子行程用的記憶體算在 worker 容器的 400 MB 上限裡。
2. 子行程用 pypdf 讀前 3 頁的文字與檔案的中繼資料，只回傳三樣東西：找到的 DOI（用規則式比對）、推測的標題、頁數。**PDF 的內文不離開這個子行程，不寫進日誌，也不送到任何外部服務。** 這三樣東西和原始檔名一起存在 `upload_item`，所以之後重查、讓使用者確認、手填，都不需要檔案還在。檔名不寫進日誌。
3. 對論文的順序：
   1. 有 DOI：正規化後查資料庫 → 沒有就查 OpenAlex → 再沒有查 Crossref（FR-12）。
   2. 沒有 DOI：用推測的標題在資料庫裡做字元相似度比對，列出候選讓使用者確認。
   3. 都對不到：請使用者手填書目。手填的只有他自己看得到，標示「使用者輸入、未經 OpenAlex 驗證」。
   - **比對用上傳者的身分查**（`MemberViewer`，由批次的擁有者建立），不用「看得到全部」的身分；候選清單不存進 `upload_item`，顯示時即時查。否則候選裡會出現別的成員私下匯入的論文（ADR-0002）。
4. 對到的論文不在追蹤範圍內時，照 FR-49 向 OpenAlex 補書目與摘要，標「追蹤範圍外」，可見範圍依上傳時的勾選框。
5. 去重：同一個上傳者、同一篇論文、同一個 SHA-256，不重複存：新傳的那一份判定成 `duplicate` 之後刪掉，原本那一份不動。同一篇、內容不同的第二份見下面「同一篇的第二份 PDF」。

### 每個檔案的狀態

`upload_item` 的狀態只有這些值，轉換只經一個函式：

| 狀態 | 意思 |
|---|---|
| `received` | 檔案收到了，等辨認 |
| `identifying` | 正在讀檔或查外部來源 |
| `matched` | 對到論文了 |
| `duplicate` | 這位上傳者已經有同一篇、同一個檔案 |
| `needs_confirm` | 沒有 DOI，用標題找到候選，等使用者確認 |
| `needs_manual` | 對不到，等使用者手填 |
| `declined` | 使用者決定不要這一份。兩種來源：在手填書目那一張按了「不加入」，而且已經離開那一頁（見下面「不加入」）；取代確認時按了取消（見下面「同一篇的第二份 PDF」）。處理失敗的那一列按了「刪除」（見下面「保留 7 天」）。論文頁對不上時按了「換一個 PDF」。終點狀態；只能從 `needs_manual`、`replace_confirm`、`failed`、`mismatch_confirm` 轉入 |
| `replace_confirm` | 認出是哪一篇了，但這位上傳者對這篇已經有另一份內容不同的 PDF，等使用者確認要不要取代（2026-11-13 補） |
| `mismatch_confirm` | 從論文頁「換成我自己下載的版本」上傳，但檔案讀出來的是另一篇，等使用者確認 |
| `lookup_deferred` | 外部來源暫時查不了：連不上（重試之後還是不行），或今天的額度用完。稍後自動再查（`sweep` 的登記清單上有這個狀態）。畫面寫「暫時查不到，稍後會自動再試」，這一批照樣算處理完 |
| `failed` | 讀檔失敗（壞檔、超過記憶體或時間上限）。可以重試，也可以刪除 |
| `over_quota` | 收下來了，但認出論文之後發現是新的一篇、而且空間不夠；這一份已經刪掉，清出空間後要重新上傳（2026-11-13 補）。終點狀態 |
| `expired` | PDF 已經不在了，要重新上傳。三種來源：還沒讀完，暫存檔就被清掉；勾了聲明、處理失敗，保留 7 天沒有處理；等確認取代，7 天沒有人確認 |

### 不加入（2026-11-13 補，UX 文件決定清單第 31、34 項）

手填書目那一張有「不加入」。按了之後那一張變成「沒有加入」＋「復原」；還在那一頁時可以復原，離開之後不能復原，勾了下載聲明、已經保存的 PDF 這時要一起刪掉。UX 文件把「離開怎麼判定」留給架構，原則是不可以留下使用者找不到、刪不掉的 PDF。

**考慮過的做法**

- **A. 按下去就告訴伺服器，伺服器記「可以復原」的狀態，再靠瀏覽器定時報到或計時器判定離開。** 伺服器要多一種中間狀態、一個計時的清理工作，還要定義多久沒報到算離開；使用者把分頁開著去吃飯再回來按復原，可能已經被清掉。
- **B. 「可以復原」的那一段只存在瀏覽器裡，離開那一頁時才告訴伺服器。** 和「移出文獻庫的復原」同一個做法（架構文件 AD-26）。

**決定：B。**

1. **按「不是」的當下就送請求。** 候選比對按「不是」時那一張原地換成手填書目（UX 文件），伺服器同時把這一項從 `needs_confirm` 改成 `needs_manual`。不這樣做的話，之後的「不加入」會因為伺服器上還是 `needs_confirm` 被擋下，PDF 也沒刪。
2. **按「不加入」時前端不送請求，只改畫面**：那一張變成「沒有加入」＋「復原」。這一筆記在一個全站共用的前端狀態裡；上傳頁的表格與總結、導覽列的提示、我的文獻庫上方的「有 N 篇等你確認」都要扣掉它。伺服器回的等確認篇數這時還含這一篇，所以顯示之前一律先扣，同一個畫面上不會有兩個不同的數字。按「復原」就只是把這一筆拿掉，已經填的內容還在。
3. **離開那一頁時才送**，兩個觸發點：
   - 站內換頁：用一般的請求送，等它回來，再重新抓等確認的篇數。不等的話，下一頁的「有 N 篇等你確認」可能先查到舊的數字。
   - 關掉分頁、重新整理、連到站外：在瀏覽器的 `pagehide` 事件用關頁也送得出去的請求（`fetch` 加 `keepalive`）送。不用 `unload` 事件，新版的 Chrome 已經不執行它。
   - 按上一頁時瀏覽器可能把整頁原樣還原（畫面上還有「復原」，但伺服器已經改成 `declined`）。所以頁面是從上一頁快取還原時（`pageshow` 事件的 `persisted` 為真），重新讀這一批的狀態。
4. **端點**：`POST /api/v1/upload-items/decline`，內容是項目 ID 的清單。可以重送：不是 `needs_manual`、`replace_confirm`、`failed`、`mismatch_confirm` 的項目略過，不算錯（頁面關閉時送的請求讀不到回應，不能靠錯誤來處理）。
5. 伺服器收到後，經 `upload_item` 的狀態函式把這些項目從 `needs_manual` 改成 `declined`，同一個交易填 `released_at`、寫一筆稽核事件；交易完成後照「保存的 PDF」那一節放掉 PDF（勾了聲明才有）。**「不加入」只有 `needs_manual` 可以變成 `declined`（另一條路是取代時按取消，見下一節）；`declined` 不能再變。** 這種刪除算清理類：放掉的是還沒對到論文的 PDF，不另外留副本。
6. **請求沒送到的時候**：伺服器上這個項目還是 `needs_manual`。使用者回來時它還在「等你確認」，PDF 也還在，可以再按一次「不加入」。所以最壞的情況是「以為不加入了，回來發現還在等」，不會有找不到、刪不掉的 PDF。會沒送到的情況：瀏覽器當掉、電腦沒電；**手機上切到別的 App 再把瀏覽器滑掉**（這時瀏覽器不會通知頁面，在手機上很常見）。
7. `declined` 的項目離開再回來仍然列在表格（「沒有加入」），算進總結的「N 個沒有加入」與「沒加入的」；**不算進等確認的篇數**（`GET /api/v1/me/status` 與我的文獻庫上方的「有 N 篇等你確認」）。之後要加入得重新上傳。
8. 沒勾聲明的項目按「不加入」：暫存檔早就刪了，只改狀態。

代價：使用者在另一個分頁或另一台裝置上，要等這邊離開那一頁之後才會看到等確認的篇數減少；手機上沒送到的機會比桌機高。

### 同一篇的第二份 PDF：確認之後才取代（Kevin 2026-11-13 決定）

去重只擋「同一個人、同一篇、內容完全相同」的 PDF。先傳預印本、後來又傳正式版，內容不同，原本會存成兩份；論文頁的設計稿只畫一份。Kevin 決定：**一位成員對一篇論文只留一份 PDF，新的取代舊的**，加兩個條件；不做「保留舊檔可以復原」。

1. **新的那一份處理成功、而且認出是同一篇論文之後，才談得上取代。** 判斷只在一個地方：狀態函式要把項目改成 `matched` 的那一刻（不管是自動對到、使用者按了「是這一篇」、還是稍後自動再查到的），先看這位上傳者對這篇論文有沒有還沒刪的 `pdf_file`：
   - 沒有：照舊變成 `matched`，建立 `pdf_file`。
   - 有，SHA-256 相同：`duplicate`（原本的規則）。
   - 有，SHA-256 不同：變成 `replace_confirm`，**不建立 `pdf_file`、不動舊的那一份**。
2. **所以這些情況舊的那一份都不會被動到**：新的讀檔失敗（`failed`）、檔案壞掉、認出來是別篇論文（照那一篇的流程走）、對不到而改成手填書目（手填的是另一筆書目）、暫時查不到、使用者一直沒回來確認。取代只發生在下面第 4 點那一個交易裡，沒有別的路。
3. **確認畫面要列出舊的和新的各自的檔名、頁數、上傳日期。** 舊的來自 `pdf_file`，新的來自 `upload_item`。`pdf_file` 因此多存兩樣：頁數（建立時從 `upload_item` 帶過來）與上傳時間。兩邊都用上傳者自己的身分讀，顯示時才查，不把舊的那一份的資料抄進 `upload_item`。畫面的文字與樣子設計已經補上（2026-11-13）；取消的按鈕在畫面上寫「不換」。
4. **按確認**（`POST /api/v1/upload-items/<項目 ID>/confirm-replace`）：一個交易裡做完四件事，交易完成後才刪物件。
   - 先對（上傳者, 論文）上鎖，**重新判斷一次**第 1 點（等確認的期間舊的那一份可能已經被刪掉或被另一份取代：變成沒有就直接 `matched`，變成內容相同就 `duplicate`）。
   - 舊的 `pdf_file` 標記為已刪除，照一般刪除的規則留紀錄的副本、寫稽核事件（副本是紀錄，不是 PDF 本身）。
   - **算配額**：已經算進配額的 − 舊的那一份 ＋ 新的那一份，超過配額就不取代，回配額的錯誤代碼，舊的與新的都不動（使用者可以取消，或先刪別的 PDF 再確認）。新的那一份從這一刻起才算配額。
   - 建立新的 `pdf_file`（物件編號是這個項目的 ID，新的那一份留在原地不搬），項目改成 `matched`、填 `released_at`。
   - 交易完成後用舊的那一份的物件編號呼叫 `release_stored_pdf`。舊的 PDF 這時就從儲存空間刪掉，沒有復原。
5. **按取消（畫面上是「不換」）**：走「不加入」同一個端點（`POST /api/v1/upload-items/decline`），項目從 `replace_confirm` 變成 `declined`、填 `released_at`，交易完成後放掉新的那一份。這裡沒有「離開頁面才送」的復原：按下去就送。
6. **等確認的期間**：新的那一份已經在 `pdf/`，是這個項目的（項目還沒放掉，所以不會被當成沒人要的物件清掉），但**不算配額**（Kevin 2026-11-13 決定）。這一項算進等確認的篇數（它在等使用者決定）。
   - **沒人回來確認，7 天到期**（Kevin 2026-11-13 決定）：項目變成 `expired`，新的那一份放掉，舊的照留。做法見下面「保留 7 天」。
   - 代價：沒算配額的 PDF 最多會在儲存空間留 7 天。4 個人、單檔最多 50 MB，不另外設上限。
7. **資料庫擋最後一道**：`pdf_file` 對（上傳者, 論文）有一個只算還沒刪的唯一索引，所以不管程式怎麼走，一位成員對一篇論文不會同時有兩份。API 裡「我的 PDF」仍然是清單（現在最多一份），之後要改成並列時不用改形狀。
8. **測試情境**（拆 Story 時帶進驗收條件）：新的讀檔失敗，舊的還開得到；新的認出是別篇，舊的還在；確認之後舊的開不到、儲存空間裡找不到、新的開得到；取消之後新的在儲存空間裡找不到、已用的空間回到原本的數字；同一篇同時有兩個項目在等確認，確認其中一個之後，另一個確認時比的是剛換上去的那一份；等確認的那一份不算在已用的空間裡，確認之後才算；確認時超過配額，舊的還開得到；7 天沒有確認，新的在儲存空間裡找不到、舊的還開得到。

### 保留 7 天；處理失敗的 PDF 可以自己刪（Kevin 2026-11-13 決定）

勾了聲明的 PDF 一收完就保存。有兩種情況會讓它停在那裡沒人管：讀檔失敗（畫面原本只有「重試」），以及等確認取代卻沒有人回來。

1. **保留期是一個設定值，預設 7 天**，兩種情況共用：
   - `failed`、而且已經保存（`stored_at` 有值）的項目：從最後一次變成 `failed` 起算；重試會重新起算。
   - `replace_confirm` 的項目：從變成 `replace_confirm` 起算。
2. **到期**：`purge-tmp` 每次也找出到期的項目，經狀態函式改成 `expired`、填 `released_at`，交易完成後放掉 PDF。畫面照 UX 現有的「檔案已經刪除，請重新上傳」。等確認取代的那一種只丟新的，舊的那一份從頭到尾沒有被動過。
3. **「處理失敗」那一列多一個「刪除」**：按下去立刻送，**不用再確認**。走「不加入」同一個端點（`POST /api/v1/upload-items/decline`），項目從 `failed` 變成 `declined`、填 `released_at`、寫稽核事件，交易完成後放掉 PDF；它佔的配額馬上還回來。
   - 沒有「復原」。正在重試的項目（狀態已經不是 `failed`）會被略過。
   - 沒勾聲明、暫存檔還在的失敗項目也能用同一個端點（一併刪掉暫存檔）；畫面上這一種一樣顯示「刪除」，和勾了聲明的是同一種列、同一組按鈕（Kevin 2026-11-13 決定）；暫存檔已經不在時只改狀態。
   - 刪除之後那一列顯示「沒有加入」，總結算在「N 個沒有加入」（Kevin 2026-11-13 確認）。按鈕的樣子設計已經補上。
4. 保留期內 `failed` 的 PDF 算在配額裡（它真的佔著空間）；等確認取代的不算（上一節）。

### 畫面怎麼分得出「沒有換」與「沒有加入」（2026-11-13 補）

設計補畫面時發現兩個分不出來的地方：取代時按了「不換」和手填書目按了「不加入」，資料上都是 `declined`，但畫面上的字不該一樣；等確認取代滿 7 天到期的和暫存檔被清掉的都是 `expired`，但前一種原本的 PDF 其實還在。

1. **`upload_item` 多記一個「上一個狀態」**（`prior_status`）：狀態函式每次改狀態時，把改之前的值寫進去。不另外加狀態值；狀態清單維持原樣。
2. API 回每個項目時帶 `status` 與 `prior_status`。
3. **那一列顯示哪一句、算進總結的哪一項，由前端的一個函式從這兩個值決定**，表格與總結共用，所以兩邊的數字一定對得起來。對照表（沒列到的照原本的狀態表）：

   | `status` | `prior_status` | 那一列的字 | 總結算在 |
   |---|---|---|---|
   | `matched` | `replace_confirm` | 照「對到了」的寫法 | N 篇換了 PDF |
   | `declined` | `replace_confirm` | 沒有換，原本的 PDF 還在 | N 篇沒有換 PDF |
   | `expired` | `replace_confirm` | 沒有換，原本的 PDF 還在 | N 篇沒有換 PDF |
   | `declined` | `needs_manual` | 沒有加入 | N 個沒有加入 |
   | `declined` | `failed`（按了「刪除」） | 沒有加入 | N 個沒有加入 |
   | `declined` | `mismatch_confirm`（論文頁按了「換一個 PDF」；Kevin 2026-11-13 確認） | 論文頁回到選 PDF 的樣子，不另外顯示一句；上傳清單有列到這一項時寫「沒有加入」 | N 個沒有加入 |
   | `expired` | 其他 | 檔案已經刪除，請重新上傳 | 照原本的 |
   | `over_quota` | 任何 | 空間不夠（文字照設計稿） | N 個空間不夠 |

4. 一個項目只會算進總結的一項。
5. 小地方：按確認取代的那一刻，如果舊的那一份剛好已經被使用者自己刪掉，結果其實是「加入」而不是「換」，但照上表仍然算在「換了 PDF」。使用者確實按了確認取代，不另外處理。
6. 測試情境：按「不換」之後 API 回 `declined` 與 `replace_confirm`；7 天到期之後回 `expired` 與 `replace_confirm`，而且原本的 PDF 還開得到；失敗的按「刪除」之後回 `declined` 與 `failed`。

### 開啟 PDF（2026-11-13 補，UX 文件決定清單第 49 項）

論文頁「我的 PDF」多了「開啟 PDF」：在新分頁打開自己上傳的那一份，只有上傳的人開得到。

1. 路徑：`GET /api/v1/pdf-files/{pdf_file_id}/content`。用 `pdf_file` 的 ID，不用論文的 ID（現在一位成員對一篇論文只留一份；之後要改成並列時這個路徑不用改）。
2. **只有擁有者開得到**：讀 `pdf_file` 走只給擁有者的那個查詢函式（架構文件 AD-4）；不是擁有者、已經刪除、不存在，都回同一個 404。不發預先簽名的網址，也沒有任何不用登入就能開的網址。
3. API 檢查通過後，**先確認物件還在**，再從物件儲存一邊讀一邊送給瀏覽器，不整份讀進記憶體（api 只有 350 MB）。v1 不支援只要其中一段的請求，整份送。
4. **回應的標頭整組固定**，寫在這個路由自己的一個地方：

   | 標頭 | 值 | 為什麼 |
   |---|---|---|
   | `Content-Type` | `application/pdf` | — |
   | `Content-Disposition` | `inline`，加兩種檔名：`filename`（只有英數的備用檔名）與 `filename*`（UTF-8 編碼的原始檔名） | 直接顯示而不是下載；中文檔名要用第二種寫法才不會變亂碼 |
   | `X-Content-Type-Options` | `nosniff` | 上傳時只檢查過開頭是 `%PDF-`，要擋住偽裝成 PDF 的網頁 |
   | `Cache-Control` | `private, no-store` | 不進共用快取，也不留在這台電腦的快取裡。有使用者回報 Chromium 的檢視器另存時會因此重新下載一次；Story 實測有問題的話改成 `private`，改之前問 Kevin |
   | `Content-Length` | 檔案大小 | 瀏覽器才顯示得出進度 |
   | `Accept-Ranges` | 不送 | v1 不支援分段讀取 |

   不加 CSP 的 `sandbox`：它確定會讓 Chromium 與舊版 Safari 的內建檢視器顯示不出來。
5. **前端用一般的連結開新分頁**（網址由資料來源層的函式產生），不用程式先把 PDF 抓下來再開：登入用的 cookie 在同一個網站開新分頁時會帶上，不需要另外處理；也不用為了它放寬安全標頭。
6. **打不開的時候不回給程式看的 JSON。** 這個網址是瀏覽器直接開的，使用者會看到整頁內容：
   - 沒登入（登入過期）：轉到登入頁，登入後回到這個網址。
   - 不是擁有者、已經刪除、不存在、紀錄還在但物件不見了：都轉到前端同一個「找不到這份 PDF」的頁面，不分原因（維持「沒有權限和不存在看起來一樣」）。這一頁的文字設計已經補上（2026-11-13）：標題「找不到這份 PDF」，說明「可能已經刪除，或不是你上傳的。」，連結「到我的文獻庫」；三句都放 i18n。
7. 這個端點在換人測試與金絲雀測試的範圍內（每個端點都要有，架構文件 AD-3）；換人測試的預期結果是被轉到「找不到」那一頁、拿不到任何內容。檔名不寫進日誌。
8. **還沒有驗證的事**：瀏覽器內建的 PDF 檢視器在全站安全標頭（CSP）下能不能正常顯示，查不到保證，三種瀏覽器引擎都要在做這個功能的 Story 實測。要測的四件事：直接開；按上一頁再按下一頁（Safari 有這種情況變灰的舊問題）；用檢視器另存，檔名與內容對不對；一份 50 MB 的 PDF。不行的話只對這個回應調整安全標頭（架構文件 AD-22 明列這是唯一可以不同的回應），不放寬全站的。

### 沒有下載聲明的檔案一定會消失：三道防線

| 防線 | 做法 | 什麼時候起作用 |
|---|---|---|
| 1 | 辨認工作從檔案讀出 DOI、標題、頁數之後**立刻**刪除 `tmp/` 的檔案，並在 `upload_item` 記下刪除時間；後面查外部來源、等使用者確認都不需要檔案 | 正常情況，幾秒內 |
| 2 | `purge-tmp` 工作每 15 分鐘跑一次：列出 `tmp/` 底下放了滿 60 分鐘的檔案，全部刪除；沒完成的分段上傳開始超過 60 分鐘的一律中止。所以最慢 75 分鐘消失 | worker 處理到一半當掉；讀檔失敗的檔案；API 收到一半被結束 |
| 3 | R2 bucket 對 `tmp/` 設 lifecycle 規則，1 天後自動刪；沒完成的分段上傳也是 1 天後自動中止 | 整台主機都掛了 |

- **讀檔失敗的檔案不馬上刪**，留到 `purge-tmp`。UX 文件的「處理失敗」狀態有「再試一次」，馬上刪的話就沒有檔案可以重試。能不能重試看檔案實際還在不在（至少 60 分鐘、最多 75 分鐘），不是用時間推算。
- `purge-tmp` 刪掉一個檔案時，先鎖住那一列並重讀，把還沒讀完、也還沒搬好的那一項（`received`、`identifying`、`failed`，而且 `stored_at` 是空的）標成 `expired`、填 `released_at`；已經搬好的（`stored_at` 有值）不標。辨認工作剛好在補搬的話，它記 `stored_at` 之前也會鎖住同一列重讀：看到已經是 `expired` 就不記，並把剛複製進 `pdf/` 的那個物件放掉（「傳到一半的檔案」第 4 點）。辨認工作開始時發現檔案已經不在，也走同一個轉換，不重試。這樣不會有項目永遠停在「處理中」。
- 已經讀完的項目（等確認、等手填、稍後自動再查）不受影響，因為它們不需要檔案。

FR-49 的兩個驗收測試各對應第 1、2 道：處理完後儲存空間裡找不到檔案；工作中途被中斷，一小時後跑清理也找不到。第 2 道另外加一個測試：收到一半就中斷的分段上傳，一小時後跑清理，列不到沒完成的分段。

這批上傳對到的論文會加進上傳者的個人文獻庫，加入方式記成 `shared_list`（勾了下載聲明的是 `upload`）。加入方式只記第一次怎麼加入的，之後不改；文獻庫頁的「我上傳的／別人分享的／我自己加入的」篩選靠它，一次選一個（架構文件 AD-4）。**「有我的 PDF」開關與「看有 PDF 的論文」不看加入方式，看的是這位成員對這篇有沒有還沒刪的 `pdf_file`**：先自己加入、後來才上傳 PDF 的論文，加入方式還是 `manual`，不會出現在「我上傳的」，但打開「有我的 PDF」找得到。兩者可以同時用（Kevin 2026-11-13 定案，UX 文件「13. 我的文獻庫」）。

### 換成我自己下載的版本

論文頁的「換成我自己下載的版本」就是對同一篇論文再走一次「勾了聲明」的上傳。

### 保存的檔案記錄什麼

`pdf_file`：擁有者、論文、物件編號（當初那個上傳項目的 ID，唯一；存放位置由它決定，2026-11-13 補）、SHA-256（只用來比內容是不是一樣）、大小、原始檔名、頁數、上傳時間、取得方式（OA／訂閱／其他）、授權、下載聲明的時間、處理方式、版本（預印本／作者接受稿／正式版）。頁數與上傳時間是取代確認畫面要用的（2026-11-13 補）。v1 的處理方式只會是「只存不擷取」。版本欄位 v1 由上傳者選填、預設「不確定」；「有正式版時怎麼優先」是全文管線（Should）的事，等那時再決定（ARCH-10）。

### 刪除

上傳者刪除自己的 PDF 時：`pdf_file` 標記為已刪除並寫稽核事件，交易完成後用它的物件編號呼叫 `release_stored_pdf`（和「不加入」同一個函式）；已經從它擷取並分享的衍生事實保留，來源顯示「上傳者已刪除檔案」（FR-7）。v1 不擷取全文，所以實際上沒有這種衍生事實，但欄位先留好。

## 理由

1. **經過 API，檢查才做得完整。** 大小、檔頭、配額、放哪個路徑，都在自己的程式裡，一邊收一邊擋；不合格的檔案不會整份先進到儲存空間。
2. **同一個網域**，CSP 維持 `connect-src 'self'`。
3. **4 個人、一次最多 100 份**，流量經過主機不是問題；用串流的方式，API 的記憶體不會隨檔案大小增加。
4. **辨認只需要 DOI 與標題**，前幾頁的文字就夠；期刊論文的 DOI 幾乎都印在第一頁。不需要為此跑 GROBID。
5. **三道防線各自獨立。** 「一定會刪」是授權上的承諾，不能只靠一段程式永遠不出錯。

## 取捨

- **上傳的流量經過 1 GB 主機。** 100 份 × 平均幾 MB，可以接受；NFR-19「100 份 30 分鐘內辨認完」的量測在這個設計下做。
- **記憶體的數字還沒有實測。** 子行程上限 200 MB 加上 worker 本身，要塞進 400 MB。做上傳的那個 Story 要用幾份大的、圖多的 PDF 實測，驗收條件是：worker 本身在閒置時用多少、加上 200 MB 之後離 400 MB 還有多少；不夠就調低子行程上限，並把量到的數字寫回這份 ADR。
- **排隊太久的檔案會過期。** `pdf` 佇列一次只跑一個，一次上傳 100 份時，排在後面的檔案如果滿 60 分鐘還沒輪到，暫存檔會先被 `purge-tmp` 清掉，變成 `expired`，使用者要重新上傳那幾份。照每份幾秒估計不會發生；外部來源很慢或 worker 停了一陣子時才會。這是為了守住「一小時內清掉」的承諾而接受的。
- **勾了下載聲明的 PDF 幾乎不受這些影響**：它們收完就搬到 `pdf/`，不會被清。唯一的例外是 API 在「寫好紀錄」與「搬過去」之間當掉、而且辨認工作過了 60 分鐘才輪到它，這時暫存的那一份已經被清掉，項目變成 `expired`。
- **配額快滿時，有兩種新版本還是換不了。** 認得出是哪一篇之前，系統不知道它是不是取代。(1) 讀檔失敗的：要變成 `failed`（算配額）時空間不夠，會直接變成 `over_quota`，沒有「重試」。(2) 對不到論文、要手填書目的：一樣在變成 `needs_manual` 時被擋。沒有 DOI、靠標題找到候選的不受影響（等確認的期間還沒算配額）。
- **儲存空間實際佔用最多會到「配額 ＋ 寬限」**，也就是每人多 50 MB；另外等確認取代的最多留 7 天。
- **同一份 PDF 傳兩次會短暫存兩份**（Kevin 2026-11-13 決定一筆紀錄一個檔的代價）：第二份在判定成 `duplicate` 之後刪掉，這之前它算在收檔檢查的「收進來還沒算的」裡。
- **當掉留下的 PDF 不會馬上清**：剛進來的物件要放滿 60 分鐘才會被補刪，最慢 75 分鐘。這是為了不誤刪剛收進來的 PDF 而接受的；這段時間沒有人開得到它，也不算配額。
- **`purge-tmp` 每 15 分鐘多列一次 `pdf/` 與沒完成的分段上傳。** 4 個人、每人最多 1.5 GB，物件只有幾千個，列一次的費用與時間可以忽略；之後物件變多時改成一天一次。
- **用規則找 DOI 會有找不到的**（掃描的舊論文、DOI 在頁尾被切斷）。這些落到「用標題比對」與「手填」，使用者要多按幾下。之後有 GROBID 時，讀 PDF 這個動作才升級成 port、多一個實作（現在是函式注入，ADR-0001）；流程不用改。
- **掃描成圖片的 PDF 讀不出文字**，直接進手填流程。v1 不做文字辨識（OCR）。
- **第 3 道防線是雲端設定**，不在程式裡，要 Kevin 在 R2 後台設一次。部署文件列為上線前的檢查項目。
- 本機開發用 RustFS 當物件儲存（MinIO 的社群版已經停止維護，映像也下架了）；單元測試用 moto 模擬。

## 和 PRD 不一致的地方

- PRD FR-49 的原文是「暫存檔設存活時間，排程清掉超過 1 小時的暫存檔」，§12 寫「暫存檔存活 1 小時」（都標了 `[ASSUMPTION]`，是設定值）。這裡是**滿 60 分鐘才刪、每 15 分鐘掃一次，所以一個檔案最久會留 75 分鐘**（Kevin 2026-11-13 決定）。照字面，「清掉超過 1 小時的」做到了；和「存活 1 小時」比，最壞情況多 15 分鐘，這裡列為偏離。
  - 第一版寫「每小時掃一次、刪超過一小時的」，Codex 審查指出最壞情況接近兩小時。
  - 沒有改成「45 分鐘就刪」來守住一小時，是因為畫面文字寫「超過一小時已刪除」，提早刪會讓畫面和實際對不上，使用者在第 50 分鐘按重試卻發現檔案沒了。
  - FR-49 的驗收測試（中斷後過一小時跑清理，檔案不在）照樣會過；偏離的只有「兩次清理之間最多多等 15 分鐘」。
  - 正常情況不受影響：檔案在讀出資料後幾秒內就刪了，這條只管當掉與讀檔失敗的檔案。

## 名詞

- **物件儲存**：專門放檔案的雲端服務，用「路徑＋檔名」存取；本專案用 Cloudflare R2。
- **串流**：資料一邊收一邊處理，不用等全部收完；所以不管檔案多大，佔用的記憶體都差不多。
- **SHA-256**：把檔案內容算成一串固定長度的指紋；內容一樣指紋就一樣，用來判斷是不是同一個檔案。這裡只拿來比內容，不拿來當存放位置。
- **子行程**：主程式另外開出來的一個獨立小程式；它當掉或用太多記憶體時可以單獨結束掉，不影響主程式。
- **檔頭**：檔案最開頭的幾個位元組；PDF 一定以 `%PDF-` 開頭，檢查它比看副檔名可靠。
- **分段上傳**：把大檔案切成幾段傳到物件儲存、最後再合起來的做法；傳到一半中斷時，已經傳的那幾段會留在儲存空間，要另外清掉。
- **佔著／放掉**：一筆紀錄還需要它那一份保存的 PDF 叫佔著；不需要了叫放掉。一份 PDF 只屬於一個上傳項目（對到論文後交給 `pdf_file`），沒有紀錄還要它的才會真的被刪。
- **物件編號**：保存的 PDF 在儲存空間裡的名字，就是當初那個上傳項目的 ID。
- **補刪**：紀錄已經改好、PDF 卻因為程式當掉沒刪到時，由定時的清理工作事後補上。
- **上鎖**：請資料庫幫忙排隊的做法；兩段程式要動同一個東西時，後到的等前一個做完。
- **`pagehide`**：瀏覽器在頁面要被關掉或換掉時通知網頁的事件。
- **上一頁快取**：按上一頁時，瀏覽器直接把離開時的整個畫面拿回來用，不重新載入。
- **presigned URL（預先簽名的網址）**：儲存服務發的限時通行證網址，拿到的人可以直接上傳或下載一個檔案。
- **中繼資料**：檔案自己帶的描述資訊（標題、作者等），不是內文。
