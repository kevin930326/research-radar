# ADR-0061：示範站匯出的檔案切法、目錄結構與白名單模型

- 狀態：提議（Story 3.7，等 Kevin 確認）
- 日期：2026-11-25（同日第 1、2、3 輪審查後修正；第 4 輪照 Kevin 2026-11-25 晚的決定補 `demo_eligible`、已知限制；2026-11-27 補已知限制第 5～8 條；同日 epic-3m PR A 改程式修掉第 5、8 條）
- 對應：Story 3.7；ADR-0007（示範站匯出與寫出前的自我檢查）、ADR-0010、ADR-0052；AD-14、AD-20、AD-21；FR-7
- 補 ADR-0007／AD-20 沒寫到的細節。和它們字面不一樣的地方（自我檢查用系統身分讀成員 email、CLI 不經佇列、
  幾項留到之後）在「與 ADR-0007／AD-20 不一樣的地方」逐條列出，等 Kevin 確認。

## 背景

示範站是公開的靜態網站，讀的是匯出好的 JSON 檔。ADR-0007／AD-20 定了大方向（manifest 最後換、白名單模型、
寫出前自我檢查、只放 `counted_paper`、完整內容只給 `demo_full_paper`），但沒定：檔案怎麼切、目錄長什麼樣、
每個檔的欄位怎麼定、兩個行程同時匯出時怎麼辦、哪些檔留到之後。這份把 Story 3.7 做的選擇記下來。

## 考慮過的選項

### 一、目錄結構

| | 做法 | 選了會怎樣 |
|---|---|---|
| A | 每次匯出一個新目錄 `preview/<匯出編號>/`，`preview/manifest.json` 最後用 `os.replace` 換 | 讀者永遠看到完整的一批；舊目錄留著，要另外清 |
| B | 直接覆寫同一個目錄 | 寫到一半時讀者會看到新舊混在一起 |

### 二、論文清單的檔

| | 做法 | 選了會怎樣 |
|---|---|---|
| A | 一個「欄式」索引 `papers-index.json`（每一欄一個陣列）＋ `titles.json` ＋ 每 200 篇一個分片 `papers/NNN.json` | 篩選只要載索引；欄名不重複出現，檔小；點進論文才載分片 |
| B | 一個大檔放全部論文 | 首頁就要載全部摘要與 AI 產出，篇數多時太大 |
| C | 一篇一個檔 | 檔數多，manifest 很長 |

### 三、欄位怎麼定

| | 做法 | 選了會怎樣 |
|---|---|---|
| A | 論文的欄位直接組合成員版的共用模型（`PaperBiblio`、`ClassificationBlock` 等） | 兩邊一致；但成員版多出來的欄位（修正人數、意見不一、回報的欄位、`in_scope`、`origin`、`is_retracted`、內部產出 ID）跟著出去，不符合 ADR-0007 第 4 點的清單 |
| B | 照 ADR-0007 第 4 點逐欄列出示範站自己的模型（`DemoBiblio`、`DemoClassificationBlock` 等）；本身整個在清單裡的形狀（快照、來歷、顯示名稱、原文摘要、全文連結、構面與假設）才共用成員版的模型 | 清單外的欄位預設出不去；要加欄位得改模型，改動會出現在 PR |

### 四、兩個行程同時匯出、做到一半中斷

| | 做法 | 選了會怎樣 |
|---|---|---|
| A | 只靠部分唯一索引（同一個快照只能有一筆排隊或執行中） | 不同快照的兩次匯出可以同時跑，舊的可能把 manifest 蓋回舊的；sweep 補排時兩個行程可能同時做同一筆 |
| B | 部分唯一索引＋接手代號＋發佈鎖＋換 manifest 前比新舊＋重跑時補記成功 | 多一欄、多一把鎖；正常連線下上面幾種情況都擋得住，但資料庫連線在檢查後斷掉時，鎖跟著放掉，舊行程的檔案操作不會停 |
| C | B ＋ `preview/` 資料夾本身的檔案鎖（`fcntl.flock`）包住寫目錄到換 manifest，拿到鎖後再確認接手代號、鎖內換之前再比一次新舊 | 資料庫斷線也不會放掉檔案鎖：**同一台主機、同一個資料夾**的兩個行程，檔案操作一次一個；不同主機或不同的檔案系統時檔案鎖互不相干，只剩資料庫的鎖與接手代號 |

### 五、匯出寫到哪裡

| | 做法 | 選了會怎樣 |
|---|---|---|
| A | CLI 用 `--output-dir`，worker 用 `RADAR_DEMO_EXPORT_DIR` | CLI 中斷後由 worker 補做時，可能寫到另一個資料夾 |
| B | 記在 `demo_export` 那一列 | CLI 與 worker 在不同容器時，同一個路徑可能指到不同地方 |
| C | 兩邊都只看 `RADAR_DEMO_EXPORT_DIR` | 只有一個來源；CLI 要先在環境變數設好 |

## 決定

- 目錄選一 A；匯出編號＝`<快照編號>-<這個快照第幾次>`；`RADAR_DEMO_PUBLISH` 預設關，只寫 `preview/`，這一輪沒有打開的路。
- 檔案選二 A：`manifest.json`（快照、匯出編號、匯出時間、每個檔的路徑與 sha256 與大小、`summary`、`client_config`）、
  `<匯出編號>/taxonomy.json`、`papers-index.json`、`titles.json`、`papers/NNN.json`。論文分兩層：`DemoPaperBiblio`
  （每一篇 `counted_paper`）與 `DemoPaperFull`（只有示範站有完整內容的論文才有）。manifest 列的路徑只能是
  `<自己的匯出編號>/` 底下認得的資料檔（不會有 `..`），而且要是完整的一批：分類表、索引、標題都在，分片從 `000`
  起連號、個數照 `summary.paper_count` 算（每 200 篇一個；0 篇沒有分片）。不齊全的 manifest 不符合模型。
- 欄位選三 B。`demo-openapi.json` 由 `radar export-demo-schema` 從這些模型產生，repo 放一份，測試比對兩者一致。
  示範站輸出的欄位：
  - 書目：論文 ID、標題、作者、年份、期刊代號與 ISSN-L、卷期頁碼、DOI 與連結、OpenAlex ID 與連結、被引用次數。
  - 第一層的是或否：有沒有摘要（`has_abstract`）、有沒有完整內容（`has_full_content`）、示範站可用
    （`demo_eligible`，第 4 輪加，見下一條）、本週新增（`is_new_this_week`）。
  - 分類：主題與方法的代號、各自是否已核對；分類的來歷（模型、產生時間、`input_kind`＝是否只根據標題、是否已核對）。
  - 完整內容層：原文摘要與來源、中文重點四欄、研究模型（研究情境、樣本數、限制、未來研究、構面與假設），
    後兩者帶狀態與來歷。
  - 不輸出：修正人數、意見不一、回報的欄位、誰修正的與理由、`in_scope`、`origin`、`is_retracted`、中文重點與研究模型的內部 ID。
- **`demo_eligible`（第 4 輪加，Kevin 2026-11-25 選 A）**：
  - 為什麼加：示範站論文頁有三種版本（EXPERIENCE 畫面 8）：有完整內容、「授權允許但沒有摘要」、「只有書目」。
    原本第一層只有 `has_abstract` 與 `has_full_content`，`demo_full_paper` 要求有摘要，所以「授權允許但沒有摘要」
    和「授權不允許又沒有摘要」兩種的值一模一樣，前端分不出來（`docs/runs/epic-3i/reviews/3.9-decisions.md`）。
  - 值從哪來：資料庫存的 `paper.demo_eligible`（寫入時由 `policy.is_demo_eligible` 判，含授權、出版社、期刊排除
    清單；view `demo_full_paper` 用的就是這一欄），而且匯出時出版社與期刊直接對排除清單也沒有對上
    （`domain/demo_export.demo_eligible_for`）。「不給完整內容」那一道用的是同一次判定的結果，所以兩者不會矛盾；
    匯出這邊不另外判授權。模型檢查：`has_full_content` 是 true 時 `demo_eligible` 一定是 true。
  - 為什麼公開安全：它只是一個是或否，不帶授權字串、出版社 ID 或名稱、比對到排除清單的哪一項；授權本身在 OpenAlex
    上就是公開的書目資料，訪客自己也查得到。它不讓任何完整內容出去：完整內容照舊只給 `demo_full_paper` 裡、
    排除清單沒對上的論文。排除清單裡的出版社或期刊一律是 false（不會說 IEEE 的論文「授權允許轉載」）。
  - 自我檢查第 7 項：另外一句讀資料庫存的 `demo_eligible` 與出版社欄位、用同一個函式算出可以是 true 的名單；
    分片檔裡標成 true 的論文不在名單裡（或在排除清單裡）、或不是布林，就失敗。直接看原始 JSON，不靠模型。
  - `papers-index.json` 不加這一欄：論文清單的篩選不用它，只有論文頁要（只加這一個欄位）。
- 分類標籤只在摘要來源是 OpenAlex 時給（`DEMO_LABEL_ABSTRACT_SOURCES`）；只看標題的分類照常給。
- **完整內容再擋一次**：匯出時直接用 `config/demo_publishers.yaml` 的排除清單（出版社 ID、名稱、期刊 ISSN-L，和
  `is_demo_eligible` 同一個比對規則）判每一篇，對上的就算還在 view `demo_full_paper` 裡（舊的 `demo_eligible`
  還是 true、還沒 `radar reparse`），也不給完整內容，並記一筆警告。
- 所有讀取（含自我檢查要的 `demo_full_paper` 名單、出版社欄位、成員 email）在同一個 REPEATABLE READ 唯讀交易裡；
  匯出的資料只用 `PublicViewer` 讀。
- 自我檢查（寫 manifest 之前，ADR-0007 第 1、2、3 項與第 6 項的分片與索引部分）：
  1. 每個檔過白名單模型。
  2. 不在 `demo_full_paper` 的論文沒有完整內容（直接看原始 JSON，不靠模型）；`full.paper_id` 要是那一篇自己的。
  3. 找不到金絲雀字串與任何成員 email：兩邊先做 Unicode NFKC 正規化再不分大小寫比，原文、JSON 解碼後的
     每個字串、百分比編碼還原後的寫法都找。
  6. 另外直接讀出版社欄位，排除清單裡的出版社或期刊的論文沒有完整內容。
  7. 分片檔裡 `demo_eligible` 是 true 的論文，另外算的判定也要是可以（見上面 `demo_eligible` 一條）。
  沒過就一個檔都不寫、manifest 不換。失敗原因只印檔名、已知的欄位名稱與陣列位置、錯誤代碼、看得懂的論文 ID；
  多出來的鍵名與看不懂的 ID 不印。
- 並行與中斷選四 C（第 1 輪是 B，第 2 輪審查補檔案鎖，第 3 輪把鎖改成鎖 `preview/` 本身、補拿鎖後的確認）：
  - `demo_export` 多一欄 `run_token`：接手（`queued`，或 `running` 超過 6 小時）時換新的代號；寫檔前與記結果時
    都要拿著同一個代號，被別的行程接手後舊的那個什麼都不寫、也不改狀態。
  - 寫檔與換 manifest 在一個短交易裡，先拿資料庫的發佈鎖（CLI 與 worker 共用的 advisory lock），確認還是自己
    接手的；再拿 `preview/` 這個資料夾本身的檔案鎖（`fcntl.flock` 鎖另外打開的目錄 fd，**不建鎖檔**，匯出在
    `preview/` 以外不建立任何檔；資料庫斷線不會放掉它）。在檔案鎖裡看現在的 manifest 沒有指向比這次新的匯出
    （比快照編號再比序號）才寫目錄，換 manifest 之前在檔案鎖裡再比一次；比較新的就記成 `superseded`、不蓋回去。
    記成功也在同一個資料庫交易。
  - 拿到檔案鎖之後、寫目錄前與換 manifest 前，各再確認一次接手代號（同一條連線、同一個交易，順便鎖住那一列）：
    等檔案鎖的期間資料庫連線斷掉、被別的行程接手時，這一句不是失敗就是回「不是自己的」，manifest 不換。剩下的
    空窗只有「確認完到下一個檔案動作」這一下（見「已知限制」第 1 條）。
  - **寫好匯出目錄之後、換 manifest 之前停下就嘗試刪掉那個目錄**（第 4 輪，修 Opus 第 3 輪確認的中；第 5 輪補）：
    範圍從匯出目錄改名那一下起（含改名之後 fsync `preview/` 失敗），到換 manifest 為止；被接手、換之前的檢查失敗
    （較新的 manifest、`preview/` 被搬走、確認接手代號那一句丟錯）、換 manifest 失敗、中斷，都在還拿著檔案鎖的
    時候嘗試刪掉這次寫的 `preview/<匯出編號>/`（manifest 沒指向它，沒有讀者讀得到）。所以被接手時這個行程正常
    會留下「什麼都沒有」，之後接手的行程用同一個匯出編號重做不會碰到 `output_exists`。
    - **只刪這次寫的那一個**（第 5 輪，修 Codex 第 4 次複查新高 2）：改名前記下暫存目錄的 `st_dev`／`st_ino`（改名
      不變）；刪之前相對於 `preview/` 的目錄 fd 打開同名目錄（不跟符號連結）比對，不一樣（被搬走後換成別的目錄）就
      不刪、記警告；一樣才相對於它的目錄 fd 刪掉裡面的東西，最後刪掉這個空目錄（名字若在這一下被換成別的非空目錄，
      刪不掉；換成空目錄時刪掉的是那個空目錄）。
    - **換 manifest 的那一下停下不刪**（第 5 輪，修 Codex 第 4 次複查新高 1、Opus 新高 1）：開始換 manifest 的名之後
      才停下（例如換名的系統呼叫剛完成、還沒記下「已發佈」就收到 Ctrl-C），清理前先重讀 manifest：已經指向這一次就
      補記「已發佈」、不刪目錄，照下面「manifest 一換好就算已發佈」處理。
    - **換名那一下停下、又讀不出 manifest 時當成已發佈**（2026-11-27 epic-3m PR A，Kevin 2026-11-26 決定，修掉
      「已知限制」第 5 條）：開始換 manifest 的名之後才停下，清理重讀 manifest 出錯（不知道換了沒有、讀者看不看得到）
      時，一樣補記「已發佈」、目錄留著、記一筆錯誤日誌，照下面「manifest 一換好就算已發佈」處理：不記失敗、留在
      `running`，之後記失敗前也不再靠重讀 manifest（或 `preview/` 還在不在原位）決定。補排時 manifest 若真的指向
      這一次就補記成功；其實沒換的，補排照一般流程重做同一個匯出編號，通常會碰到留著的目錄、記成 `output_exists`
      （最新的快照已經變了時先記 `snapshot_changed`；都不會一直停在 `running`）。「開始換名」的記號設好到換名的系統
      呼叫之間那一下停下也分不出來，一樣當成已發佈（其實沒換，照上面補排）。確定 manifest 沒有指向這一次時（還沒
      開始換名，例如寫暫存 manifest 或換之前的檢查就失敗；或重讀確認沒換），照舊依身分刪這次寫的目錄、記失敗。
      補排時仍讀不出 manifest、或補記時 fsync 一直失敗的情況，走的是既有的補記路徑，這一次沒有改（列給 Kevin）。
    - 刪不掉或不是這次寫的而留著時記一筆警告日誌，寫明「同一個匯出編號重做會碰到 output_exists」（或「不是這次寫的，
      沒有刪」），原本的例外照樣往上丟。被接手時的日誌照實寫匯出目錄的下場：「這次還沒寫匯出目錄」「這次寫好的匯出
      目錄已刪掉」「這次寫好的匯出目錄沒有刪掉（見前一筆警告）」或「這次寫過匯出目錄，但目錄已經不在原位（被搬走或
      刪掉），沒有刪」。最後一種是 2026-11-27 epic-3m PR A 補的（修掉「已知限制」第 8 條）：改名成功後記下「已改名」，
      清理時這個名字底下找不到目錄、又記過「已改名」，就是寫過、但已經不在原位（分不出搬走還是刪掉）；沒記過才是改名
      沒成功。改名成功到記下之間那一下停下、目錄又剛好不在時，仍會寫成「這次還沒寫匯出目錄」（只差日誌）。
  - 檔案鎖的前提：`flock` 只在兩個行程用**同一個系統核心、同一個本機檔案系統上的同一個資料夾**時互斥。所以
    CLI 與 worker 要在同一台主機、掛同一個資料夾（同一個 volume）；Kevin 手動跑 `radar export-demo` 要在
    worker 容器裡跑（`docker compose exec worker radar export-demo`），不要在 Mac 主機上直接跑、也不要用
    `docker compose run` 另起一個容器（Docker Desktop 的容器和 Mac 主機是不同的核心，鎖互不相干）。不符合這個
    前提時，只剩資料庫的發佈鎖與接手代號擋（正常連線下仍擋得住，資料庫斷線的那一下擋不住）。
  - 檔案鎖不建鎖檔，所以沒有鎖檔權限的問題；換一個使用者跑時，要能讀 `preview/` 才鎖得到、能寫才寫得進去，
    做不到就是一般的 `PermissionError`（記成 `error`）。正式映像的使用者是 uid 10001，CLI 與 worker 用同一個。
  - 等檔案鎖大約 5 分鐘（`DEMO_OUTPUT_LOCK_TIMEOUT_SECONDS`，每 0.05 秒試一次）：拿著的一方只在寫目錄到換
    manifest 那幾秒拿著，等這麼久代表它卡住了；超過就記成 `output_busy`、什麼都不寫（等的期間拿著資料庫交易與
    發佈鎖，不無限等）。**5 分鐘不是硬上限**：程式每一輪先試拿鎖、拿不到才看有沒有超過期限，所以最後一次試的時間
    可能剛好在期限上或稍微超過（多出最多一次睡眠，約 0.05 秒，加上行程被排程延後的時間）；那一次拿到了就照常
    發佈，不會因為「已經超過 5 分鐘」而放棄。
  - 範例產生器（`tests/demo_preview.py`）鎖的是 `web/e2e/fixtures/` 這個資料夾，和匯出鎖 `preview/` 是**不同的
    兩把鎖**（同一個機制）：同時跑兩次範例產生器時一次一個；它裡面的匯出寫的是自己的暫存資料夾，鎖的是那裡的
    `preview/`。範例產生器的搬移與清理也相對於打開的目錄 fd；新範例搬不進去、舊範例也搬不回去時，暫存資料夾
    （裡面有舊範例的備份）留著不刪，印出位置。第 4 輪補：不管是哪一種錯誤或中斷（包含還原舊範例途中按 Ctrl-C 的
    `KeyboardInterrupt`），只要備份還在、範例位置卻是空的，暫存資料夾就留著，並印出備份位置。
  - `preview/` 在途中被搬走或換掉：寫目錄前、換 manifest 前各比一次打開的目錄 fd 和 `<輸出資料夾>/preview`
    是不是同一個資料夾（`st_dev`／`st_ino`），不一樣就記成 `output_unsafe`、不換 manifest。換完之後也比一次，
    但**這時已經算發佈了**（下一條），不一樣只是不回報成功、記一筆「新的 manifest 寫進了被搬走的那個資料夾」的
    錯誤日誌，那一筆留在 `running` 等補記。補記成功前也比一次。這個比對用的是 `<輸出資料夾>/preview` 這個路徑：
    只有最後一層 `preview` 不跟符號連結，輸出資料夾本身與它上面的各層照一般路徑解析（可以是符號連結）。
  - 現有的 manifest 讀不懂（JSON 壞掉、不符合模型、別的版本寫的）時拒絕（`manifest_unreadable`）、什麼都不寫：
    不知道它指向的是不是比較新的匯出，不能當成沒有 manifest。要人工確認後移走再匯出。
  - 資料檔逐個 fsync、各層目錄 fsync 後才改名；改名後 fsync `preview/`，才寫 manifest 暫存檔（fsync）、換名，
    換完再 fsync `preview/`。
  - **manifest 一換好就算已發佈**（第 4 輪，修 Codex 第 3 次複查新高 1）：換名那一下成功，就在這個行程裡記下
    「已發佈」（`_Progress.switched`，不再等換完的位置檢查通過）。之後的任何步驟失敗（換完的位置檢查、fsync、
    記成功、commit），或收到中斷，失敗處理看到這個記號就**不記失敗**：例外是一般錯誤時回報**已發佈、狀態待補記**
    （`DemoExportPublishedUnrecordedError`；CLI 印「已發佈……不用重跑」、退出碼 1），中斷照原樣往上丟；那一筆
    都留在 `running`。失敗處理不再靠重新讀路徑判斷（位置檢查一直讀不到路徑時也不會誤記成沒發佈過）；sweep 6 小時後補排，接手時發現 manifest 已經指向這一次、檔案雜湊都對，先再 fsync 一次
    `preview/` 才補記成功、不重寫。manifest 指向這一次、檔案卻不完整時補記不了：重跑會碰到目錄已經存在，記成
    `output_exists`（不會一直停在 `running`）。換完時 `preview/` 已經被搬走的，搬回來之後補排時照樣補記成功；
    沒搬回來時，補排會在新的 `preview/` 重新匯出同一個匯出編號。換名成功、還沒記下記號就停下的那一下，由上面的
    清理重讀 manifest 補記（第 5 輪）。
  - 已發佈、還沒補記，之後又被更新的一批取代（manifest 已經指向比它新的匯出）：接手時一看到就記成 `superseded`，
    不讀資料、不寫檔（不會因為快照變了記成 `snapshot_changed`，也不會一直停在 `running`）。不記成功：它自己的
    manifest 已經被換掉，檔案無從逐一核對；它之前有沒有被讀者看到過，這張表不記（日誌有「已發佈、狀態待補記」
    那一筆）。它的 `<匯出編號>/` 目錄留給之後的清理。
  - 輸出位置的讀寫一律相對於打開的目錄 fd（`O_DIRECTORY`、`O_NOFOLLOW`、`dir_fd`）。不跟符號連結的範圍是
    **從 `preview/` 起往下**：`preview`、它底下的匯出目錄與資料檔、`manifest.json` 是符號連結時拒絕
    （`output_unsafe`）；打開之後有人把 `preview` 換成符號連結，不會沿著連結寫到別處（位置比對也會擋下，不寫進
    搬走的資料夾；比對完到下一個檔案動作之間的例外見「已知限制」第 3 條）。**輸出資料夾本身（`RADAR_DEMO_EXPORT_DIR`）與它上面的各層照一般路徑打開，可以是符號連結**
    （正常的掛載設定）。
  - 行程被中斷（Ctrl-C 這類變成例外的中斷）時：**換 manifest 之前**把那一筆記成 `interrupted`，下一次
    `radar export-demo` 不會被擋；**換 manifest 之後**（含換名那一下，見上面）算已發佈，不記失敗、留在 `running`
    待補記（這段期間再跑 `radar export-demo` 會被擋，6 小時後由 sweep 補記）。SIGTERM 不會變成例外：被系統結束
    的那一筆停在 `running`，6 小時後補排。
- 匯出位置選五 C：`radar export-demo` 與 worker 都只看 `RADAR_DEMO_EXPORT_DIR`；沒設時 CLI 不連資料庫、退出碼 1，
  worker 記成 `no_output_dir`。worker 讀設定檔失敗時那一筆記成 `config_error`（不會被 sweep 一直補排）。
- 卡住的時間：CLI 建好列、還沒開始就中斷（停在 `queued`）的，1 小時後由 sweep 交給 worker；做到一半行程不在了
  （停在 `running`、又沒被記成失敗，例如被系統直接殺掉）的，6 小時後補排。這段時間內再跑 `radar export-demo`
  會被擋，訊息會說明多久後由 worker 接手。
- AI 預算不讀：示範站把「預算延後」當成「排隊等批次」顯示（待 Kevin 確認，見下）。
- `radar export-demo` 在指令自己的行程裡做（不經佇列）；工作佇列也註冊了 `run_demo_export`（現在只有 sweep 排入）。
- 示範站論文清單一頁 50 篇放在 manifest 的 `client_config`（`DemoClientConfig`：時區、`paper_list_page_size`＝50），
  前端不另外寫一份（AD-21）；成員版的 `ClientConfig` 不變。示範站沒有文獻庫，不帶它的篇數（待 Kevin 事後確認）。
- 例外怎麼記：
  - 設定錯誤（`ConfigError`，讀設定檔或環境變數時）：訊息照設計只有環境變數或設定檔的名稱與原因、不含設定值。
    CLI 印出每一條原因；worker 先把那一筆記成 `config_error`，再把 `ConfigError` 原樣往上丟（和其他工作一樣）。
  - 進了匯出服務之後的其他例外：只記類別名稱，例外訊息（可能帶主機、帳號或被擋的內容）不印、不串（CLI 印類別名稱；
    worker 丟只帶類別名稱的 `DemoExportJobError`）。

## 已知限制（Kevin 2026-11-25 決定接受，這一輪不改程式）

1. **最後一次確認接手權之後資料庫才斷線**
   - 什麼情況：舊行程在檔案鎖裡確認完接手代號（寫目錄前或換 manifest 前那一次），接著資料庫連線才斷；資料庫那邊
     放掉了列鎖與發佈鎖，另一個行程在 6 小時的卡住期限之後接手同一筆。舊行程沒有再問資料庫，照樣做完接下來的
     那一個檔案動作（寫目錄或換 manifest）。
   - 最壞結果：兩個行程用同一個匯出編號各自發佈一次，或新行程碰到 `output_exists` 記成失敗、要人工再跑一次。
     同一個快照編號**不保證兩次組出的內容相同**（兩次之間分類、摘要等可能變了），所以兩次發佈的資料可能不一樣。
     檔案鎖不共用時（不在同一台主機或同一個資料夾，見上面「檔案鎖的前提」），舊行程在最後一次確認後斷線，換 manifest
     時新行程可能已經發佈了更新的一批，舊行程仍可能把 manifest 蓋回較舊的那一批，直到下一次匯出才恢復。不會公開
     不該公開的東西：兩邊寫的都是通過自我檢查的檔。同一台主機同一個資料夾時檔案鎖還在，兩邊的檔案動作仍是一次
     一個，換 manifest 前在鎖裡比新舊，不會蓋回較舊的。
   - 為什麼現在不修：要完全擋住得在每個檔案動作跟資料庫做成同一個不可分割的動作（兩階段提交這類），對 1 人維護、
     一週匯出一次的示範站太重；空窗只有「確認完到下一個檔案動作」那一下，還要碰上斷線又超過 6 小時被接手。
2. **被更新的一批取代的舊匯出記成 `failed/superseded`，看不出它曾經發佈過**
   - 什麼情況：一次匯出換好 manifest（讀者可能看過）、但沒記上成功；它補記之前，更新的一批已經發佈。補排時記成
     `superseded`。
   - 最壞結果：`demo_export` 表上這一次是失敗，查歷史時會以為它從沒上線過；要看日誌的「已發佈、狀態待補記」那一筆
     才知道。行程若在換好 manifest 之後、寫日誌之前就被系統結束，連那一筆日誌都沒有，無從追查。讀者看到的資料不受
     影響（現在是更新的那一批）。
   - 為什麼現在不修：要在表上加一個「曾經發佈」的狀態或欄位（遷移、sweep、CLI 訊息都要跟著改），而這張表目前只
     用來排程與擋重複，沒有任何畫面或決定讀「曾經發佈過」。
3. **位置比對通過之後、實際寫入之前，`preview/` 剛好被搬走**
   - 什麼情況：寫目錄前（或換 manifest 前）比過 `preview/` 還在原位，下一個動作執行前它被搬走。程式透過已打開的
     目錄 fd，把這一次寫進被搬走的那個資料夾。
   - 最壞結果：寫目錄這一步：檔案寫進搬走的資料夾，下一次比對（換 manifest 前）會擋下，記 `output_unsafe`，並嘗試
     刪掉寫好的目錄（刪的是搬走的資料夾裡的那一個；刪不掉時留下，記警告）。這是上面「不寫進搬走的資料夾」的例外。
     換 manifest 這一步：新的 manifest 在搬走的資料夾裡，讀者看不到；照「manifest 一換好就算已發佈」
     留在 `running`，換完的比對會報錯並記日誌。都不會寫到搬走的資料夾以外（不跟符號連結）。
   - 為什麼現在不修：比對與寫入之間一定有一小段時間，作業系統沒有「確認路徑還指著這個目錄並同時寫入」的單一動作；
     `preview/` 只有部署的人會動，正常運作不會在匯出的那幾秒搬它。
4. **範例產生器執行途中 `web/e2e/fixtures/` 被換成另一個目錄，驗證的和搬進去的可能不是同一個**
   - 什麼情況：`tests/demo_preview.py` 匯出與 `check_complete` 用路徑（`FIXTURES / work / …`）找暫存資料夾，
     `replace_target` 用一開始打開的 fixtures 目錄 fd 搬。途中有人把 `fixtures/` 換成另一個真實目錄時，兩邊可能
     各自找到不同的 `<work>/out/preview`。
   - 最壞結果：搬進範例位置的，是一份沒有經過這次完整性檢查的資料夾內容（仍是範例產生器自己建的暫存資料夾裡的
     東西）。目錄 fd 固定的是一開始打開的那個 `fixtures/`：它若途中被搬到 repo 外，之後的相對搬移也發生在那裡，
     所以搬移的位置不一定在 repo 裡。範例只給前端測試用，之後 `test_demo_preview_fixture.py` 等測試會逐檔檢查它。
   - 為什麼現在不修：範例產生器是開發者在自己的電腦上手動跑的工具、不在正式環境；要全部改成目錄 fd 得改寫匯出
     服務的輸出入口（接受目錄 fd 而不是路徑），範圍比這個限制大。

下面第 5～8 條是第 5 次複查（2026-11-25）之後還剩的，Kevin 2026-11-26 決定當成已知限制、先合併（PR #130）。
第 5、8 條在 2026-11-27 已改程式（epic-3m PR A），第 6、7 條不改。

5. **換 manifest 之後讀不回來，這一次可能記成失敗**（**2026-11-27 已改程式**，見「決定」裡「換名那一下停下、
   又讀不出 manifest 時當成已發佈」）
   - 發生過什麼：PR #130 的版本在換名那一下前後被中斷、清理與記失敗前兩次都讀不出 manifest（或 `preview/` 不在
     原位）時，會把 manifest 其實已經換成這一次的匯出記成 `interrupted`／`error`，和「換 manifest 之後算已發佈」
     不一致。現在不知道換了沒有就當成已發佈、留在 `running` 讓補排處理。
6. **改名後 fsync 失敗進清理，暫存目錄若在寫完前被換掉，可能刪到換進來的目錄**
   - 什麼情況：這次的暫存目錄還沒寫完，就有人把它換成另一個同名的目錄；接著改名成功、但 fsync `preview/` 失敗，
     進入清理。
   - 最壞結果：清理記下的身分是被換進來的那個目錄，所以把它當成「這次寫的」連內容一起刪掉。只會動
     `preview/` 底下那一個名字，不會刪到 `preview/` 以外。
   - 為什麼現在不修：要有人在匯出那幾秒動 `preview/` 底下的暫存目錄，同時磁碟又出 I/O 錯誤；`preview/` 只有
     部署的人會動。
7. **比對「是不是這次寫的目錄」只看裝置與 inode 編號，編號被重用時會誤認**
   - 什麼情況：有人把這次寫的目錄**刪掉**（不是搬走），再建一個同名、有內容的目錄，檔案系統剛好把同一個 inode
     編號給它（ext4 有可能；tmpfs、APFS 幾乎不會）。
   - 最壞結果：清理時比對通過，把新建的那個目錄裡的東西刪掉。
   - 為什麼現在不修：作業系統沒有不會重用的目錄身分可以比；要另外在目錄裡放一個這次才知道的記號檔再比，
     而這個情況要有人在匯出那幾秒刪掉又重建同名目錄。
8. **寫好的目錄被搬走時，被接手的日誌寫成「這次還沒寫匯出目錄」**（**2026-11-27 已改程式**，見「決定」裡
   「被接手時的日誌照實寫匯出目錄的下場」那一段的最後一種）
   - 發生過什麼：PR #130 的版本在目錄寫好、改名成功之後被人搬走（沒有換進別的目錄）、接著被接手時，日誌寫「這次
     還沒寫匯出目錄」；只有日誌不準，檔案與狀態表不受影響。現在寫「這次寫過匯出目錄，但目錄已經不在原位（被搬走或
     刪掉）」。

## 與 ADR-0007／AD-20 不一樣的地方（列給 Kevin 確認）

1. **自我檢查用系統身分讀成員 email**。AD-20 寫「只用 `PublicViewer` 經 repo 讀」、ADR-0007 第 1 點寫產生器
   「只能建立 `PublicViewer`」。但 ADR-0007 自我檢查第 3 項要比對所有成員的 email，訪客身分讀不到成員表（讀到的
   是空的、檢查等於沒做）。所以這是唯一的例外：只有 `list_member_emails` 用 `SystemViewer`、只讀一次、結果只拿來
   比對，不寫進任何檔或日誌；組檔的函式拿不到這個身分（測試鎖定：其他讀取一律是 `PublicViewer`）。
   替代做法：由入口先讀好 email 再傳進來（入口一樣要用系統身分，只是換個地方）；或不做 email 檢查（違反 ADR-0007）。
2. **`radar export-demo` 不經佇列**。AD-14 寫「手動的 `radar export-demo` 走同一步」（排入佇列）。這一版 CLI 在
   自己的行程裡做，但接手代號、發佈鎖、補記成功和 worker 是同一套，所以並行時一樣安全。
3. **留到之後的自我檢查**：第 4 項（每個數字用 `papers-index.json` 重算，含 `manifest.json` 的 `summary`）、
   第 5 項與第 6 項的 `relations.json`、`qa.json`、`home.json` 部分，等那幾個檔出現時一起做（Story 3.15 與
   Epic 9、10、13）。`summary` 這一輪已經輸出，但還沒有重算檢查。
4. **舊匯出目錄不自動刪**。ADR-0007 寫「照 `demo_export` 的紀錄保留最近 4 次」；這一輪只寫 `preview/`，先不刪。
   之後做清理時，manifest 正指向的那一次一律以檔案為準（不只看表）；失敗留下的目錄（例如換 manifest 前停下、刪不掉
   或讀不出 manifest 而留著的 `<匯出編號>/`，被系統殺掉時留下的暫存目錄）也一起清。
5. **開放取用版本的連結一律是 null**。ADR-0007 第 4 點列了它，但成員版也還沒有來源（資料庫沒存開放取用的位置，
   ADR-0048 列給 Kevin）；成員版有來源之後示範站照同一個來源填。
6. **預算延後顯示成排隊等批次**。ADR-0007 第 5 點說 AI 區塊照成員版同一個狀態輸出；示範站匯出不讀預算帳本（那要
   系統身分），所以本來是 `deferred_budget` 的區塊會是 `pending_batch`。兩個在畫面上都是「還在產生」。

## 取捨

- 示範站自己的模型和成員版會慢慢有差異；共用的形狀用測試鎖住同名同形（`test_shared_shapes_are_the_same_as_the_member_api`）。
- 舊匯出目錄不自動刪，磁碟會慢慢變多。
- 論文 ID 是資料庫裡真的 UUID，每次匯出都一樣；示範站看得到論文 ID（和成員版的網址一致，ADR-0007 第 4 點）。
- 寫檔時拿著資料庫的鎖與一條連線（幾秒）；同時有第二個匯出時它會等，等太久（超過連線的 `statement_timeout`）就記成失敗。
- 檔案鎖等大約 5 分鐘（不是硬上限，見決定）：拿著的一方真的卡住時，等的那一次記成 `output_busy`，要人工看是哪個行程卡住。拿著它的
  行程結束時自動放掉。
- 檔案鎖只在同一台主機、同一個資料夾有效（見決定）：Kevin 手動匯出要進 worker 容器跑，多一個操作上的規矩。
- 被更新的一批取代的舊匯出一律記 `superseded`，就算它曾經發佈過也不記成功（狀態表不記「曾經被看到過」；見「已知限制」第 2 條）。
- manifest 換好之後的錯誤一律當成已發佈、留在 `running`：真的沒被讀者看到（例如 `preview/` 剛好被搬走）時，要等 6 小時
  補排才會有結論。
- 示範站多公開一個「授權允許轉載」的是或否（`demo_eligible`）。
- manifest 讀不懂時要人工處理（移走或修好），匯出不會自己蓋過去。
