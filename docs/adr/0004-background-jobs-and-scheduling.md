# ADR-0004：背景工作用 Procrastinate，排程由外部 cron 呼叫 `radar` 指令

- 狀態：提議（等 Kevin 在 PR 確認）
- 日期：2026-11-12
- 對應：PRD FR-1、FR-9、FR-12、FR-14、FR-48、FR-49、NFR-5、NFR-11、NFR-18；addendum「待寫成 ADR 的架構決策」第 2、3 項；架構文件 AD-14、AD-15

## 背景

有四類事情不能在使用者等網頁回應時做：

- 每週更新（抓 14 本期刊、比對變動、送出 AI 處理）。
- Anthropic Batch API：送出後要等幾分鐘到 24 小時才有結果。
- 上傳的 PDF：一次最多 100 份，要逐一辨認。
- 維運：每晚備份、每 15 分鐘清一次暫存檔。

addendum 已經定了方向：不引入 Redis 與編排器；需要工作佇列時用 Procrastinate；GitHub Actions 只做 CI，排程放主機。這份 ADR 把剩下的細節定下來：排程由誰觸發、工作怎麼做到「重跑不出事」。

## 考慮過的選項

**工作佇列**

- **A. Procrastinate 3.11**：佇列就是 PostgreSQL 裡的幾張表，不用多一個服務；支援重試、鎖、非同步；收到停止訊號會等手上的工作做完（NFR-18）。對照官方文件查到三個限制，下面的決定都有對應：
  - worker 不是正常結束時（記憶體不足被強制關掉、主機重開），做到一半的工作會停在「執行中」，**不會自動重跑**；要自己定期找出這種卡住的工作（文件叫 stalled job）再重試。
  - 沒有「每條佇列同時幾個」的設定；要讓某一類工作一次只跑一個，用 `lock`（同一把鎖的工作一次只跑一個）。
  - 優雅關機沒有預設的時間上限，要自己設。
- **B. pgqueuer、chancy**：同樣用 PostgreSQL，比較新，文件與使用者都比較少。
- **C. Celery＋Redis**：最多人用，但要多跑一個 Redis（addendum 已排除，1 GB 主機也放不下）。
- **D. 不用佇列，全部靠 cron 直接跑指令**：每週更新可以，但上傳 PDF 需要「網頁丟工作、背景接手」，還是需要佇列。

**排程由誰觸發**

- **甲. Procrastinate 內建的週期任務**：寫在程式裡，worker 自己定時觸發。
- **乙. 外部排程器呼叫 `radar` 指令**：Compose 環境用主機的 cron；之後 K8s 用 CronJob。指令只做一件事：把工作排進佇列。

## 決定

**佇列選 A，排程選乙。**

1. **工作的參數只放 ID。** 例如 `identify_upload(upload_item_id)`。要處理的內容與目前進度都從資料表讀，不放在工作的參數裡。
2. **長流程的狀態放資料表**，工作只是「把狀態往前推一步」：

   | 流程 | 狀態表 | 狀態（資料庫裡存的值） |
   |---|---|---|
   | 每週更新 | `weekly_run` | `fetching`（抓取中）→ `published`（快照已發佈）→ `ai_done`（這一週的 AI 處理完成，或已等滿 24 小時）→ `exported`（示範站已匯出）；`failed`（抓取失敗） |
   | Batch | `batch_submission`、`batch_item` | `queued` → `submitting` → `submitted` → `ended` → `imported`；`failed`；`needs_attention`（需要人工處理） |
   | 上傳 | `upload_batch`、`upload_item` | `received` → `identifying` → 下面其中一種：`matched`（對到了）、`duplicate`（重複）、`needs_confirm`（可能是這幾篇，等使用者確認）、`needs_manual`（查不到，請填書目）、`mismatch_confirm`（檔案和這篇對不上，等使用者確認）、`lookup_deferred`（書目來源暫時連不上，稍後自動再試）、`failed`（讀檔失敗，一小時內可以重試）、`expired`（暫存檔已經刪除，要重新上傳） |

   - 每張狀態表的狀態只經過一個 services 函式改。
   - 同一時間只能有一個 `fetching` 的 `weekly_run`（資料庫的唯一索引擋）。
   - 上傳的狀態照 UX 文件「14. 上傳與匯入」的狀態表；「不接受」的檔案（太大、不是 PDF、超過配額）不建列，API 直接回錯誤代碼。

3. **每個工作都能重跑（NFR-5）。** 工作一開始先讀狀態；已經做完的步驟直接跳過。寫入一律用「有就更新、沒有才新增」。
4. **Batch 不重複送出（FR-1）。**
   - 送出前，先在同一個交易裡寫好 `batch_submission`（狀態 `queued`）與每一筆 `batch_item`。
   - **同一份輸入不重送**：每個 `batch_item` 在建立時就寫好一筆「正在跑」的來歷紀錄（`derivation_run`），記（對象, 工作代碼, prompt 版本, 模型, 輸入的雜湊）；資料庫保證這五個欄位相同、而且正在跑的只能有一筆（ADR-0009「同一份輸入同時只有一個在跑」）。所以摘要更新了（雜湊變了）、原本只有標題後來補上摘要、上一次失敗要重試，這三種情況都送得出第二次；同一份輸入則送不出第二筆。互動呼叫用的是同一個保證，所以兩邊也不會撞在一起。
   - `custom_id` 就是 `batch_item` 的 ID（32 個十六進位字元，符合 Anthropic「最長 64 字元、只能英數字與 `-`、`_`」的規定）。對象可以是論文，也可以是一對構念（合併判斷）。
   - 送之前先問閘門「這份輸入要不要跑」（ADR-0009）：已經有結果、或已經有別的呼叫在處理同一份輸入，就不排進這一批。
   - 呼叫 Anthropic 之前把狀態改成 `submitting`；拿到 Anthropic 的 batch ID 後存起來、改成 `submitted`。
   - 如果程式死在這兩步中間，重跑時看到 `submitting` 而且沒有 batch ID，**不會自動再送一次**，而是標成 `needs_attention`，用 `radar batches resolve` 人工確認。寧可卡住，不重複花錢。
   - **`needs_attention` 不會自己好，所以不能讓人以為還在跑。** 有這種批次時：`poll-batches` 不送心跳，管理者因此收到通知；底下每個項目的 AI 區塊顯示成 `failed`，不是「還在產生」（ADR-0015）。`radar batches resolve` 有兩種結果：補上 Anthropic 那邊查到的 batch ID，回到 `submitted` 繼續等；或標成失敗，把這些項目放掉，下一次每週更新會重新排。
   - 匯入結果時用 `custom_id` 找回 `batch_item`；同一筆匯入兩次，第二次不做事。
   - `batch_submission` 記它屬於哪一次 `weekly_run`（手動補跑的可以沒有）。
5. **排程一律是「cron 呼叫 `radar enqueue <工作>`」**，在已經開著的 worker 容器裡執行，不另開容器（不佔 750 MB 以外的記憶體）。排程表放在 repo 的 `deploy/crontab`：

   | 工作 | 頻率 |
   |---|---|
   | `weekly-update` | 每週一 03:00（台北時間） |
   | `poll-batches` | 每 15 分鐘 |
   | `sweep`（把卡住的項目與卡住的工作重新排入，見第 9 項） | 每 15 分鐘 |
   | `purge-tmp`（清暫存檔，FR-49；刪掉放了滿 60 分鐘的） | 每 15 分鐘 |
   | `backup`（FR-48） | 每天 02:00 |
   | `purge-sessions`（清過期的登入狀態） | 每天 |

6. **佇列分四條**：`ingest`、`ai`、`pdf`、`maintenance`。`pdf` 同時只跑一個（解析 PDF 最吃記憶體），做法是這條佇列的工作都帶同一把 `lock`；不另開一個 worker 行程（會多佔記憶體）。
7. **失敗的處理（FR-9）**
   - 重試分兩層，不重疊：連線層（逾時、429、暫時性錯誤）只在 adapter 裡重試，間隔逐次拉長，收到 429 時照對方給的等待時間；工作層只處理「整個工作失敗」。兩層的次數與間隔都放設定。
   - 到上限仍失敗時，把狀態標成失敗、寫一筆錯誤日誌，並且**不送出**當次的心跳。
   - **心跳一個排程一個**（每週更新、Batch 輪詢、sweep、清暫存檔、備份、示範站匯出各有自己的檢查名稱與網址）。共用一個網址的話，每 15 分鐘成功一次的 `sweep` 會一直報到，備份失敗就看不出來。
   - 外部服務的每日額度（OpenAlex、Workers AI）快用完時，工作停下、留到下一次排程續跑，不算失敗（架構文件 AD-29）。
8. **AI 產出要等多久（UX 文件問的）**：不給預計時間。
   - **哪些走 Batch 是固定的**：第一次匯入與每週新收的論文走 Batch（五折），通常一小時內，最晚 24 小時；問答與使用者自己觸發的（上傳、匯入推薦清單）不走 Batch，worker 直接呼叫，通常幾分鐘內；之後新增的工作預設走 Batch。
   - API 與示範站檔案裡，論文的每個 AI 區塊都有一個 `state`，前端依它決定顯示哪一句話。八個值：`ready`（有內容）、`empty`（跑過了，沒有可擷取的內容）、`pending_interactive`（幾分鐘內）、`pending_batch`（最晚 24 小時）、`deferred_budget`（這個月額度用完，下個月才產生）、`no_input`（沒有摘要）、`failed`（產出被拒收，或所屬的批次卡在 `needs_attention`；終點狀態，不會自動再跑，見 ADR-0015）、`not_applicable`（這種論文不做這個工作）。判定只寫在一個函式（架構文件 AD-7）。
9. **`sweep` 做兩件事**
   - 掃狀態表：依一份登記清單（哪張狀態表、起始狀態叫什麼、要排入哪個工作、停多久算卡住）把卡住的項目重新排入。新增狀態表的 Story 必須在清單加一列，不然它的表沒有人掃。互動呼叫中斷後留下的「正在跑」來歷紀錄也在清單上：超過時限就改成失敗，把那份輸入放掉，之後才排得進去。時限設得比單次呼叫的硬性時間上限長，所以超過時限代表那個工作已經不在了，不用人工確認；萬一結果之後才回來也不會啟用（ADR-0009）。卡住的示範站匯出紀錄（`demo_export`）也在清單上。
   - 掃佇列：用 Procrastinate 的 `get_stalled_jobs()` 找出 worker 已經不在、卻還停在執行中的工作，重試它們。沒有這一步，worker 被強制關掉時做到一半的辨認會永遠停住，而且因為 `pdf` 佇列用同一把鎖，後面排隊的全部跟著等。
   - `sweep` 自己由 cron 觸發（不用 Procrastinate 的週期任務）。
10. **誰把每週更新推到下一步**
    - 抓取與寫入成功 → 每週更新的工作自己發佈快照、送 `weekly-update` 心跳，狀態到 `published`。這時不等 AI。
    - `poll-batches` 每次結束時呼叫 `weekly_run` 的狀態函式，由它判斷「這一週的 Batch 都結束了，或發佈後已滿 24 小時」，成立就把狀態改成 `ai_done` 並排入示範站匯出。其他地方不排這個工作（Kevin 手動執行 `radar export-demo` 除外）。
    - **等滿 24 小時先匯出之後，遲到的結果怎麼辦**：同一個函式負責。條件是「這一週已經沒有未結束的 Batch，而且最後一次匯入結果的時間，晚於最近一次成功匯出的開始時間」，成立就再排一次匯出（匯出編號加一）。用時間比，不另外設「需要重新匯出」的標記，所以不會有標記忘了清或清太早的問題。
    - **同一個快照同時只有一個匯出在排隊或執行。** 只比時間擋不住重複排入：第一次匯出還在排隊、執行或重試時，「最近一次成功匯出」沒有變，15 分鐘後的下一次檢查條件照樣成立。所以排入匯出固定照這個順序，前三步在同一個交易裡：(1) 鎖住那一筆 `weekly_run`；(2) 拿到鎖之後才判斷要不要匯出：重新讀最後一次匯入結果的時間、最近一次成功匯出的開始時間、有沒有排隊中或執行中的匯出，鎖之前讀到的不算數；(3) 還需要才新增一筆「排隊中」的 `demo_export`；(4) 交易完成後才排入工作。`demo_export` 對同一個快照有一個只算排隊中與執行中的唯一索引，已經有一筆就不再排。匯出跑完後如果期間又有結果匯入，下一次檢查會照時間比較再排一次。手動的 `radar export-demo` 走同一步。
    - 實作時要有對應的並行測試，拆 Story 時帶進驗收條件：匯出還在排隊或執行時連續檢查多次，只會有一個匯出；匯出執行中又匯入結果，跑完後會再匯出一次，而且只有一次；第二個檢查等到第一個匯出成功之後才拿到鎖，不會再匯出一次。
    - 示範站匯出成功 → `exported`，送 `demo-export` 心跳。
11. **瀏覽器怎麼知道背景工作的進度**：一律用輪詢（瀏覽器每隔幾秒問一次），間隔放設定；不另開長連線推送（1 GB 主機不划算）。`GET /api/v1/me/status` 一次回：處理中的上傳數、做完還沒看過的上傳數、等確認的篇數、今天剩餘題數、問答是否因預算停用。導覽列的小圓點與問答頁一進來要顯示的狀態都讀它。

## 理由

1. **排程放外面，才搬得上 K8s。** NFR-18 要求「migration 與排程是獨立的 `radar` 指令」；K8s 的 CronJob 就是「定時跑一個指令」。用內建週期任務的話，開兩個 worker 還要處理誰來觸發。
2. **排程表看得見。** `deploy/crontab` 一個檔案就是全部的排程，不用翻程式。
3. **狀態放資料表，出事時查得到。** 「這批 Batch 現在到哪了」一句 SQL 或一個 CLI 指令就能回答（FR-1 的驗收）。
4. **少一個服務就少一個會壞的地方。** 佇列和資料放同一個資料庫，備份一次全包。
5. **「資料寫了但工作沒排進去」與「工作做到一半 worker 死了」都有固定的補救。** 順序一律是：先寫狀態列並完成交易，再排工作。排工作那一步失敗，或 worker 中途被關掉，每 15 分鐘的 `sweep` 會把它們找出來重新排入。因為每個工作都能重跑，重複排入不會出事。

## 取捨

- **佇列的輪詢會佔資料庫一點資源。** 4 個人的規模可以忽略。
- **cron 設定在主機上，不在容器裡。** 部署步驟要多一步「安裝 crontab」；寫進部署文件。
- **Procrastinate 的使用者比 Celery 少**，遇到問題能查到的資料比較少。換來的是不用 Redis。用到 Procrastinate 的程式只有兩處：`entrypoints/worker/`（定義工作）與 `adapters/jobs/`（負責排入的函式，用函式注入交給流程層，ADR-0001）；要換佇列只改這兩處。
- **Batch 卡在「需要處理」時要人工介入。** 這是刻意的；預期一年發生不到幾次。

## 名詞

- **背景工作**：不在使用者等網頁回應時做、丟給另一個程式慢慢處理的事。
- **工作佇列**：排隊等著被處理的工作清單；網站把工作放進去，worker 一件一件拿出來做。
- **worker**：專門從佇列拿工作出來做的程式，和回應網頁的 api 分開。
- **cron**：Linux 內建的定時器，到了設定的時間就執行指定的指令。
- **CronJob**：Kubernetes 裡的定時器，作用和 cron 一樣。
- **冪等**：同一件事做一次和做很多次，結果一樣；工作失敗重跑時不會多出重複的資料或重複扣錢。
- **stalled job（卡住的工作）**：佇列裡標示「執行中」、但負責它的 worker 其實已經不在的工作；不處理的話會永遠停在那裡。
- **lock（佇列的鎖）**：Procrastinate 的功能；帶同一把鎖的工作一次只會跑一個，其他的排隊等。
- **輪詢**：瀏覽器每隔一段時間主動問伺服器一次「好了沒」；相對的做法是伺服器主動推送。
- **心跳**：工作成功後向外部監看服務報到一次；該報到卻沒報到，監看服務就發通知。
