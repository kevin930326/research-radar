# ADR-0003：部署拓撲：服務跑在 1 GB 主機，資料庫放在主機外面

- 狀態：提議（資料庫位置 Kevin 已在 2026-11-12 決定選 A；其餘等 PR 確認）
- 日期：2026-11-12
- 對應：PRD NFR-1、NFR-17、NFR-18、FR-48、§6「環境」、§8.4 時程；addendum ARCH-11、ARCH-12、ARCH-16、ARCH-17、ARCH-18、ARCH-19；架構文件 AD-17、AD-28、AD-29

## 背景

PRD 預定的正式主機是 Azure for Students 的 1 GB 虛擬機，並規定 api 與 worker 兩個容器的記憶體上限加起來不超過 750 MB。剩下約 250 MB 要留給作業系統和 Docker，放不下 PostgreSQL。所以資料庫要放在別的地方（ARCH-16）。

2026-11-12 查到的事實：

| 項目 | 查到的內容 |
|---|---|
| Azure for Students | 每年 100 美元額度，不用信用卡，在學期間每年可續 |
| Azure 虛擬機 B1s（1 GB） | 前 12 個月每月 750 小時免費 |
| Azure 託管 PostgreSQL（Flexible Server B1MS） | 前 12 個月每月 750 小時＋32 GB 儲存免費，官方標示「僅限新客戶」；**之後約每月 23–26 美元**，一年的 100 美元額度只夠付 4 個月左右 |
| Azure 託管 PostgreSQL 的功能 | 支援 PostgreSQL 18（有內建 `uuidv7()`）；pgvector 0.8.2（依 2026-07-10 的官方文件；要先加進 `azure.extensions` 允許清單；`halfvec` 型別從 0.7.0 就有）；自動備份預設保留 7 天、最長 35 天 |
| Azure B1MS 的連線數 | 上限 50 條，Azure 自己保留 15 條，**可用 35 條**；這個等級沒有內建的連線池 |
| 預設映像裡的工具 | `python:3.14-slim` 是 Debian trixie，套件庫裡的 `pg_dump` 是 17 版；PostgreSQL 規定 `pg_dump` 不能匯出比自己新的資料庫，所以要另外裝 18 版 |
| Oracle 永久免費主機 | 2 核心、12 GB、Arm；7 天內 CPU（第 95 百分位）、網路、記憶體三項都低於 20% 會被回收 |

免費期滿後費用會不會從續約重新計算，查不到明確答案，以「不會」來規劃。

## 考慮過的選項

**A. Azure 虛擬機＋Azure 託管 PostgreSQL。** 服務在 1 GB 虛擬機，資料庫用 Azure 代管的。

**B. 全部放在 Azure 的 1 GB 虛擬機。** 把 PostgreSQL 也塞進同一台。

**C. 全部放在 Oracle 的 12 GB 主機。** 服務和資料庫都在同一台。

**D. 服務在 Azure，資料庫在 Oracle。** 跨兩家雲端連線。

| | 費用 | 記憶體 | 維運 | 主要風險 |
|---|---|---|---|---|
| A | 前 12 個月 0 元；之後每月約 23–26 美元，或搬走 | 守得住 750 MB | 最省事：備份、更新由 Azure 做 | 12 個月後的費用 |
| B | 0 元（在免費期與額度內） | 守不住：PostgreSQL 至少要 150–200 MB，容易被系統強制關掉 | 自己顧資料庫 | 記憶體不足時服務與資料庫一起掛 |
| C | 永久 0 元 | 很寬裕 | 自己顧資料庫 | 閒置回收；NFR-1 要重訂；PRD 寫的是「穩定數週後再評估」 |
| D | 0 元 | 守得住 | 最麻煩：跨雲端的連線、加密、延遲都要自己處理 | 兩家任一出問題就全掛 |

## 決定

**先用 A，並把「之後能搬走」做成設計的一部分。**（Kevin 2026-11-12 決定：選 A，2027-12 免費期結束前再評估。）

1. **正式環境（2027-01 起）**
   - Azure B1s 虛擬機用 Docker Compose 跑三個容器：`api`（`mem_limit` 350 MB）、`worker`（400 MB）、`cloudflared`（Cloudflare Tunnel 的連線程式，不計入 750 MB）。
   - `api` 同時送出成員版的前端檔案，所以不需要另外的網頁伺服器容器。
   - 對外只走 Cloudflare Tunnel；虛擬機不開 80／443，只開 SSH（金鑰登入）。
   - 資料庫：Azure Database for PostgreSQL Flexible Server B1MS，PostgreSQL 18，和虛擬機同一個區域；防火牆只允許虛擬機的 IP，強制 TLS。
2. **試用環境（2027-01 下旬，給同學試用）**
   - Oracle 主機跑**同一份** Compose，加上一個 `db` 容器（`pgvector/pgvector` 的 PostgreSQL 18 映像）。對外一樣走 Cloudflare Tunnel。
   - 這時還不用 k3s。Kustomize 與 k3s staging 是 PRD 4.16 的 Should（2027-03 底前），到時在同一台主機接上去（見「和 PRD 不一致的地方」）。
3. **應用程式不知道資料庫在哪裡，只認連線字串。** 資料庫有兩個角色、兩個連線字串：
   - 應用程式角色（`DATABASE_URL`）：api、worker 與一般的 CLI 指令用。它對人工判斷事件與稽核事件這兩張表沒有修改與刪除的權限。
   - 擁有者角色（`RADAR_MIGRATION_DATABASE_URL`）：只給 `radar migrate` 與 `radar restore` 用。
   - 只用一個角色的話，「不能改事件表」這條限制擋不住自己（表的擁有者隨時可以把權限加回來）。本機與 CI 也建同樣的兩個角色，測試才測得到真的限制。
   - 資料庫要用到的功能（`uuidv7()`、pgvector 不低於 0.8.0、`pg_trgm`）在遷移的第一步檢查，缺了就停下來並說明缺什麼；同時把 pgvector 的實際版本寫進日誌。
4. **連線數有預算。** 以 35 條可用連線為準：api 8、worker 6、每個 CLI 行程 2，其餘留給備份與人工連線。數字寫成設定的預設值，不靠各函式庫自己的預設（SQLAlchemy 預設每個行程最多 15 條，三個行程就會頂到上限）。
5. **備份不依賴 Azure**（架構文件 AD-28）。
   - 每晚 `radar backup` 用 `pg_dump` 匯出、用 age 加密、上傳 R2 的 `backup/`，成功後送出 `backup` 心跳（FR-48）。Azure 的 7 天自動備份是多一層，不是唯一一層。
   - 映像裡的 `pg_dump` 是 18 版（從 PostgreSQL 官方的套件庫安裝），`radar backup` 開頭先檢查它的大版本不低於資料庫。age 用官方發佈的執行檔。
   - 主機上只放加密用的公鑰。解密用的私鑰不放主機、不進 repo，放在哪裡記在 FR-46 的帳號與秘密清單。
   - 備份保留 30 天（設定值），由 R2 的 lifecycle 規則刪除。FR-31 說問答紀錄在備份裡的副本「隨保留期到期自然消失」，指的就是這個天數。
   - R2 裡的原始資料（`raw/`）與成員的 PDF（`pdf/`）不在備份裡，只有 R2 上的一份。v1 接受這個風險；第一次匯入後量過實際大小，再決定要不要多留一份（架構文件 Deferred）。
6. **還原是一個指令，搬家是演練過的動作。** `radar restore <備份檔>` 只能對空的資料庫執行。FR-48 規定上線前實際還原一次；還原的目標刻意選 Oracle 主機上的 PostgreSQL。這樣「搬到 Oracle」等於已經做過一遍。
7. **2027-12（免費期結束前一個月）重新決定**：搬到 Oracle 主機（選項 C），或付費留在 Azure。到時寫一份新的 ADR 取代這一份。Oracle 試用環境到那時已經跑了近一年，有實際資料可以判斷閒置回收是不是問題。
8. **試用期間產生的資料（ARCH-19）整個搬**：把試用環境的資料庫備份、在正式環境還原，R2 的試用 bucket 整個複製過去（複製 bucket 是 Kevin 手動做的雲端操作）。不另外寫「匯出／匯入人工判斷事件」的指令。
   - 理由：試用期間會產生的不只人工判斷事件與個人文獻庫，還有保存的 PDF、手填書目（沒有 DOI，沒辦法用 DOI 對應）、匯入的追蹤範圍外論文與分享勾選、構面合併的決定（重新擷取後構面不一定一樣，決定會對不上）。逐種搬一定會漏；整個搬不會漏，AI 也不用重跑（省約 9 美元），而且就是第 6 點要演練的同一個動作。
   - 論文的內部 ID 也因此不變，示範站與成員版的論文網址在搬家前後都一樣。
9. **換版與退版的步驟固定**（架構文件 AD-29）。
   - CI 把映像推到 GHCR，用 git 的 commit SHA 當標籤；Compose 檔用一個變數指定要跑哪個 SHA。
   - 換版寫成 `deploy/release.sh`，只由 Kevin 在主機上執行：拉新映像 → `radar migrate` → 重啟 api 與 worker。
   - 退版就是把變數指回上一個 SHA 再重啟。資料庫的破壞性變更一律分三步做，所以上一版的程式在新的資料表結構上還跑得動。
10. **容器的雜項設定**
    - 每個容器設日誌的大小與份數上限（NFR-15；1 GB 主機的磁碟也小）。
    - 容器內所有行程合計受 `mem_limit` 限制：worker 的 400 MB 要同時裝得下 worker 本身、讀 PDF 的子行程（上限 200 MB）、cron 觸發的 `radar enqueue`、每晚的 `pg_dump`。**夠不夠沒有實測**，第一個有 worker 的 Story 要量（見「取捨」）。
    - worker 的優雅關機時間（`shutdown_graceful_timeout`）與 Compose 的 `stop_grace_period` 成對設定，後者比前者長；否則 Docker 等 10 秒就強制關掉，手上的工作會卡住（ADR-0004）。

**其他一併決定的事**

- **資料庫在 K8s 叢集外面（ARCH-12）。** 之後接 k3s 時，資料庫仍然是叢集外的一個連線位址；不在叢集裡跑有狀態的資料庫。
- **多架構映像（ARCH-18）**：GitHub Actions 用 amd64 與 arm64 各自的原生執行機建映像，再合併成一個多架構的標籤，推到 GHCR（GitHub 的映像倉庫）。不用模擬器交叉編譯（慢，而且 Python 套件容易出錯）。私有 repo 的 arm64 執行機會扣額度；repo 公開後不扣。
- **排程放主機，不放 GitHub Actions**：見 ADR-0004。
- **重運算不在正式主機跑（NFR-17）**：正式主機的 Compose 檔不含 GROBID、本機模型、UMAP。這些之後在 Kevin 的 Windows 桌機用同一個映像＋`radar` 指令跑；桌機怎麼連到正式資料庫，等全文管線（Should 第一順位）開工時再決定。

## 理由

1. **照 PRD 既定的方向。** PRD 預定 Azure，並寫明 Oracle「穩定數週後再用 ADR 評估」。現在沒有 Oracle 跑正式流量的資料，直接選 C 等於跳過這個評估。
2. **一個人維運，資料庫交給代管最省事。** 第一年要顧的事已經很多（匯入、評估、上線）。
3. **費用的懸崖可以事先拆掉。** 資料量很小（約一萬篇論文、幾百 MB），匯出再還原是幾分鐘的事，而且 FR-48 本來就要演練。
4. **B 不安全。** 記憶體不足時 Linux 會挑一個程式強制關掉，被挑中的可能是資料庫。
5. **D 的複雜度沒有換到東西。**

## 取捨

- **12 個月後一定要再處理一次**，不然每月會被收 23–26 美元。補救：在 FR-46 的帳號與秘密清單裡記下免費期到期日，並在行事曆設提醒。
- **虛擬機到資料庫多一段網路**（同區域約 1–2 毫秒）。NFR-19 的論文頁 p95 ≤1 秒有餘裕；量測腳本在這個拓撲下跑。
- **Azure 的 pgvector 版本比上游舊**（0.8.2 對 0.8.7）。用到的功能（`halfvec`、HNSW、iterative scan）0.8.0 起都有；但 0.8.2 少了 0.8.3 與 0.8.4 的三個修正，都和 HNSW 索引在清理（vacuum）時可能損壞或報錯有關，而向量表會被更新與刪除（摘要變了重算、換模型後刪舊的），正好會觸發清理。資料量小（一到兩萬筆），重建索引只要幾秒，所以對策是：建立資料庫時記下實際版本；維運文件寫一條「搜尋結果異常時先對向量索引執行 `REINDEX`」。
- **worker 的 400 MB 可能不夠（估算，未實測）。** worker 本身估 120–180 MB，加上 PDF 子行程最多 200 MB 與同一分鐘啟動的兩個 CLI 行程，最壞情況會超過。超過時系統會強制關掉容器裡的某個行程。第一個有 worker 的 Story 加一條驗收：辨認一份 50 MB 的 PDF、同時跑兩個 `radar enqueue`，記下記憶體峰值寫回 ADR-0013。不夠的話可以調：子行程上限降到 150 MB、把排程錯開幾分鐘、讓 `radar enqueue` 只載入佇列需要的部分。
- **學生訂閱可能有區域限制**（社群回報約 5 個區域可用）。申請時選得到哪個區域，虛擬機與資料庫就一起放那裡。

## 和 PRD 不一致的地方

- PRD §6 與 §8.4 寫「2027-01 下旬在 Oracle 的 **k3s** staging 給同學試用」；但 §4.16 把 Kustomize 設定與 k3s staging 列為上線後的 Should（2027-03 底前）。兩處對不起來。這裡照「Must 不能依賴 Should」處理：一月的試用環境用 Docker Compose。**Kevin 2026-11-13 已確認**：試用環境用 Compose，K8s 的兩個階段單獨成一個 epic、不在可砍的範圍；PRD R9 已同步（§6、§8.2、§8.4、§8.5）。
- NFR-1 維持原樣（1 GB、750 MB）。如果 2027-12 決定搬到 Oracle，再依 NFR-1 的但書重訂。
- addendum 的 ARCH-19 寫「論文資料從 OpenAlex 重新匯入，人工判斷事件用 CLI 匯出／匯入」。這裡改成**整個資料庫備份後還原**（決定第 8 點），理由寫在那裡。**Kevin 2026-11-13 已確認**；addendum 的 ARCH-19 已同步。試用時留下的測試資料怎麼清，上線前再決定。
- PRD 寫 Oracle「穩定數週後」再評估要不要當正式環境；這裡把重新決定的時間定在 2027-12，比「數週」晚，因為 Azure 的免費期到那時才結束，中間沒有非換不可的理由。

## Kevin 2026-11-14 的確認

- **「750 MB」以 MiB 計**：AGENTS.md 與 NFR-1 的「api＋worker 不超過 750 MB」當成 750 MiB。`compose.yaml` 的 `mem_limit` 維持 api `350m`＋worker `400m`（Docker 的 `m` 是 MiB，合計 750 MiB，約 786 百萬位元組），數字不動。
- **PDF 子行程的記憶體到 Epic 6 實測再定**：1.4 實測 worker 峰值約 228 MiB，加上子行程上限 200 MB 最壞約 427 MiB，會超過 400 MiB（見「實測紀錄」）。做 PDF 的 Story（Epic 6）實測後再決定要不要調子行程上限或錯開排程，現在不改。

## 名詞

- **部署拓撲**：系統的各個部分（網站、背景程式、資料庫）分別放在哪幾台機器、彼此怎麼連。
- **託管資料庫**：雲端公司代為安裝、備份、更新的資料庫，使用者只負責用。
- **Cloudflare Tunnel**：主機主動連到 Cloudflare，外面的人經由 Cloudflare 連進來；主機自己不用對外開網站的連接埠。
- **多架構映像**：同一個 Docker 映像標籤裡包了給不同 CPU（Intel／AMD 的 amd64、Arm 的 arm64）用的版本，拉下來時自動挑對的。
- **GHCR**：GitHub 提供的 Docker 映像倉庫。
- **age**：一個檔案加密工具；備份檔上傳前先用它加密。它用一對金鑰：公鑰只能加密，私鑰才能解密。
- **資料庫角色**：資料庫裡的帳號；每個角色可以被允許或禁止對某張表做某些事。
- **連線池**：程式預先開好、重複使用的一批資料庫連線；上限設太高會把資料庫的連線用光。
- **PGDG**：PostgreSQL 官方維護的套件庫，裝得到作業系統套件庫還沒有的新版工具。
- **REINDEX**：把一個索引整個重建的資料庫指令。

## 實測紀錄

### 2026-11-14：worker 閒置與同時兩個 `radar enqueue`（Story 1.4）

- 環境：本機 Mac（Apple Silicon），Docker 29.8.2（linuxkit 核心 7.0.14）；Compose 專案 `radar-1-4-mem`，只起 `db` 與 `worker`（`mem_limit 400m`，cgroup 的 `memory.max` 讀到 419430400，也就是 400 MiB）；映像是這個分支 `docker build` 出來的 arm64 映像，Procrastinate 3.11.0、並行數 2。
- 量法：`radar migrate` 後等 worker 自己接上佇列，閒置 30 秒以上；然後同時跑兩個 `docker compose exec -T worker radar enqueue sweep`（一個排入、一個回「已經在排隊」，worker 執行那一筆到 `succeeded`）。記憶體從主機那一側讀 worker 容器的 cgroup：另開一個特權容器唯讀掛 `/sys/fs/cgroup`，每 50 ms 讀一次 `memory.current` 取最大值，結束後讀 `memory.peak`（容器建立以來的峰值）。兩者都含檔案快取。
- 結果：

  | 項目 | 數字 |
  |---|---|
  | 閒置（`memory.current`） | 約 77.5 MiB（81,260,544 bytes） |
  | 同時兩個 `radar enqueue` 時，每 50 ms 取樣的最大值 | 約 224 MiB（235,094,016 bytes） |
  | `memory.peak` | 約 227 MiB（237,662,208 bytes） |
  | 做完後（`memory.current`） | 約 77 MiB（80,900,096 bytes） |

- 同日審查修正後（相依改成 `psycopg[binary,pool]`、佇列連線字串轉換、卡住工作的重試上限等）用同一個量法重量一次：閒置約 77 MiB（80,883,712 bytes）；取樣最大值約 224 MiB（234,434,560 bytes）；`memory.peak` 約 228 MiB（239,038,464 bytes）；做完後約 77 MiB（80,314,368 bytes）。和第一次只差約 1 MiB，結論不變。

- 峰值主要來自兩個 CLI 行程（各自是一個完整的 Python 行程）；worker 本身閒置時遠低於原本估的 120–180 MB。
- **沒有量到的部分**：辨認 PDF 的子行程（上限 200 MB）還沒有程式，這次沒有算進去。把這次的峰值直接加 200 MB（以 200 MiB 算）約 427 MiB，會超過上限 400 MiB；但兩個 `radar enqueue` 同時、又剛好在解析大 PDF 的最壞情況，要等做 PDF 的 Story 實測才知道（見上面「取捨」的「worker 的 400 MB 可能不夠」；ADR-0013 也記了同一份紀錄）。
