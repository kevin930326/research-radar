# ADR-0002：讀取權限用「viewer 參數＋架構測試」強制，不用資料庫的列層級權限

- 狀態：提議（等 Kevin 在 PR 確認）
- 日期：2026-11-12
- 對應：PRD FR-7、FR-35、FR-42、FR-49、FR-50；addendum ARCH-15；架構文件 AD-3、AD-4

## 背景

系統裡有三種只有本人看得到的資料：上傳的 PDF、問答紀錄、個人文獻庫；另外，成員匯入的追蹤範圍外論文預設也只有匯入者看得到。PRD FR-7 要求「所有讀取權限都經過同一個權限判斷函式」，並用兩種測試驗收：

- 換人測試：每個回傳使用者資料的 API 端點，換成另一位成員呼叫要得到 403 或空結果。
- 金絲雀測試：在成員 A 的私人資料放一個唯一字串，換成員 B 問答、搜尋、匯出、產生示範站，任何地方都不能出現這個字串。

用哪一種機制強制，PRD 留給架構決定。難的地方是讀資料的入口很多：API、問答的檢索、語意搜尋、匯出、示範站產生器、背景工作。只要有一條路忘了過濾，就會外洩。

## 考慮過的選項

**A. viewer 參數＋架構測試。** 所有 SQL 集中在 `radar/repo/`。每個讀取函式的第一個參數是 `viewer`（代表「現在是誰在看」的物件），沒有預設值，不傳就不能呼叫。可見範圍的條件只寫在一個地方（`repo/visibility.py`），其他查詢都從它接出去。再用 import-linter（檢查「誰可以 import 誰」的工具）在 CI 擋住 `repo` 以外的程式直接碰資料庫。

**B. PostgreSQL 的列層級權限（row-level security，RLS）。** 在資料表上設定政策，資料庫依「目前是誰」自動過濾每一列。程式每次連線先執行 `SET LOCAL app.viewer_id = ...`。

**C. 兩種都做。** A 當主要機制，B 在私人資料表上再擋一層。

## 決定

選 **A**。

- `Viewer` 有三種，型別定義在 `radar/domain/viewer.py`：`MemberViewer`（某一位成員）、`PublicViewer`（示範站產生器用，只看得到可以公開的資料）、`SystemViewer`（看得到全部）。
- 誰可以建立哪一種：
  - `MemberViewer`：API 的登入檢查（由 session 得到）；**背景工作替某位成員做事時**（上傳辨認、推薦清單），worker 用狀態列上的擁有者建立；CLI 指令帶 `--as <管理者 email>` 時。
  - `PublicViewer`：只在示範站產生器與展示問答。
  - `SystemViewer`：只用在沒有特定使用者的工作（匯入、每週更新、Batch、維運）。
- 一篇論文看不看得到，只有一條規則：`paper.lab_visible` 是真，或這位成員的個人文獻庫裡有它。這條規則寫成一個 SQL 片段，所有會回傳論文或論文衍生資料（摘要、分類、研究模型、向量）的查詢都要接上它。唯一的例外是從成員上傳的 PDF 讀出的原文摘要：論文本身大家看得到，這筆摘要只有上傳者看得到（FR-13）。
- 會改資料的函式用同一個物件當「是誰做的」（參數叫 `actor`），不另外定義一套身分（架構文件 AD-27）。
- 沒登入回 401。沒有權限和找不到回同一個結果（404），不透露那筆資料存在（UX 文件「沒有權限」狀態）。
- 管理者透過網站看到的和一般成員一樣。維運時用 CLI 讀取別人的私人資料，會寫一筆稽核事件。
- 背景工作的狀態表只存 ID 與自己的資料，不把別的表的內容抄進來。例如上傳時「可能是這幾篇」的候選清單不存起來，顯示時用上傳者的 viewer 即時查。

### 為什麼背景工作不能一律用 `SystemViewer`

上傳的 PDF 沒有 DOI 時，背景工作會用標題比對資料庫裡的論文、列出候選。如果用「看得到全部」的身分去比，候選裡會出現別的成員私下匯入的論文與手填書目，再顯示給上傳者，等於把別人的私人書目露出來。所以替誰做事，就用誰的身分查。

## 理由

1. **PRD 規定的兩種驗收測試不管選哪個都要寫。** 換人測試與金絲雀測試已經能抓到「忘了過濾」；RLS 多擋的一層，在 4 個成員、1 個開發者的規模下，換來的維運成本比較高。
2. **RLS 出錯時很安靜。** 政策寫錯或忘了設定 `app.viewer_id`，結果是「查不到資料」而不是錯誤訊息，除錯很花時間。viewer 參數漏傳，程式直接起不來。
3. **背景工作和示範站產生器需要「看得到全部」或「只看公開的」。** 用 RLS 要多開資料庫角色、各自繞過或套用政策；用 viewer 只是換一種物件。
4. **檢索的 SQL 需要自己控制過濾的位置。** 向量搜尋的索引是「先找最近的幾筆、再過濾」，過濾放錯位置會讓個人文獻庫這種小範圍搜不到東西。把條件寫在自己的查詢裡，比交給 RLS 自動加上去好掌握。
5. **之後要加 RLS 不用改函式。** viewer 已經一路傳到查詢，到時在私人資料表加政策、在連線上設定 `app.viewer_id` 即可。

## 取捨

- **放棄的**：資料庫層的最後一道防線。有人在 `repo` 以外寫 SQL，或在 `repo` 裡寫了一個沒接可見範圍條件的查詢，資料庫不會擋。
- **補救**：
  - import-linter 規則：只有 `radar.repo` 可以 import SQLAlchemy；入口（api、cli、worker）不能 import `radar.repo`。
  - 架構測試：`repo` 的公開函式名稱只能用測試裡登記的前綴，分成讀取類與寫入類；讀取類的第一個參數必須叫 `viewer` 且沒有預設值（用程式檢查函式簽名）。沒登記的名稱直接失敗，所以不會有人取一個測試認不出來的名字而漏掉檢查。不帶 viewer 的讀取只有列名的例外：登入流程要先查 session 才知道是誰，那幾個查找沒有 viewer 可帶。
  - FR-7 的換人測試（CI 對照 `openapi.json` 的端點清單）與金絲雀測試（問答、搜尋、匯出、示範站檔案、log、上傳時的標題候選）。
- **什麼時候重新考慮**：開放實驗室以外的人註冊、多實驗室（PRD 的 L01），或金絲雀測試曾經抓到外洩。那時改成選項 C。

## 和 PRD 不一致的地方

- FR-7 的換人測試寫「得到 403 或空結果」。這裡定為 **404 或空清單**：回 403 等於告訴對方「這筆資料存在，只是你不能看」。寫測試時以 404 為準。**Kevin 2026-11-13 已確認**；PRD R9 的 FR-7 已改成「404 或空清單」。
- addendum R7 建議用 `visibility` 列舉值與 `policy.can_read(user, resource)`。這裡改成 `lab_visible` 布林值加「只有擁有者」的表，判斷寫成 SQL 片段。addendum 註明這些建議架構階段可以調整。

## 名詞

- **viewer**：代表「現在是誰在看資料」的物件，查詢靠它決定要過濾掉什麼。
- **import-linter**：在 CI 檢查 Python 模組之間「誰可以 import 誰」的工具，用來守住分層。
- **架構測試**：不測功能、只測程式結構有沒有守規則的自動化測試。
