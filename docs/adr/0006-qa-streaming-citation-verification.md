# ADR-0006：問答邊串流邊驗證出處，瀏覽器只收得到驗證過的出處

- 狀態：提議（等 Kevin 在 PR 確認）
- 日期：2026-11-12
- 對應：PRD FR-28、FR-29、FR-30、FR-31、NFR-2、NFR-19、SM-3；UX 文件「16. 問答」與「給架構階段的事項」；架構文件 AD-13

## 背景

兩個需求互相拉扯：

- NFR-19 要求問答 5 秒內出現第一個字，所以回答要逐字出現（串流：模型寫一點就送一點，不等整段寫完）。
- FR-29 與 UX 文件要求「任何時候都不可以先顯示還沒驗證的出處」，沒通過驗證的出處不顯示，並寫出拿掉了幾個。

UX 文件把「文字逐字出現和驗證誰先誰後」留給架構決定。

## 考慮過的選項

**A. 整段寫完、驗證完才送出。** 最簡單，但沒有逐字出現，第一個字會等到十幾秒以後。

**B. 文字先串流、出處編號最後一起補上。** 文字逐字出現時不帶編號，整段結束後驗證，再把通過的編號插回去。使用者讀的時候看不到哪一句對應哪一篇，最後畫面會跳一下。

**C. 邊串流邊驗證。** 可以引用的論文在開始生成之前就已經確定（就是這一題檢索出來的那幾篇）。伺服器讀模型的輸出，遇到出處編號就當場查表，在表裡的才送給瀏覽器。

## 決定

選 **C**。

1. 檢索（ADR-0005）回傳這一題的候選論文，伺服器替它們編上這一題專用的編號 1…k，連同原文摘要與驗證過的假設原句交給模型。**模型看不到論文的識別碼，也不會輸出網址。**
2. 模型在句子後面寫 `[n]`。
3. 伺服器逐段讀模型的輸出。讀到 `[` 時先扣住不送，等到 `]` 出現：
   - n 在這一題的編號表裡 → 送出一個「出處」事件，內容是論文識別碼（由伺服器查表得到）。
   - 不在表裡，或格式不對 → 丟掉，計數加一。
4. 瀏覽器收到的是有型別的事件（SSE：伺服器單方向持續推送訊息給瀏覽器的標準做法）：
   - `route`：這一題怎麼處理。值固定五個：`answer`（回答）、`not_found`（找不到）、`count_redirect`（計數題導流）、`research_question`（研究問題請求）、`retrieval_only`（只檢索）。
   - `status`：「正在找相關的論文」「正在整理回答」。
   - `text`：一小段文字。
   - `citation`：一個驗證過的出處（編號＋論文識別碼）。
   - `done`：結束，附「拿掉了幾個出處」、有沒有依據（`grounded`）、剩餘題數、AI 標章要用的來歷資料。
   - `error`：失敗，帶全站共用的錯誤代碼。
   - **每種事件的內容都是後端的一個具名資料模型，列進 `openapi.json`**，前端的型別照樣由它產生。OpenAPI 本身不描述 SSE 事件，不這樣做的話前後端會各寫一份。
5. 前端只用 `citation` 事件畫出處編號與出處清單；`text` 裡就算出現像出處或連結的字，也只當一般文字，而且照 NFR-2 淨化（不允許 HTML、圖片、連結）。
6. **保存下來的回答只有一種形狀，叫 `QaAnswer`**：`route`、`segments`（依序排列的文字段與出處段，出處段帶編號與論文識別碼）、`dropped_citations`（拿掉幾個）、`grounded`、`provenance`。串流時的 `text` 與 `citation` 事件就是逐段送出的 segment。整段結束後才寫入問答紀錄。成員的問答紀錄、展示問答存的答案、示範站的 `qa.json`，存的都是它，所以同一個回答元件三處都能畫，出處在哪一句後面也不會遺失。

**這一題怎麼處理（`route`）由誰決定**

- 預算用完（熔斷）：伺服器在呼叫模型之前就決定，`route` 是 `retrieval_only`，不呼叫模型，也不在串流裡送論文清單；前端收到後用同一句話改呼叫搜尋，顯示找論文的結果（UX 文件「16. 問答」）。
- 其餘情況：系統提示要求模型的**第一行只能寫一個路由標記**，四選一：回答、找不到、計數題、研究問題請求。伺服器扣住第一行不送給瀏覽器，對照這份固定清單：
  - 回答：送出 `route`，後面的文字照上面的規則串流。
  - 找不到：送出 `route`，顯示固定的「找不到」說明（文字在前端的 i18n 裡，不是模型寫的）。
  - 計數題：送出 `route`，顯示固定的導流說明與趨勢頁連結（FR-30）；模型後面寫什麼都丟掉。標記那一行可以附一個主題代號，伺服器對照設定檔的主題清單，在清單內才放進 `route` 事件，讓趨勢頁連結帶著這個主題（UX 文件「帶入條件的趨勢頁連結」）；不在清單內就不帶。
  - 研究問題請求：送出 `route` 後就停止生成。畫面只顯示固定的說明（本系統不產生研究問題）與兩個連結：「整理這個方向已有的研究（附出處）」與「到關係排行表挑一條關係，產生證據簡報」。**這一次不寫回答、不扣題數**（照 UX 文件「16. 問答」的狀態表）。第一個連結由前端用固定句型（「整理〔原問題〕這個方向已有的研究」）把問題帶回輸入框，使用者按下才問第二次；不另外呼叫模型改寫問題。
  - 第一行不在清單裡：當作失敗，送 `error`。
- 回答到最後，一個通過驗證的出處都沒有：`done` 事件的 `grounded` 是假，前端把整段回答換成「找不到」的畫面，這一題不扣題數，紀錄裡的 `route` 記成 `not_found`。這和 UX 文件「沒有依據就直接說找不到」一致：畫面上不會留下一段沒有任何出處的回答。

**每日題數（FR-31）**

- 題數記在獨立的 `qa_usage` 表（成員、日期、已用題數），以台北時間的日期為準。不能用問答紀錄的筆數來算，因為使用者可以刪除自己的問答紀錄。
- 只有 `route` 是 `answer`、有通過驗證的出處（`grounded` 為真）、而且正常結束（`done`）的才扣一題。計數題導流、找不到、研究問題請求、只檢索、逾時、失敗、使用者中途離開都不扣（UX 文件的假設）。

「驗證」的定義比 FR-29 的字面嚴格一級：出處不只要存在於資料庫，還必須是**這一題交給模型的那幾篇之一**。那幾篇是用提問者的 viewer 查出來的（ADR-0002），所以不可能引用到提問者看不到的論文。

## 理由

1. **驗證其實是查表，不花時間。** 允許的集合在生成之前就定了，所以不需要等整段寫完。
2. **未驗證的出處根本不會離開伺服器。** 這比「前端先藏起來」可靠：前端有 bug 也不會顯示出來。
3. **藏在論文摘要裡的惡意指令偽造不出連結。** 模型只能寫編號，編號對應哪一篇由伺服器決定（NFR-2 的注入金絲雀測試）。
4. **和之後的 S06（Anthropic 原生引用）相容。** 到時候換的是「模型怎麼標出處」，事件格式與前端不用改。

## 取捨

- **多了一段串流解析的程式**，要處理 `[` 被切在兩段之間、模型寫出 `[12` 就停住等情況。這段是純函式，用單元測試涵蓋（含捏造編號、格式錯誤、被截斷的負面樣本）。
- **文字會比模型的輸出慢一點點出現**（遇到 `[` 時要等 `]`），最多扣住十個字元左右，人感覺不到。
- **只驗證「引用的是不是給它的那幾篇」，不驗證「那一篇是不是真的支持這句話」。** 後者是 FR-41 的引用支持率，用評估題組量，不在這裡擋。
- 使用者中途關掉頁面時，伺服器停止生成；這一題不寫紀錄、不扣題數（UX 文件的假設）。已經花掉的費用照樣記進帳本：帳本用自己的交易寫入，不跟著這一題的失敗一起回滾（ADR-0009）。
- **研究問題請求仍然花了一次很短的模型呼叫**（讀到第一行的標記就停），但不計入使用者的題數。

## 和 PRD 不一致的地方

- FR-2 要求保存每次 LLM 的原始回應；FR-31 要求使用者刪除問答紀錄後資料庫不留副本。問答的原始回應裡就有問題與回答的全文，兩條不能同時照字面做。這裡照比較具體的 FR-31：**問答的原始回應只存在問答紀錄那一列裡，跟著一起刪**；費用帳本留下的只有長度、費用與 request ID（NFR-15）。
- FR-30 附則寫研究問題請求「改提供既有研究整理」。UX 文件（比 PRD 晚定案）把它畫成「固定說明＋兩個連結，使用者再按一次才整理」。這裡照 UX 文件。

## 名詞

- **串流**：模型寫一點就送一點給使用者，不等整段寫完。
- **SSE（Server-Sent Events）**：伺服器單方向持續推送訊息給瀏覽器的標準做法，適合逐字出現的回答。
