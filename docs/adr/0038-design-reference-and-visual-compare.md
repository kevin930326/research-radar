# ADR-0038：前端畫面以設計稿為準，做完要量差異；字級改成可以自由組合的尺度

- 狀態：提議（等 Kevin 在 PR 確認）
- 日期：2026-11-15
- 對應：`docs/ux/reference/`；`DESIGN.md`、`EXPERIENCE.md`；ADR-0010、ADR-0037；Story 3.1、3.2 之後的每個前端 Story

## 背景

Story 3.1 做出來的使用須知和設計稿差很多：警語和說明同一個顏色、小段之間沒有髮線、三句話擠成一行、字級差 1～4px。原因有三個：

1. 設計稿在 claude.ai 的 Artifact 上，自動執行的 agent 讀不到，只照 `EXPERIENCE.md` 的文字做。
2. 設計稿的視覺細節沒有全部寫回文字規格（規格自己註明「這三個畫面只有設計畫布上的畫板」）。
3. `DESIGN.md` 的字級代幣是 21 個綁死的組合，設計稿用了 118 種組合；ADR-0037 不准寫任意值，agent 只能挑最接近的（清查見 `docs/ux/reference/token-gaps.md`）。

驗收條件雖然寫了「Kevin 對照設計畫布確認」，但那是事後才發現，而且每個畫面都要 Kevin 逐項挑。

## 考慮過的選項

**設計稿怎麼交給 agent**

| | 做法 | 缺點 |
|---|---|---|
| A | 把每個畫面的細節全部寫進 `EXPERIENCE.md` | 十幾個畫面、每個幾十種狀態，寫不完也一定會漏 |
| B | 把設計預覽頁的 HTML 原封不動存進 repo，規定以它為準 | repo 多約 5 MB 的 HTML；設計改了要重新存 |
| C | 每個 Story 的任務檔附截圖 | 截圖量不出字級與顏色，agent 只能目測 |

**怎麼確認做對了**

| | 做法 | 缺點 |
|---|---|---|
| A | Kevin 自己對照 | 就是現在的做法，每個畫面都要花他的時間 |
| B | 截圖做像素比對 | 字體渲染、還沒做的導覽列都會讓像素不同，雜訊太多 |
| C | 用文字配對元素，量字級、行高、顏色、字重、字距、和上一段的距離、有沒有髮線 | 量不到圖形（星系、圖表）；設計稿與實作文字不同的元素配不到（會列出來） |

**字級的缺口**

| | 做法 | 缺點 |
|---|---|---|
| A | 維持 21 個角色，挑最接近的 | 畫面和設計稿不一樣（這次的問題） |
| B | 拿掉 ADR-0037 對字級的限制 | 任何值都能寫，失去一致性 |
| C | 替 118 種組合各取一個角色名稱 | 名稱沒有意義，也維護不了 |
| D | 加三組尺度（字級、行高、字距），值只收設計稿用到的；組合自由，尺度以外照擋 | 同一種文字可能在不同畫面被組成不同的樣子，要靠比對工具守住 |

## 決定

1. **設計稿存進 repo（選項 B）**：`docs/ux/reference/screens/`，14 個檔，內容不改。`docs/ux/reference/README.md` 有畫面對照表與每個檔的狀態清單。前端畫面的字級、行高、字距、顏色、間距、髮線、分行以設計稿為準；`EXPERIENCE.md` 管文字與行為。兩邊文字不同時列為 Kevin 的決定。
2. **做完要量差異（選項 C）**：`web/scripts/design-compare.mjs`。每個做畫面的 Story，桌機（1280）與手機（390）、碰到的每一種狀態各跑一次，報告貼進 PR 說明。報告裡會擋的四段（樣式不一樣、設計稿沒有這段文字、位置、寬度、順序不一樣、設計稿有而畫面沒有又沒列在清單裡的文字）都是 0，結束碼才是 0；不是 0 的每一條都要有原因，原因只能是「範圍還沒到（寫出哪個 Story）」「Kevin 決定過（寫出日期與文件）」「ADR-0037 的無障礙規定（寫出哪一條）」。屬於別的 Story 的文字用 `--expect-missing` 清單檔明確列出（放 `docs/ux/reference/expect-missing/`），不是默默略過。這是合併門檻；審查的 subagent 要自己重跑一次，不能只看 PR 說明。
3. **字級改成尺度（選項 D）**：`DESIGN.md` 加 `font-sizes`、`line-heights`、`letter-spacings` 三組，值照 `token-gaps.md`。21 個角色留著。ADR-0037 的其他規定（顏色只用代幣、不准任意的字級與行高、斷點、焦點外框、減少動態）不變。這一點另開一個 PR 實作。
4. **沒有設計稿的畫面**（README 列了）：做之前先停下來列為 Kevin 的決定，不自己設計。
5. Kevin 的確認還是要做，但變成看最後結果，不是逐項挑。

## 理由

- agent 讀得到檔案、讀不到 Artifact；HTML 裡每個值都寫在行內樣式，比任何文字描述都完整。
- 用文字配對不需要替每個畫面另外寫比對清單，新畫面直接能用。拿 Story 3.1 原本的使用須知試跑，它自己抓到顏色、髮線、文字三種差異。
- 尺度只收設計稿出現過的值，所以「只用設計過的值」這個原則還在。

## 取捨

- 比對工具量不到圖表、星系、圖示、背景、圓角、陰影與動態，那些仍要看截圖（工具會存）。
- 「和上一段的距離」量的是兩個元素外框之間的距離：設計稿用外距、畫面用內距，看起來一樣也會被報成差異（方向保守，不會讓錯的畫面過關）；`<hr>` 畫的髮線認不出來；畫面一直有網路請求時工具會等到逾時。
- 比對工具用文字配對：文字本身改了，會同時報成「設計稿沒有這段文字」和「缺少」，不會比樣式。
- 尺度的檢查擋的是寫成類別的字串。擋不到的寫法：用 `${""}` 把類別名拆開再拼起來（Tailwind 的掃描器還是會產生 CSS）、`style` 屬性裡直接寫行高、字距、字重的數字，或在 `style` 裡改寫主題變數與 `--tw-leading` 這類 Tailwind 內部變數；`font-(family-name:--x)` 這種用變數指定字體的類別。這些靠審查看。
- `font-sizes` 的 `s44` 只有使用須知的標題用過，統一 40px 之後沒有畫面在用；留著是因為尺度照設計稿出現過的值收，頁面標題不得用它。
- 設計稿不是最新的時候，工具會把「Kevin 後來改過的決定」報成差異，要在 PR 說明寫明；累積多了就該重新存一份設計稿。
- 頁面標題在設計稿之間不一致（40／44／36px），尺度讓三種都寫得出來，Kevin 2026-11-15 決定統一用 40px（`token-gaps.md`）。
- repo 公開前要把設計稿裡示意用的論文摘要換掉（Story 13.6）。

## 名詞

- **設計稿**：`docs/ux/reference/screens/` 裡實際大小的設計預覽頁。
- **設計稿比對**：用工具量出做出來的畫面和設計稿在字級、顏色、間距等項目上的差異。
- **尺度**：一組允許使用的值（例如字級只能是 11、12、13…），可以自由搭配，和「角色」（把字級、行高、字距綁成一組並取名）相對。
