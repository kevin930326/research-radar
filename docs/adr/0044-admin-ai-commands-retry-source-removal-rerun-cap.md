# ADR-0044：管理者的 AI 指令：查詢、重跑拒收（`retry_of`）、依摘要來源移除、改版預估與重跑上限

- 狀態：提議
- 日期：2026-11-16
- 對應：Story 2.12；FR-11（摘要來源授權改變時移除衍生產出）、AD-8（拒收只有 `radar runs retry` 能重跑、閘門是唯一呼叫 provider 的地方）、AD-26（稽核事件）、AR-46；ADR-0015（AI 結果表的狀態與「改版重跑上限：待決」）、ADR-0030（`llm_result_pending` 與接續）、ADR-0031（預算）、ADR-0035（稽核表）、ADR-0041（Batch 規劃）、ADR-0043（手動全庫）

## 背景

- 出問題時只能直接查資料庫：沒有指令看一篇論文的 AI 結果與來歷。
- `rejected` 是終點狀態：平常流程（互動服務、試跑、Batch 規劃）同一組鍵遇到它一律 `SKIPPED`（ADR-0015）。AD-8 指定只有 `radar runs retry` 能讓它重跑，但這條路還沒有。
- 摘要來源（OpenAlex、Semantic Scholar、自己上傳的 PDF）的授權可能改變，要能移除用那個來源的摘要產生的 AI 結果（FR-11）。問題：表頭只記 `abstract_id`，而來源拿掉摘要時 `paper_abstract` 整列刪掉，`abstract_id` 就接不回來源了。
- 改分類表或情境值清單之後，下一次 Batch 規劃會重跑所有受影響的論文，但事前不知道會重跑幾篇、花多少，也沒有上限（ADR-0015「待決」）。
- 同一個指令可能被執行兩次、兩個人同時執行，或執行到一半被中斷；寫入不能只靠「同時只會有一個人在跑」。

## 考慮過的選項

### 1. 怎麼讓被拒收的結果重跑

| | 做法 | 優點 | 缺點 |
|---|---|---|---|
| A | 閘門 `run_llm_job` 加 `retry_of`（確認時那一列 `rejected` 表頭的 id）；鎖內：`active` 照樣 `SKIPPED`，`rejected` 只在「這組鍵最新的一列平常流程表頭就是 `retry_of`」時放行；只准 `services/run_retry.py` 傳（arch 測試） | 走同一個閘門（預算、記帳、驗證、接續都一樣）；兩個重跑同時跑、或同一個確認過的 id 重送，都只呼叫一次 | 閘門多一個參數與一次查詢 |
| B | 重跑前把那一列 `rejected` 改成別的狀態（例如 `superseded`），讓平常流程重跑 | 閘門不用改 | 拒收的歷史被改掉；改完到重跑之間，Batch 規劃也會撿走它 |
| C | 加一個「忽略 rejected」的布林旗標 | 簡單 | 兩個重跑同時跑會各付一次錢；重跑完再送一次會再付一次 |

看「最新一列表頭」而不是「最新一筆 run」：重跑被中斷只留下沒有表頭的 `failed` run，下一次照樣能重跑；有存下輸出的（`llm_result_pending`）照常接續、不重付。

### 2. 依來源移除怎麼找到要刪的表頭

| | 做法 | 優點 | 缺點 |
|---|---|---|---|
| A | 遷移 0018 在 `derivation_run` 加 `abstract_source`（送出時用的摘要來源），閘門新增 run 時寫入；回填接得到 `paper_abstract` 的舊 run | 摘要列刪掉之後仍查得到；互動、試跑、Batch 都同一個寫入點 | 遷移前、摘要列已刪的舊 run 回填不到（「來源不明」） |
| B | 用表頭的 `abstract_id` 接 `paper_abstract` 查來源 | 不用遷移 | 授權改變的標準做法正是先刪摘要，刪了就查不到 |
| C | 依 `llm_call` 或請求內容推回來源 | 不用改表 | 請求內容沒存；推不準 |

### 3. 刪除的方式與擋下條件

| | 做法 | 優點 | 缺點 |
|---|---|---|---|
| A | 預設只印不做；`--execute` 確認後在一個交易裡：固定名稱的交易級 advisory lock → 鎖內重查擋下條件 → 先細項後表頭直接刪（不複製）→ 有刪到才寫一筆稽核（系統身分，只記來源與各表計數） | 中斷就整個退回；兩個同時執行只有一筆稽核；刪完再跑刪 0 列、不寫稽核 | 被刪的內容找不回來（只剩計數） |
| B | 先複製到 `deleted_record` 再刪 | 可以還原 | 授權改變就是不能再留內容；多一張表 |
| C | 改狀態（例如加 `removed`）不刪 | 可以還原 | 內容還在資料庫；每個讀取都要多一個條件 |

擋下條件（鎖內重查，任一成立就什麼都不刪、不寫稽核，印原因與下一步）：

- 還有這個來源的 `running` run：它回來會再寫一列表頭。
- 還有論文的目前摘要是這個來源：下次規劃會用同一份摘要重新產生，刪了也白刪，而且新 run 可能在刪除之後才寫入。

兩者都沒有時，之後幾乎不會再出現這個來源的新表頭，但不是絕對：互動閘門在第 1 步讀摘要、第 5 步才在另一個交易裡建 run，所以一個在摘要被刪之前剛讀到這個來源的呼叫（試跑、重跑、互動服務），仍可能在刪除 commit 之後才寫進一列這個來源的表頭。這列表頭的 `derivation_run.abstract_source` 一樣是這個來源，所以預覽看得到、再跑一次就會刪掉。做法：刪完之後再跑一次預覽確認是 0；最好在沒有試跑、重跑正在進行時執行移除。

### 4. 改版重跑上限

| | 做法 | 優點 | 缺點 |
|---|---|---|---|
| A | `config/llm_batches.yaml` 的 `revision_rerun_max_usd`（字串、0～50、預設 5）；Batch 規劃在熔斷檢查之後估「現行有效結果用的設定檔版本和現在不同」的候選，Batch 價保守上限合計超過就整次不排（`PlanStop.RERUN_CAP_EXCEEDED`）、不寫任何列、記錯誤日誌；`radar runs estimate-revision` 事前估 | 改版不會在沒人注意時花掉大半個月的預算；第一次全庫沒有現行結果，不受影響 | 每次規劃多掃一次候選（多讀，不多寫）；超過時連新論文也一起不排，要人決定 |
| B | 超過時只排上限內的部分 | 新論文照常排 | 哪些先排、哪些晚排要另外定規則；改版會拖好幾週才做完 |
| C | 不設上限，只靠每月熔斷線 | 簡單 | 熔斷時當月其他工作（每週新論文、問答）全部停 |

## 決定

1. **`radar runs show <ID或DOI>`（只讀）**：三個 AI 區塊（狀態沿用 `get_ai_blocks`，不自己判斷）、有效值、來歷（模型、prompt 版本、產生時間、輸入種類、人工核對），以及這篇三個工作的歷次 run（有表頭照表頭狀態，沒有照 run 狀態；原因代碼、模型、prompt 版本、輸入種類、摘要來源、時間；評估另外標出）。有效值的 prompt 版本取歷次裡同工作 `active` 那一列的 run；只有人工值時寫「人工」。終端機印的有效值先跳脫控制字元，不寫進日誌。
2. **`radar runs retry <ID或DOI> [--task …] [--yes]`**：選項 1-A。先算出每個工作這次會送的請求（和試跑、Batch 同一套 `plan_for` → `prepare_llm_request`），在只讀交易裡查目前這組鍵：有 `active`、正在跑、或最新一列平常流程表頭不是 `rejected` 都不能重跑（印原因）。可以重跑的印單次上限 × adapter 的 `attempts`（含重試的最壞情況，互動價）與本月預算，確認後（`--yes` 不問）每項經閘門互動呼叫一次，帶 `confirmed_key`（確認後輸入變了 → `input_changed`、不呼叫）、`retry_of` 與 `BudgetGuard`。沒有可以重跑的退出碼 1；結果是 `active`、再一次 `rejected` 或鎖內判定 `skipped`（別人做了）退出碼 0。
3. **遷移 0018**：選項 2-A。`derivation_run.abstract_source text NULL`；CHECK 值只能是三個摘要來源、向量化（`task = 'embed'`）先不記；回填只補還是 NULL、看摘要、接得到摘要列的 run（做兩次結果一樣）。可降版。
4. **`radar runs remove-by-source <來源> [--execute] [--yes]`**：選項 3-A。預覽印各表各狀態會刪幾筆、細項幾筆、還在跑的 run 數、目前摘要仍是這個來源的論文數、來源不明的表頭數。刪的是 `derivation_run.abstract_source` 是這個來源的所有表頭（四種狀態）與細項（`classification_label`、`construct_mention`、`hypothesis`）。不動 `derivation_run`、`llm_call`、`batch_item`、構面、向量、`paper_abstract`、人工判斷事件、稽核；標題輸入、其他來源、**來源不明的表頭不刪**（照計數印出）。
5. **移除的操作順序**：先停用來源、移除那個來源的摘要，再跑這個指令；順序反了會被擋下並印出下一步。刪完之後再跑一次預覽（不加 `--execute`），確認是 0；不是 0 就再執行一次（見選項 3 下面的說明）。最好在沒有試跑、重跑正在進行時執行。
6. **稽核**：`audit_event` 的寫入函式定名 `create_audit_event`（AD-26 寫的 `record()` 不符合 repo 的前綴規則）；CLI 以系統身分執行（`member` 表在 3.3），`actor_role='system'`、沒有成員 id；`detail` 只有 `source` 與各表 `counts`。
7. **`radar runs estimate-revision [--taxonomy] [--context-values]`** 與選項 4-A。預估用 `assume_changed=True`（有現行結果的都算會重跑）；規劃用 `assume_changed=False`（只算版本已經不同、而且規劃真的會排的：新鍵已經有 running、有擋下的結果（例如改版後那次被拒收）或可接續的 `llm_result_pending` 不算，不然累積的拒收會讓每次規劃都卡在上限）。超過上限時指令退出碼 1、`radar batches create` 印原因、退出碼 1。
8. **`revision_rerun_max_usd` 預設 5 美元，數字待 Kevin 決定**：每月熔斷線 50 的 10%，留空間給每週新論文與問答。以 Batch 價保守上限粗估（不是實際值，以指令印的為準）：分類表改版約 3 美元會過，情境值清單改版約 6 美元會被擋——刻意的，第一次改情境值清單前要 Kevin 決定。
9. 所有服務用 `require(actor, Action.RUN_AI_JOBS, None)`，不新增 `Action`。退出碼照既有慣例（參數錯 2；找不到、設定錯、讀不到資料庫、沒確認、被擋下、有錯誤 1；Ctrl-C 130）。日誌只記 id、工作、計數、原因代碼與錯誤類別。

## 理由

- 每條寫入路徑都在資料層擋，不靠佇列鎖：重跑靠閘門的 advisory lock＋鎖內 `retry_of` 核對＋running 部分唯一索引；移除靠固定名稱的交易級 advisory lock＋鎖內重查＋單一交易；規劃上限在寫任何列之前判斷。並行、重複執行、中途中斷都有 integration 測試。
- 重跑走同一個閘門，預算、記帳、驗證與接續的規則不用再寫一次；拒收的歷史不被改掉，`show` 看得到每一次。
- 來源記在 run 上，是唯一在摘要列刪掉之後還留著的地方；授權改變時正好會先刪摘要。
- 授權改變就是不能再保留內容，所以直接刪、不複製；稽核只留計數，夠回答「什麼時候、刪了多少」。
- 上限做成設定值而不是寫死：Kevin 看過 `estimate-revision` 的數字再調，不用改程式。

## 取捨

- 遷移前、摘要列已經刪掉的舊 run 回填不到來源：它們的表頭是「來源不明」，`remove-by-source` 不刪，只印計數；真的要刪要另外處理。
- 被刪的 AI 內容找不回來；人工判斷事件還在（分類的人工值仍是有效值），但沒有 AI 值可以對照。
- 移除**不會**刪掉的、同樣從那份摘要衍生的東西：
  - `llm_call.output_text`／`raw_response`（模型當時的輸出原文）：帳本只能新增，應用程式角色不能 UPDATE、DELETE。
  - `embedding` 的向量（向量化的 run 沒記摘要來源）。
  - `construct` 的構面名稱（多篇論文共用，只刪 `construct_mention`）。
  - 分類修正的 `judgment_event.ai_result_id` 會指向已經刪掉的表頭（沒有外鍵，人工值本身照樣有效；只是對不回當時修正的那一筆 AI 結果）。
- 刪完之後仍可能有一列這個來源的新表頭（讀摘要與建 run 不在同一個交易，見選項 3 的說明）；要靠刪完再跑一次預覽發現。
- 重跑上限只看分類表與情境值清單的版本：prompt 升版或換模型也會讓全部論文重跑，但不受 `revision_rerun_max_usd` 管（`estimate-revision` 的說明也寫了），只靠每月熔斷線。
- 每次 Batch 規劃多掃一次候選來算上限（讀，不寫）；論文多時規劃會慢一些。
- 現行結果的 run 沒記設定檔版本（NULL）時，規劃的上限檢查把它當成「版本不同」（保守，可能多算）。
- 超過上限時整次不排，連新論文也一起等；要 Kevin 調上限或分次改版。
- 重跑在鎖內判定 `skipped`（別人已經做了）時退出碼是 0：照確認的結果已經有人做完，不算失敗；只看退出碼的人看不出這次自己沒有呼叫。
- `source_removal` 的鎖鍵定義在 `services/admin_runs.py`（`named_lock_key("source_removal")`），不在 `domain/fingerprints.py` 的共用清單；目前只有這一處用。
- 向量化（`embed`）的 run 先不記來源；向量本身不含摘要文字，等需要時再決定。

## 要 Kevin 決定

- `revision_rerun_max_usd` 要不要維持 5 美元。
- 授權改變時，移除不會刪掉的衍生資料要不要處理（見「取捨」）。可以選的做法：
  - 給應用程式角色 `llm_call` 的欄位級 UPDATE 權限，只用來把那些 run 的 `output_text`／`raw_response` 清成 NULL（帳的金額與 tokens 照留）；
  - 依來源刪掉對應的 `embedding`（要先讓向量化的 run 也記摘要來源）；
  - 維持現狀，只刪結果表與細項。

## 名詞

- **重跑拒收（`retry_of`）**：管理者確認後，讓一筆被拒收的 AI 結果重跑一次；閘門會再核對「它還是最新的那一列」，避免重複付錢。
- **依來源移除**：摘要來源授權改變時，刪掉用那個來源的摘要產生的 AI 結果，預設只印不做。
- **稽核事件**：記下「誰、什麼時候、做了什麼」的一筆紀錄，只新增、不改不刪。
- **改版預估**：改分類表或情境值清單之前，先估下一次 Batch 規劃會重跑幾篇、花多少。
- **重跑上限（`revision_rerun_max_usd`）**：改版後一次規劃最多花多少重跑，超過就整次不排、等人決定。
- **來源不明（表頭）**：看摘要產生、但 run 沒記摘要來源的舊結果，依來源移除不會刪它。
