# ADR-0014：原始資料先存再解析；每週更新把 14 本期刊整本重掃

- 狀態：提議（等 Kevin 在 PR 確認）
- 日期：2026-11-12
- 更新：2026-11-13（決定第 5 項補一段：OpenAlex 的關鍵字比照被引用次數，每週整批覆寫、不算進指紋；單篇查詢不寫關鍵字）
- 對應：PRD FR-2、FR-6、FR-8、FR-9、FR-10；addendum R2；架構文件 AD-2、AD-6、AD-19、AD-25、AD-29

## 背景

PRD 對匯入有三個要求，合在一起才有這份 ADR：

- **FR-2**：每次抓到的 OpenAlex 原始 JSON 都要保存；之後要加欄位時，只靠已經存下來的原始資料就能重新解析，不用重抓。
- **FR-9**：每週抓「新論文與變動」。變動指摘要補上或更新、撤稿標記、書目更正；被引用次數這種每晚重算的數字不算變動。
- **FR-10**：遵守 OpenAlex 的額度與速率限制，記錄每次呼叫花了多少額度。

查證到的事實（2026-11-12，OpenAlex 官方文件）：

| 項目 | 事實 |
|---|---|
| 「只給我某天之後有更新的論文」（`from_updated_date`、`from_created_date`） | 要付費方案 |
| 免費額度 | 每天 1 美元；清單查詢每次 0.0001 美元 |
| 14 本期刊的論文數 | 2016–2025 年共 9,646 篇（2026-11-11 量的），另加當年度；每頁 100 筆，全部抓一次約 100 次出頭的請求，約 0.01 美元 |

所以「每週只抓有變動的」這條最省事的路，免費方案走不了。

另外，審查時發現一個會讓各 Story 做出不同東西的地方：論文來源的轉接器（`PaperSource`）要回傳「解析好的論文」還是「原始內容」，兩種寫法都說得通，但只有一種能保證「先存再解析」。

## 考慮過的選項

**每週怎麼抓**

- **A. 用 `from_updated_date` 只抓有更新的。** 最省請求數，但要付費方案。
- **B. 每週把 14 本期刊從 2016 年起整本重掃，自己比對哪些變了。**
- **C. 只抓最近出版的論文。** 請求數最少，但舊論文後來補上的摘要、撤稿、書目更正都抓不到，FR-9 的「變動」做不到。

**原始資料放哪裡**

- **甲. 放資料庫（`jsonb` 欄位）。** 查起來方便，但每天的資料庫備份都會帶著它，而且資料庫是租來的小型方案，空間比物件儲存貴。
- **乙. 壓縮後放物件儲存，資料庫只記「哪一筆、什麼時候抓的、內容指紋」。**

**`PaperSource` 回傳什麼**

- **一. 解析好的論文。** 轉接器裡自己解析。寫起來直覺，但「原始內容有沒有先存」變成每個轉接器自己要記得做的事，欄位也可能在轉接器裡就被丟掉。
- **二. 原始紀錄，不解析。** 存檔與解析是流程裡固定的下兩步。

## 決定

**B＋乙＋二。**

1. **`PaperSource` 只負責抓，回傳原始紀錄**：來源、外部鍵（例如 OpenAlex ID）、原始位元組、抓取時間。不解析，也不挑欄位；引用清單（`referenced_works`）等現在用不到的欄位都留著（FR-8）。
2. **每一筆（一篇論文一筆）先存起來**：壓縮後放物件儲存，路徑是 `raw/<來源>/<內容的 SHA-256>.json.gz`；資料表 `raw_fetch` 記一筆（來源、外部鍵、SHA-256、抓取時間）。內容和上次一模一樣時不重存檔案，只多記一筆抓取時間（FR-2）。
3. **解析是純函式**，放在 `domain/parsers/`，輸入只有已經存下來的原始內容。每個來源一個解析函式，輸出同一種資料型別 `ParsedPaper`。論文只能用 `ParsedPaper` 寫進資料庫（`repo.papers.upsert_by_external_id`，架構文件 AD-6），所以沒有「跳過解析直接寫」的路。
4. **流程固定四步**：抓 → 存原始 → 解析 → 寫入。`radar reparse` 可以不連網路，只重跑後兩步；這就是 FR-2「加一個欄位不用重抓」的驗收方式。每週更新與 `reparse` 的「寫入」分兩段做（下面「寫入分兩段」）；`reparse` 共用的只有「先放暫存表、最後一個交易套用」，它不抓取、不指定新論文的快照、不建立也不發佈快照；上傳與推薦清單一次只查一篇，解析後直接寫入。
5. **怎麼判斷一篇論文變了**：從解析後的摘要、撤稿標記、書目欄位算一個指紋（`source_hash`）。指紋變了才重新跑摘要、分類、擷取。被引用次數不算在指紋裡，它每週直接覆寫論文上的欄位，不觸發任何重新處理。
   - **OpenAlex 的關鍵字比照被引用次數**（2026-11-13 補）：不算在指紋裡，每週套用時整批覆寫 `paper_keyword` 裡來源是 `openalex` 的列，不觸發任何重新處理。OpenAlex 換演算法時同一篇論文的關鍵字會變；算進指紋的話，一次改版就會讓全部論文重跑 AI。單篇查詢（上傳、推薦清單）不寫這個來源的關鍵字，只有每週更新寫；所以關鍵字一定和目前的快照同一天，快照日期就是資料截止日（ADR-0016）。單篇查詢進來的論文在下一次整本重掃時補上關鍵字。其他來源的關鍵字（之後自家整理的）不受每週更新影響。
6. **每週更新＝14 本期刊整本重掃。** 用量記在 `api_call`；每日額度寫在設定檔，用到設定的比例就停下，留到下一次排程續跑，不算失敗（架構文件 AD-29）。
7. 每週更新什麼時候建立快照、哪些論文算進數字，見 ADR-0011。

### 寫入分兩段：先放暫存表，最後一個交易寫入

第一版是邊抓邊寫。Codex 審查指出：抓到第 8 本失敗時，前 7 本的舊論文已經被改了（新的摘要、書目、被引用次數），成員看得到這些變動，畫面卻還掛著上一個快照的截至日期。所以改成：

1. **抓取階段**（可以中斷後續跑）：一本一本抓。每一筆照樣先存原始資料、再解析，但解析好的結果只放進暫存表 `ingest_staging`（這一次更新的編號、外部鍵、指紋、抓取時間、解析結果），**不動論文資料**。抓到哪一本、哪一頁記在 `weekly_run`。
2. **套用階段**：14 本都抓完後，開一個交易：從暫存表一批一批讀出來（每批幾百筆），經同一個寫入函式寫進論文資料；被引用次數用一句 SQL 整批更新；指定新論文的快照；發佈快照；結束交易。成功後清掉這一次的暫存列。
3. **失敗時**：抓取階段失敗，下次從斷掉的地方接著抓；套用階段失敗，整個交易取消，暫存表還在，重跑套用就好。兩種情況成員看到的資料與截至日期都不變。
4. **舊的不蓋掉新的。** 例：每週更新抓到摘要 A、放進暫存表後中斷；這期間成員上傳同一篇，單篇查詢抓到比較新的 B 並直接寫入；每週更新續跑時，不能把 A 寫回去。指紋只看得出「不一樣」，看不出誰比較新。所以論文上記每個來源目前這份資料的抓取時間，暫存表的每一列也帶抓取時間；寫入函式先鎖住那篇論文再比較，暫存的比較舊就跳過並計數，一樣新或比較新才寫。被引用次數的整批更新照同一個比較。每週更新、`reparse`、單篇查詢都經過同一個寫入函式，所以都受保護。
   - 實作時要有對應的並行測試，拆 Story 時帶進驗收條件：每週更新抓完、還沒套用時，單篇查詢寫入同一篇比較新的資料；套用之後論文上仍然是比較新的那一份。

**為什麼需要暫存表，不是「抓完直接在一個交易裡解析寫入」**：解析結果要有地方放。放記憶體的話，一萬篇解析好的論文估計要 50–250 MB，worker 的上限只有 400 MB；在交易裡回頭從 R2 讀一萬個原始檔，交易會開很久，也違反「不在開著的交易裡呼叫外部服務」。

**為什麼不是「另外寫好一套表，最後整套換過去」**：上傳、成員的修正、AI 結果隨時都在寫同一批表，整套替換會把抓取期間的這些寫入蓋掉。暫存表只放「這次抓到的結果」，套用時逐筆合併，並照第 4 點比較抓取時間，不會蓋掉別人寫的。

**一個交易撐不撐得住**（粗估，沒有實測）：

| | 平常的每週更新 | 第一次匯入 |
|---|---|---|
| 新增或有變動的論文 | 幾十篇（14 本一年約一千篇，一週約 20 篇，加上少數舊論文的更正） | 約 10,500 篇 |
| 交易裡寫的列數 | 幾百列，加上被引用次數最多約 10,500 列的單欄更新 | 約 5–10 萬列（論文、摘要、識別碼等） |
| 寫入的資料量 | 約 10–20 MB | 資料加索引約 60–170 MB，交易日誌約 60–340 MB（假設見下） |
| 估計時間 | 幾秒到幾十秒 | 幾分鐘；磁碟只有基準速度時可能更久 |
| 暫存表的大小 | 約 30–50 MB，每次清掉 | 同左 |

- **估算用的假設**（都還沒量過）：每篇論文寫 5–10 列（論文、摘要、外部識別碼、作者等）；摘要一筆約 2 KB，其餘每列 0.2–0.5 KB，合計每篇約 4–8 KB；索引約是資料的 0.5–1 倍；交易日誌約是資料加索引的 1–2 倍。10,500 篇因此是 40–85 MB 的資料，加索引 60–170 MB，交易日誌 60–340 MB。來回次數：每批 500 筆、每批幾條 SQL，全部約 100–200 次來回。
- **資料庫主機的限制**（Microsoft 官方文件，2026-11-13 查）：B1MS 是 1 個 vCore、2 GiB 記憶體，主機這一層的磁碟上限是每秒 640 次讀寫與 10 MiB。**磁碟自己的基準更低**：32 GiB 的 Premium SSD 平常只保證每秒 120 次，可以短時間衝到 3,500 次。B1MS 的 CPU 也是「平常低、有額度時才衝得高」的類型。所以不能拿上限直接算時間：照主機上限算，300 MB 約 30 秒；只有基準速度時可能是好幾分鐘。
- PostgreSQL 的交易大小不受記憶體限制：改動是邊做邊寫到磁碟的，所以問題是「要多久」，不是「放不放得下」。
- 交易開著的那幾分鐘：成員照常讀得到舊資料；剛好要改同一篇論文的寫入（例如上傳時補書目）會等它結束。排程在週一凌晨 3 點，影響很小。
- **結論：估計撐得住，但只是估計。** 因為沒有實測，做第一次匯入的那個 Story 要量套用階段的時間，寫回這份 ADR。
- **唯一的例外：開放成員登入之前的第一次匯入**（Kevin 2026-11-13 決定保留這條退路）。套用超過門檻（設定值，預設 10 分鐘）時，第一次匯入可以改成一本期刊一個交易。這和上面「最後一個交易一次切換」不同，只在這個條件下允許：還沒開放成員登入，而且快照 1 還沒發佈，所以沒有任何論文算進數字，也沒有人看得到寫到一半的資料。**開放登入之後的每週更新一律是最後一個交易一次切換，沒有這條退路**（架構文件 AD-19）。

## 理由

1. **整本重掃是免費方案下唯一抓得到舊論文變動的做法**，而且一次約 0.01 美元、約 100 次請求，幾分鐘跑完，不值得為了省這些去付費。
2. **原始資料寫一次、幾乎不讀。** 放物件儲存便宜，也不會讓每晚的資料庫備份變大。資料庫只留查詢需要的那一行索引。
3. **回傳原始紀錄，「先存再解析」才是結構保證的，不是靠人記得。** 轉接器手上沒有解析的程式，丟不掉欄位；解析函式不連網路，可以直接拿存下來的真實回應當測試資料（FR-10 的離線測試）。
4. **加一個資料來源＝一個轉接器加一個解析函式**，流程不用改（設計原則的情境 C1）。

## 取捨

- **FR-2「內容沒變就不重存」幾乎不會成立。** OpenAlex 的被引用次數等指標每晚重算，所以每週大部分論文的原始內容都和上週不同，等於每週多存約一萬個小檔。這是照 PRD 的意思（PRD 明講這些指標「當時的快照事後無法重建」，所以要存），不是多做的。
- **容量只有粗估，沒有實測**：每個檔壓縮後估 2–4 KB，一年約 1–4 GB。R2 的免費空間是 10 GB，還要放成員的 PDF（每人上限 1.5 GB）與資料庫備份。**第一次匯入後要量一次實際大小**，再決定保留規則（例如每篇只留第一份、最新一份、每月一份）；在那之前什麼都不刪。這一項列在架構文件的 Deferred。
- **`raw/` 只有 R2 上的一份**，不在每晚的備份裡（架構文件 AD-28）。萬一遺失，論文目前的資料可以重抓回來，丟掉的是「過去每一週的指標長什麼樣」。
- **每週重掃比只抓更新慢**（幾分鐘對幾秒），而且每一篇都要算一次指紋。量很小，接受。
- **多一張暫存表、多一個步驟。** 換來的是失敗時畫面完全不變。新論文也因此要等 14 本全部抓完才出現，比邊抓邊寫晚幾分鐘。
- **什麼時候重新考慮**：OpenAlex 改變免費額度或收費方式；或追蹤的期刊數增加到一次重掃接近每日額度（現在約用掉 1%）。

## 和 PRD 不一致的地方

- PRD FR-9 的標題是「每週**增量**更新」。這裡的做法對外的效果相同（只有新論文與有變動的論文會被重新處理），但抓取本身是整本重掃，不是增量。
- addendum R2 寫原始 JSON 存「R2 儲存空間（或 jsonb）」，這裡定為物件儲存。LLM 的原始回應比較小、而且要和費用帳本一起查，存在資料庫的 `llm_call`；問答是例外，原始回應只存在問答紀錄裡，隨使用者刪除而消失（ADR-0006）。

## 名詞

- **原始資料**：外部服務回傳的內容，一個位元組都不改地存下來；相對於「解析後」只留我們要的欄位。
- **解析**：把原始內容轉成系統自己的資料格式。
- **純函式**：只看輸入、不連網路也不碰資料庫的函式；同樣的輸入永遠得到同樣的輸出，所以很好測。
- **指紋（雜湊）**：把一段內容算成一串固定長度的字；內容一樣指紋就一樣，用來快速判斷「有沒有變」。
- **整本重掃**：不問「哪些變了」，每次都把整本期刊的論文清單重新抓一遍，自己比對。
- **gzip**：一種常見的壓縮格式；JSON 文字壓縮後通常只剩原本的一兩成。
- **暫存表**：先把結果放著、還不算數的一張表；確定全部成功後才一次寫進正式的資料表。
- **交易**：資料庫把一連串改動綁成「全部成功或全部取消」的一個單位；中途失敗就當作什麼都沒發生。
