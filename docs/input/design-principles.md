# 設計原則（整理自軟工課「AI 時代的細部設計」講義）

> 用途：給 `bmad-architecture` 和之後的開發參考。第 1、2 節現在就適用；第 3 節要到架構階段才決定。

## 1. 核心觀念

- **AI 的預設是「能跑就好」**：只給一句話，會得到一個方法從頭做到尾的程式（層次 1）。沒寫進規格的事，AI 就不會遵守。
- **解耦的操作型定義**：一個需求改變，要動幾個檔案？能不能不連資料庫、不呼叫外部 API 就測試核心邏輯？
- **內聚的操作型定義**：這個類別有幾個「改變的理由」？
- **規則要寫成測試，不能只寫在 prompt**：prompt 會被忘記，測試每次都要過。
- **LLM 的輸出等同使用者輸入**：一律驗證。LLM 只產生「意圖」，事實（論文是否存在、引用來源、費用）由程式決定。
- **先有痛點再抽象（Rule of Three）**：沒有第二種實作之前，不建立 interface。沒有痛點的抽象就是負債。

## 2. 五種設計層次

| 層次 | 做法 | 多隔離了哪種變化 | 代價 |
|---|---|---|---|
| 1 單一 Controller | 一個方法從頭做到尾 | 無 | 1 個類別 |
| 2 BCE | 介面、流程、資料分開 | 入口 | ≈5 |
| 3 分層＋Repository | SQL 集中在 Repository | 資料庫 | ≈7 |
| 4 Strategy／Factory／Adapter | 會變的規則各自一個類別 | 業務規則、外部服務 | ≈12 |
| 5 Hexagonal | 核心定義 port，外圈實作 adapter；依賴全部指向核心 | 所有技術 | ≈16 |

- 層次 4 和 5 的差別在依賴方向：介面由「使用者」一方（核心）定義，資料庫與 SDK 反過來實作它（依賴反轉）。
- 同一個專案的不同模組，可以停在不同層次。

## 3. 架構階段要決定的事（給 bmad-architecture）

### 3.1 本專案的變更情境（用來檢驗每個設計）

| # | 變更情境 | 它在測什麼 |
|---|---|---|
| C1 | 加一個資料來源（例如 arXiv） | 外部 API 的隔離 |
| C2 | 換 LLM 模型或供應商 | LLM 的隔離 |
| C3 | 換 embedding 模型（整個資料庫要重新向量化） | 向量化的隔離與重建流程 |
| C4 | 加一個入口（排程、CLI、MCP） | 流程能不能重用 |
| C5 | 不連網路、不花 API 費用就能跑測試 | 可測試性 |

每個模組選哪一層、各情境要改哪些檔，做成一張比較表（✓ 只新增／△ 小改／✗ 牽一髮動全身），寫進 ADR。

### 3.2 各模組的初步建議（待架構階段確認）

| 模組 | 建議層次 | 理由 |
|---|---|---|
| 論文來源（OpenAlex、Semantic Scholar、Crossref、Unpaywall） | 4–5 | 來源會增加，各家 API 形狀不同 → 每家一個 Adapter，統一轉成同一種 Paper 格式 |
| LLM 呼叫 | 5 | 模型與價格常變；要能用假的 provider 測試；外面包一層預算控管（Proxy） |
| Embedding | 5 | 模型可能更換 |
| 向量儲存 | 3 | 只用 pgvector，先不做抽象 |
| 帳號、收藏、標籤 | 3 | CRUD 為主 |
| 匯出（APA、BibTeX、RIS） | 4 | 一種格式一個 Strategy |

### 3.3 要放進設計的機制

- **架構測試**：用 `import-linter` 在 CI 檢查 core 不得 import httpx、sqlalchemy、anthropic 等套件。
- **CitationValidator**：LLM 回答中引用的每篇論文，必須確認資料庫中存在才能顯示。
- **BudgetGuard**：LLM 呼叫前檢查當月預算，超過就拒絕。
- **入庫流程用 Template Method**：抓取 → 清理（資料品質規則）→ 向量化 → 寫入。
- **冪等**：排程重抓用 DOI／OpenAlex ID 做 upsert；Batch API 重試不得重複送出。
- **測試分兩種**：單元測試用 FakeProvider（確定性、每次 commit 跑）；評估（eval）用真模型跑固定題組，量正確率。
